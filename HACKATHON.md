# Хакатон: кто что делает

Направление — здравоохранение. Двое в команде. Делим по одному признаку:
**нужны ли для задачи локальные модели и снимки.**

У Б их нет и не будет (веса не помещаются в GitHub, снимки пациентов из
клиники не выходят), поэтому Б достаётся всё, что считается по уже
готовому кейсу: мобильное приложение целиком, фронт, отчёты, личный
кабинет. У А — машина с RTX 5090, датасеты и клинические снимки, поэтому А
достаётся всё, где надо что-то посчитать моделью.

Читать до начала: `SETUP.md` — что именно отсутствует в репозитории и что
при этом работает.

## Данные, по которым работает Б

# Б — мобильное приложение, фронт, отчёты

## Б1. Личный кабинет пациента: вход по логину и паролю

**Аутентификации в проекте нет вообще** — это пишется с нуля и блокирует
приложение, поэтому идёт первым.

- хранение пароля — хэшем (`bcrypt`/`argon2`), не в открытом виде;
- сессия или токен, срок жизни, выход;
- **каждый эндпойнт пациента обязан проверять, что это ЕГО данные.** Сейчас
  `/api/patients/{pid}` отдаёт любого по номеру — для демо так можно, для
  кабинета нельзя;
- врачебные экраны (разметка, план, загрузка) пациенту не показываем.

Файлы: новый `research/scripts/patient_auth.py`, правки `demo_server.py`.
Карточки пациентов уже есть в `patients.py`.

## Б2. Мобильное приложение (Flutter) — целиком твоё

Экраны: вход → список исследований → одно исследование (находки, снимок) →
скачать PDF.

- 3D на первом этапе проще показать через WebView на наш вьюер, чем тянуть
  glTF в Flutter. Если останется время — нативно;
- офлайн не нужен, медицинские данные на устройстве не кэшируем;
- язык интерфейса русский, как и везде в проекте.

## Б3. PDF прямо из веба

`cbct_report.py` уже написан и работает из командной строки (reportlab,
зубная формула, находки по специальностям, основание у каждой находки). К
вебу он **не подключён** — это и есть задача:

- `GET /api/cbct/report/{case_id}?model=...` → файл PDF;
- кнопка «Скачать отчёт» во вьюере и в кабинете пациента;
- отдавать с правильным `Content-Disposition`, имя файла — человеческое.

Моделей не требует: отчёт собирается по сохранённым находкам.

## Б4. Новая страница продукта и редизайн

Сейчас интерфейс выглядит как демонстрация возможностей — так и задумывалось.
Нужна вторая страница, где то же самое подано как продукт: скромно,
минималистично, но максимально информативно. Лишнее убрать.

- **главный экран — пациенты**, а не список примеров;
- от каждого пациента — к его исследованиям, от исследования — к находкам;
- фронт собран строками в `demo_static/`, фреймворка сборки нет;
- проверять правки без браузера: вырезать `<script>` из HTML и прогнать
  `node --input-type=module --check`. На этом файле так уже ловилась ошибка,
  из-за которой молча не грузилась вся страница.

## Б5. Автовращение 3D

При открытии модель КЛКТ медленно крутится вокруг горизонтальной оси.

- **останавливать вращение, как только пользователь взял мышь**, и не
  возобновлять: иначе невозможно рассмотреть зуб;
- скорость — порядка оборота за 20–30 секунд, быстрее раздражает;
- через `requestAnimationFrame`, с учётом `prefers-reduced-motion`.

## Б6. Метрики с доверительными интервалами

Международные стандарты отчётности медицинского ИИ (STARD-AI, TRIPOD+AI,
CLAIM) требуют публиковать не голое число, а интервал. Смысл простой: «97.1%»
посчитано на 15 пациентах, на других 15 вышло бы другое число. Интервал
честно показывает, в каком диапазоне лежит настоящая точность. Без него наше
число ничем не отличается от чужих «97%», которые мы сами же критикуем за
отсутствие методологии.

Что сделать:

- **бутстреп по ПАЦИЕНТАМ, а не по зубам.** 2000 итераций (для mAP хватит
  500 — там каждый раз заново запускается COCOeval). Берём пациентов с
  возвращением, пересчитываем метрику, берём 2.5-й и 97.5-й перцентили.
  Зубы одного пациента зависимы, и бутстреп по зубам даст искусственно
  узкий интервал — то есть соврёт в нашу пользу;
- выводить в виде: `Precision 97.1% (95% ДИ 95.0–98.3%), n = 15 пациентов,
  452 зуба`;
- **широкий интервал не прятать, а помечать** — «мало случаев, оценка
  ненадёжна». Это ровно то место, где честность и есть продукт;
- свести всё в одну таблицу и показать её на главной странице.

Вход — JSON с результатом по каждому пациенту (TP, FP, FN, список Dice по
зубам). Его готовит А, задача А1. Сам бутстреп моделей не требует: это
numpy поверх таблицы.

# А — модели, данные, измерения

## А1. Сохранение результатов по пациентам (блокирует Б6)

Проверки сейчас печатают итог в консоль и забывают подробности.
`cbct_eval_external.py` уже считает строку на каждый том — её надо сохранять.

- `--out results.json`: по каждому пациенту TP, FP, FN и список Dice по
  зубам, плюс номер модели и выборка;
- то же для 2D (`eval_ensemble.py`) — там метрика mAP через COCOeval;
- формат один на оба трека, чтобы Б писал бутстреп один раз.

Делать первым: пока его нет, Б6 не с чем сверять.

## А2. Фикстура и поддержка Б

Выложить `fixtures/cbct_pair001` (сделано). Если Б понадобится второй кейс
или срезы — готовит А, потому что для этого нужен том.

## А3. Модельная часть

- дообучение модели канала по разметке врачей (94 зуба в очереди);
- пересборка кейсов при изменении постобработки (`cbct_rebuild.py`);
- пакетный ввоз новых КЛКТ от клиники.

## А4. Ревью

Правки Б приходят ветками. А смотрит в первую очередь: не сдвинуты ли
пороги, не поднят ли `POSTPROC_VERSION`/`FINDINGS_VERSION` без пересборки, не
попали ли в коммит снимки или веса.

## Где стыкуемся

| | кто отдаёт | кто берёт |
|---|---|---|
| `fixtures/cbct_pair001` | А | Б — весь фронт, PDF, приложение |
| `results.json` с метриками | А (А1) | Б (Б6) |
| API пациентов и КЛКТ | есть в `demo_server.py` | Б — приложение и кабинет |
| аутентификация | Б (Б1) | А — подключит к рабочему серверу |

Порядок внутри Б: **Б1 → Б3 → Б4 → Б5 → Б2 → Б6.** Вход нужен приложению;
PDF и автовращение — быстрые и сразу видны; приложение самое долгое;
метрики ждут А1.
