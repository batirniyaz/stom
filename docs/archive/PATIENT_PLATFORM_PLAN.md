# План: от набора демо-экранов к платформе «пациент → исследования → план»

Составлен 06.09.2026. Реализация НЕ начата — это план к обсуждению.

## Зачем это вообще

Сегодня продукт устроен вокруг ФАЙЛА, а врач работает вокруг ПАЦИЕНТА.
Кейс КЛКТ, скан и снимок ОПТГ живут в трёх несвязанных папках и ничего не
знают друг о друге; 2D-снимок вообще не сохраняется — он предсказывается из
временного файла и удаляется. Поэтому нельзя ответить на вопрос, с которого
начинается любой приём: «что у нас есть по этому человеку».

## Что есть сейчас (замер по коду, а не по памяти)

```
хранилище КЛКТ    research_3d/web_cases/<case_id>/meta.json + volume/mask/mesh
хранилище сканов  research_ios/web_cases/<id>/scan.glb, findings.json, occlusion.json
2D-снимки         НЕ хранятся: tempfile -> предсказание -> удаление
связь между ними  только register_<кейс>.json при суперимпозиции
загрузка          /api/cbct/upload (КЛКТ), /api/predict (2D), для скана ЕЁ НЕТ
фронт             demo_static/index.html 144 КБ одним файлом, ios_static 37 КБ
аутентификация    отсутствует; наружу сервис выходит через Cloudflare Tunnel
```

## Решение до кода: персональные данные

Как только в системе появятся фамилия и дата рождения, это перестанет быть
демо-стендом и станет хранилищем персональных медицинских данных, открытым
наружу без входа по паролю. Это не «доделаем потом»: сегодня ссылку на
туннель может открыть любой, кому она попала.

Поэтому вход по паролю входит в ЭТОТ план (этап 7), а до его готовности
предлагается хранить пациента как «фамилия + инициалы + номер карты
клиники», без полной даты рождения — для возраста достаточно года.

## Модель данных

Три уровня, разделять их обязательно — иначе повторится нынешняя каша.

**Пациент** — человек. `id`, фамилия и имя, год (или дата) рождения, пол,
номер карты клиники, заметка, даты создания и правки. Возраст НЕ хранится, а
вычисляется: сохранённый возраст устаревает молча.

**Исследование** — один загруженный набор данных. `id`, `patient_id`,
`тип` (`cbct` | `opg` | `periapical` | `ios`), дата съёмки (из DICOM, если
есть) и дата загрузки, аппарат, статус (`uploaded → processing → ready |
error`), путь к данным.

**Анализ** — результат обработки одного исследования: находки, версии правил
(`POSTPROC_VERSION`, `FINDINGS_VERSION`), отметки врача и подпись. Хранится
рядом с исследованием, а не с пациентом: подпись относится к конкретному
снимку и конкретной версии правил.

**Сводный план** собирается ПО ПАЦИЕНТУ из анализов всех его исследований.
Сейчас план считается по одному кейсу, и это тупик: у пациента с КЛКТ и
сканом получилось бы два несвязанных плана.

## Хранилище

```
data/patients/<patient_id>/
    patient.json
    studies/<study_id>/
        study.json       тип, даты, аппарат, статус
        source/          как прислали: ZIP с DICOM, STL, JPG
        derived/         volume.mha, mask_*.mha, mesh_*.glb, scan.glb, panorama
        analysis.json    находки, отметки, подпись
```

Индекс — **SQLite** (`data/index.db`), файлы остаются файлами. Почему не
JSON, как сейчас: список пациентов нужен с поиском по фамилии, сортировкой и
проверкой на дубли, а это на россыпи JSON-файлов разваливается уже на первой
сотне записей. SQLite есть в стандартной библиотеке и сервера не требует.

Исходники храним ВСЕГДА (`source/`): при смене версии правил анализ можно
пересчитать, а исходник заново не появится. Это же закрывает нынешний провал
с 2D-снимками, которые сейчас исчезают после предсказания.

**Миграция:** существующие client2..client5 и сканы становятся пациентами с
пометкой «пример», по одному исследованию на кейс. Прямые ссылки
`/cbct/<кейс>` и `/ios/<кейс>` продолжают работать — врачу уже давали такие
ссылки.

## Очередь задач (без неё платформа развалится)

Инференс КЛКТ и сегментация скана требуют видеокарты. Два одновременных
запуска уводят память в спилл — в этой сессии так и вышло: одна пересборка
заняла 94 ГБ оперативной памяти, и всё встало. Значит нужна ОДНА очередь на
GPU: задачи выполняются по одной, у каждой статус и место в очереди, врач
видит «третий в очереди», а не пустой экран.

## Загрузка исследований

Единый диалог: перетащить файлы -> система предлагает тип, врач подтверждает.

```
DICOM-серия (много файлов)   -> КЛКТ
один DICOM / JPG / PNG       -> ОПТГ или прицельный (выбор врача)
STL / PLY / OBJ              -> интраоральный скан
```

Скана сегодня нет вовсе — это отдельная работа: приём двух челюстей
(обычно два файла), определение верх/низ по имени файла и по геометрии,
запуск `ios_build_mesh` (сегментация DGCNN на GPU), затем `ios_build_raw`,
`ios_occlusion`, `ios_findings`. Всё через ту же очередь.

Анализ идёт по каждому исследованию отдельно. Нет ОПТГ — считается только то,
что загружено; сводный план собирается из имеющегося и честно говорит, чего
не хватает («периапикальные очаги на КЛКТ не оцениваются — нужен прицельный
снимок»).

## Экраны

```
/patients                     список: поиск по фамилии, дата последнего исследования
/patients/new                 создание карточки
/patients/<id>                карточка: данные, лента исследований, сводный план
/patients/<id>/upload         загрузка исследования
/studies/<study_id>           просмотр: тот же вьюер, что сейчас, но внутри пациента
/cbct/<кейс>, /ios/<кейс>     остаются как прямые ссылки (обратная совместимость)
```

Карточка пациента — главный экран: слева данные и список исследований
(значок типа, дата, статус), справа сводный план и находки по специальностям.

## Дизайн и юзабилити

Что чинить — по тому, что уже видно на приёме:

1. **Единый каркас.** Сейчас два независимых вьюера с разной шапкой и
   навигацией. Нужен общий: шапка с пациентом, переключатель исследований,
   область просмотра.
2. **Разбить монолит.** 144 КБ и около 3000 строк в одном файле — правки в нём
   уже ломали соседнее (чёрный экран из-за функции, объявленной в другом
   блоке). Вынести: `viewer3d.js`, `findings.js`, `chart.js` (зубная карта),
   `i18n.js` (уже общий), `upload.js`.
3. **Состояние в адресе** — принцип уже принят, распространить на пациента:
   `/patients/<id>?study=<sid>&tab=findings&tooth=13`.
4. **Пустые состояния честные.** Уже исправлено на скане («находки не
   посчитаны» вместо «находок не выявлено») — сделать так же везде.
5. **Прогресс вместо тишины:** место в очереди, оценка времени, что именно
   считается сейчас.

## Оптимизация (по замеренному, не по ощущениям)

| что | сейчас | предложение |
|---|---|---|
| фронт | 144 КБ на любом экране | модули по экрану |
| меш кейса | 5–7 МБ, `no-store` — качается заново каждый раз | ETag по версии меша, кэш в браузере |
| GLB | без сжатия | Draco: ожидаемо 6 МБ -> около 1 МБ |
| GPU | конкурирующие запуски, спилл | одна очередь |
| находки | ускорены в 10 раз (SVD) | профилировать остальное так же |

Кэширование мешей — самый заметный выигрыш для врача: сейчас `no-store` стоит
на всём, включая шестимегабайтные меши, потому что иначе браузер отдавал
устаревшие. С ETag по версии обе задачи решаются разом.

## Порядок работ

```
1. Модель данных, SQLite-индекс, миграция существующих кейсов   (без UI)
2. Очередь задач на GPU + статусы
3. API пациентов и исследований
4. Экраны: список, карточка пациента, загрузка
5. Загрузка интраорального скана (новая функциональность)
6. Перевод вьюеров на исследования, общий каркас, разбиение фронта
7. Вход по паролю — ДО работы с реальными пациентами
8. Оптимизация: Draco, ETag, модульная загрузка
```

Этапы 1–4 дают работающий каркас: можно завести пациента, загрузить КЛКТ и
увидеть анализ в его карточке. Этап 5 добавляет скан. Этап 7 обязателен
перед реальными данными.

## Принятые решения (06.09.2026)

- **Хранилище:** `D:\code\dbc\stomadent\data`, каталог создаётся сам.
  Путь настраивается переменной окружения `STOMADENT_DATA` — данные потом
  переедут на другой том, и переезд не должен требовать правки кода.
- **Персональные данные:** на этапе показа врачам реальные имена вводить не
  будут, поэтому вход по паролю отложен. Структура при этом рассчитана на
  реальные данные, чтобы не переделывать её потом.
- **Порядок:** начинаем с каркаса пациентов (этапы 1–4).

## Что решено отложить

1. **Где хранить данные.** Диск `D:` рядом с research или отдельный том?
   Один пациент с КЛКТ занимает около 500 МБ (том, маски, меши).
2. **Полнота персональных данных.** Полные ФИО и дата рождения — или
   фамилия с инициалами и номер карты, пока нет входа по паролю?
3. **Вход по паролю** — делать на этапе 7 или раньше, если реальные пациенты
   появятся сразу?
4. **Сколько моделей считать по умолчанию.** Сейчас КЛКТ считается моделью
   `sp`; считать ли сразу и `pretrained` — вдвое дольше, но врач сможет
   сравнить, не дожидаясь пересчёта.
