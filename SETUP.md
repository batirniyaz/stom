# Что НЕ лежит в репозитории и как без этого работать

Читать первым, до `CLAUDE.md`. Этот файл отвечает на один вопрос: почему
после `git clone` половина проекта не запускается и что с этим делать.

`CLAUDE.md` — рабочий журнал проекта: замеры, пороги, отрицательные
результаты. Он описывает код, который лежит рядом, и ему можно верить. Но он
писался на машине, где есть всё: модели, датасеты, снимки клиники. В
репозитории ничего этого нет.

## Чего нет и почему

| | объём | почему не в git |
|---|---|---|
| веса моделей | 9.7 ГБ | четыре файла по 119 МБ, жёсткий лимит GitHub — 100 МБ на файл |
| датасеты | 152 ГБ | объём; плюс ToothFairy3 некоммерческий, распространять его копию мы не вправе |
| снимки и карточки пациентов | 14 ГБ | медицинские данные клиники, за пределы машины не выходят |
| `data/` | — | там же ключ API и база пациентов |

Исключения расписаны в `.gitignore` с причинами.

## Что РАБОТАЕТ без моделей и снимков

Это главное, что надо понять: моделей требует только **инференс** — разбор
нового снимка. Всё, что показывается по уже посчитанному кейсу, считается
геометрией и обычным кодом:

- 3D-вьюер КЛКТ: меш, зубы поштучно, прозрачность, срезы по готовой маске;
- слой находок и план лечения — это геометрия поверх маски, не сеть;
- PDF-отчёт (`cbct_report.py`);
- карточки пациентов, исследования, сводка;
- весь фронт, вся вёрстка, вся навигация;
- мобильное приложение целиком.

**Не работает без весов:** разбор нового снимка (2D-инференс), сегментация
нового КЛКТ, дорисовка каналов, сегментация сканов, обучение чего угодно.

Сервер при отсутствии весов **поднимается нормально** и отдаёт на
инференс-запросы 503 с объяснением — см. `require_models` в
`demo_server.py`. Падать на импорте он не должен; если упал, это ошибка.

## С чего начать

```bash
python -m venv .venv
.venv/Scripts/pip install -r requirements.txt   # на Windows
# torch можно ставить обычный, CPU-сборка подойдёт: инференса всё равно нет
.venv/Scripts/python.exe research/scripts/demo_server.py --port 7861
```

`requirements.txt` **устарел** — в нём нет fastapi, uvicorn, reportlab,
trimesh, SimpleITK, scikit-image. Ставить точечно, по ошибкам импорта.
Переустанавливать окружение по этому файлу не надо.

Консоль на Windows живёт в cp1252, а проект в UTF-8. Русский `print` роняет
скрипт на ровном месте — запускать с `PYTHONIOENCODING=utf-8`.

## Данные для разработки

`fixtures/cbct_pair001/` — готовый кейс КЛКТ: меш и находки. Из публичного
набора figshare 26965903 под CC BY 4.0, поэтому лежать в репозитории может.
По нему делается 3D, находки, план, PDF и мобильное приложение — без единой
модели.

**Копировать никуда не надо.** Кейс подхватывается при старте
(`cbct_backend.register_fixtures`) и появляется в списке примеров. Открыть:

```
http://127.0.0.1:7861/cbct/pair001_cbct/sp
```

Проверено на чистом клоне без весов: список примеров отдаёт кейс, находки
34 КБ, меш 7 МБ, страница КЛКТ грузится.

У фикстуры нет тома (300+ МБ) — значит нет срезов и нельзя пересчитать
маску. Всё остальное работает. `has_volume: false` у кейса — это признак, а
не поломка.

Клинические кейсы так отдать нельзя: это снимки пациентов.

**Оговорка по этому кейсу.** Он из исследовательского набора, и находки на нём
местами странные: у зуба 28 стоит «не дошёл до зубного ряда на 41.4 мм», чего
анатомически быть не может, и к тому же зубу привязаны шесть «коронок». Замер
по 18 кейсам: это единственный такой выброс из 40 находок ретенции, остальные
11–15 мм. То есть код исправен, а кейс неудачный. Для вёрстки это не мешает,
для показа используется клинический кейс.

## Чат по кейсу (`case_chat.py`)

```
POST /api/cbct/chat/{case_id}   {"question": "...", "model": "sp"}
  -> {"answer": "...", "used": ["canal_close:38", ...],
      "grounded": true, "blocked": null, "provider": "..."}
```

`used` — ключи находок, те же, что у отметок врача (`cbct_backend.finding_key`).
Поэтому ссылку под ответом делают кликабельной и ведут в ту же строку ленты.

`grounded: false` означает, что ответ не подкреплён данными кейса и вместо
него показан отказ; `blocked` говорит, почему. Это нормальный ответ, а не
ошибка — показывать его надо как есть.

Нужен ключ: `ANTHROPIC_API_KEY` в `data/secrets.env` (файл в `.gitignore`).
Без ключа эндпойнт отдаёт 503 с объяснением. Ключ не передавать и не
коммитить — каждый работает со своим.

## Карта кода

```
research/scripts/
  demo_server.py        главный сервер (:7861): API + отдача фронта
  demo_static/          вьюер, одна страница на three.js; patients.html, study.html
  cbct_backend.py       вся 3D-логика КЛКТ: маска, постобработка, меш
  cbct_findings.py      находки на зуб; cbct_perio/endo/bone_* — измерения
  cbct_plan.py          находки -> услуги -> этапы лечения
  cbct_report.py        PDF-отчёт (reportlab). Написан, но к вебу НЕ подключён
  patients.py           карточки пациентов, база в data/
  study_pipeline.py     конвейеры обработки снимков
  annotate_server.py    разметка панорам врачами (:7862)
  canal_annotate_server.py  разметка каналов КЛКТ (:7863)
```

Эндпойнты пациентов уже есть: `/api/patients`, `/api/patients/{pid}`,
`/api/patients/{pid}/summary`, `/api/patients/{pid}/plan`,
`/api/patients/{pid}/studies`, `/api/studies/{sid}`, `/api/studies/{sid}/teeth`.
КЛКТ: `/api/cbct/examples`, `/api/cbct/info/{case}`, `/api/cbct/findings/{case}`,
`/api/cbct/mesh/{case}`, `/api/cbct/tooth/{case}/{fdi}`.

**Аутентификации в проекте нет вообще.** Для личного кабинета пациента её
надо написать с нуля.

## Соглашения, которые легко нарушить

- **Код, комментарии и интерфейс — на русском.** Проект для рынка
  Узбекистана. Русские строки в вёрстке при правках сохранять.
- **Комментарий объясняет ПОЧЕМУ, а не что делает строка.** Особенно у
  эмпирических порогов: рядом с числом должен стоять замер, по которому оно
  выбрано. Образец стиля — `cbct_backend.py`.
- **Никогда `git add .`** — затянет десятки гигабайт, если данные окажутся
  на месте.
- **Ответы API отдаются с `Cache-Control: no-store`** (меши и срезы
  перестраиваются между версиями). Middleware в `demo_server.py`.
- **Пути из HTTP валидируются** регуляркой и проверкой родительского
  каталога — образцы `_example_path`, `dataset_dir`, `get_case`.
- **Имя человека не попадает ни в код, ни в комментарии, ни в документацию.**
  Для ссылки на замер хватает идентификатора кейса.
- Тестов, линтеров и CI нет. Проверка ручная: запустить и посмотреть.

## Чего НЕ делать

- Не менять пороги в `cbct_*` и `ios_*`: каждый подобран замером, который
  записан рядом в комментарии и в `CLAUDE.md`. Изменение без перепроверки на
  тех же кейсах ломает находки молча.
- Не трогать `POSTPROC_VERSION` и `FINDINGS_VERSION`: они инвалидируют кэш
  мешей и находок, а пересобрать их без моделей нельзя.
- Не переписывать `wbf()` — он продублирован в трёх файлах и обязан
  совпадать, иначе демо и разметка разойдутся с метриками.

## Скрипты запуска лежат в `scripts/`

`scripts/start_demo.bat` — демо, `scripts/start_all.bat` — все четыре сервиса,
`scripts/start_stomadent.bat` — боевой запуск с туннелем, `scripts/install_*` —
установка служб и автозапуска. Пути внутри считаются от КОРНЯ проекта, а не от
папки скрипта, поэтому запускать можно откуда угодно.

**Если этот репозиторий разворачивается на машину клиники — автозапуск надо
перерегистрировать.** Задача планировщика `Stomadent` и обёртка в папке
«Автозагрузка» хранят АБСОЛЮТНЫЙ путь к `start_stomadent.bat`, и обе лежат вне
гита. После переезда файла в `scripts/` старый путь указывает в пустоту: демо
не поднимется после перезагрузки, снаружи будет 502, а в журнале — ничего.
Лечится повторным запуском `scripts/install_boot_task.bat` (от администратора)
или `scripts/install_autostart.bat`: оба прописывают путь от своего нового
расположения.

Проверять это надо **не входя в систему** — перезагрузить и открыть сайт с
телефона. Вход в учётную запись запускает автозапуск из «Автозагрузки» и
маскирует отказ задачи.
