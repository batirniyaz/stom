## СНАЧАЛА ПРОЧИТАЙ `SETUP.md`

Этот файл — рабочий журнал проекта, и он описывает машину, где есть ВСЁ:
веса моделей, 152 ГБ датасетов, снимки клиники. **В репозитории этого нет** —
ни весов (файлы больше лимита GitHub в 100 МБ), ни датасетов (объём и
лицензии), ни снимков пациентов (медицинские данные за пределы клиники не

воспроизводится, и это не поломка.

`SETUP.md` отвечает, что при этом всё-таки работает — а работает многое:
3D-вьюер, находки, план лечения, PDF, карточки пациентов считаются по уже
готовым кейсам, а не моделями. Там же: как поднять сервер без весов и какой
кейс взять как данные для разработки.

Деление задач между двумя разработчиками — в `HACKATHON.md`.

## Что это за проект

**Stomadent** — AI-диагностика в стоматологии (аналог Diagnocat). Фаза «research»:
всё живёт в `research/` (2D) и `research_3d/` (3D), production-код (`src/`) ещё не
начат. Два независимых трека, объединённых одним демо-сервером:

| Трек | Данные | Модель | Задача |
|------|--------|--------|--------|
| **2D** | Панорамные снимки (OPG), DENTEX | Ансамбль YOLO12x + YOLO26x-tuned (WBF) | Детекция 4 патологий |
| **3D** | КЛКТ (CBCT), ToothFairy2 | nnU-Net v2 3d_fullres | Сегментация 48 анатомических классов |

Классы 2D: `0 Impacted` (ретенированный), `1 Caries` (кариес),
`2 Periapical Lesion` (периапикальное поражение), `3 Deep Caries` (глубокий кариес).

### Адресация экранов (URL)

Каждый экран демо адресуется путём, чтобы врачу можно было дать ССЫЛКУ, а не
инструкцию «нажмите сюда, потом сюда». Маршруты объявлены в `demo_server.py`
ДО `app.mount("/")`, иначе статика перехватит всё:

```
/2d                      двумерные снимки (ОПТГ)
/cbct                    КЛКТ: загрузка и примеры
/cbct/<кейс>             кейс с моделью по умолчанию
/cbct/<кейс>/<модель>    ours | pretrained | tf3
/ios                     интраоральные сканы (без кейса — первый доступный)
/ios/<кейс>              сегментация
/ios/<кейс>/raw          исходный скан
```

Плюс `?tab=` (какая вкладка панели открыта) и `?tooth=` (открытая карточка зуба). Фронт читает `location.pathname`
при старте и переписывает адрес через `history.replaceState` при каждом
переключении, поэтому строка адреса всегда отражает то, что на экране.

**Гоча:** блок разбора адреса в `demo_static` стоит в КОНЦЕ модульного
скрипта. Сверху он падал: `showView` трогает `renderer`, объявленный через
`let` ниже по файлу, — временная мёртвая зона роняла весь модуль, и вместе с
ним не грузились примеры. Симптом обманчивый: пустой список примеров, а
причина — совсем в другом месте.

Панели разбиты на вкладки (у КЛКТ: находки, план, срезы, кейс; у скана:
модель, находки, план). Одна лента на 40 находок не читается — это была прямая
просьба с приёма.

- **demo_server.py :7861** — главный: 2D-инференс + весь КЛКТ-функционал.
  FastAPI + `demo_static/index.html` (одна страница, ~1500 строк, three.js с CDN
  через importmap). Слушает `127.0.0.1`; наружу — только через Cloudflare Tunnel
  (`install_tunnel_service.bat`, запуск от администратора).
- **annotate_server.py :7862** — менеджер клинических датасетов и проверка
  AI-разметки врачом.
- **app_ui.py :7860** — старый Gradio-UI на одной модели YOLO12x. Легаси, не
  развивается; новую функциональность добавлять в demo_server.
- **monitor_server.py :8080** — мониторинг обучения (логи, `results.csv`,
  nvidia-smi). Только stdlib, без FastAPI.

Все веса грузятся в память один раз при старте сервиса — перезапуск демо стоит
около минуты (плюс фоновый прогрев двух моделей nnU-Net).

## 2D-трек: DENTEX → YOLO → ансамбль

Конвейер данных (конвертеры кладут hardlinks, а не копии):

```bash
.venv\Scripts\python.exe research\scripts\download_dentex.py --download   # 11.8 ГБ
.venv\Scripts\python.exe research\scripts\convert_dentex_yolo.py          # -> dentex_yolo/  (обучение YOLO)
.venv\Scripts\python.exe research\scripts\convert_dentex_coco.py          # -> dentex_coco/  (RF-DETR + COCOeval)
.venv\Scripts\python.exe research\scripts\augment_rare_classes.py         # -> dentex_yolo_aug/
```

Из COCO берётся только `category_id_3` (патология); зубы без патологии
отбрасываются. `dentex_yolo_aug/dentex_aug.yaml` использует train из аугментации,
а **val — исходный** (иначе метрики нечестные).

`augment_rare_classes.py` — position-aware copy-paste: объект редкого класса
вырезается по полигональной маске и вставляется в ту же нормализованную позицию
другого снимка (панорамы стандартизированы по композиции). Копий: Impacted ×2,
Periapical ×8, Deep Caries ×3.

Обучение и оценка:

```bash
.venv\Scripts\python.exe research\scripts\train_yolo.py --model yolo12x.pt --imgsz 960 --batch 8
.venv\Scripts\python.exe research\scripts\train_rfdetr.py --resolution 784 --batch 4 --grad-accum 4
.venv\Scripts\python.exe research\scripts\eval_ensemble.py    # COCOeval: модели по отдельности vs WBF
```

Высокое разрешение критично (кариес мелкий), но 1152 и 1280 в экспериментах
проиграли 960 — см. `research/output/runs/` и логи `train_*.log`. Обучение пишет
в `research/output/runs/<name>/`, финальная валидация — в `<name>_val/`.

Достигнутые mAP50: ансамбль **0.665**, yolo12x 0.647, yolo26x 0.596,
yolo26x_tuned 0.592. RF-DETR заметно хуже, дальше не развивается.

### Ансамбль (WBF)

Инференс обеих моделей с низким порогом `conf=0.05`, слияние Weighted Boxes
Fusion по классам (`iou=0.55`), затем фильтр по пользовательскому порогу (0.25).
Score после слияния = средний вес × бонус за согласие моделей.

**Реализация `wbf()` продублирована в трёх местах** — `demo_server.py`,
`annotate_server.py`, `eval_ensemble.py` (`preannotate_clinic.py` импортирует
версию из `eval_ensemble`). Меняя пороги или формулу — синхронизировать все,
иначе демо и разметка разъедутся с метриками.

Новую модель подключать в `MODELS_INFO` (`demo_server.py`) и `MODEL_WEIGHTS`
(`annotate_server.py`).

## 3D-трек: КЛКТ (nnU-Net)

`research/scripts/cbct_backend.py` (~700 строк) — вся 3D-логика; `demo_server.py`
только отдаёт её через `/api/cbct/*`. Кейсы лежат в `research_3d/web_cases/<case_id>/`
(`volume.mha`, `mask_<model>.mha`, `mesh_<model>.glb`, `meta.json`) и переживают
перезапуск сервера через `meta.json`. Примеры `client2..client5` регистрируются
по абсолютным путям из `research_3d/inference_input|output` без копирования.

Пайплайн одного кейса (фоновый поток, стадии `ready → predicting → meshing → done|error`,
фронт опрашивает `/api/cbct/status/<id>`):

```
ZIP/DICOM-серия → SimpleITK → volume.mha → nnU-Net → mask.mha
                                    ↓
              HU-гейт + connected components (фильтрация артефактов)
                                    ↓
             marching cubes → decimate → smooth → GLB (three.js)
```

Две модели:
- `ours` — `nnUNetTrainer__nnUNetPlans__3d_fullres`, обучена локально (Dataset112,
  480 кейсов, fold 0: 384/96, 1000 эпох, ~60 с/эпоху). Быстрая.
- `pretrained` — `nnUNetTrainer__nnUNetResEncUNetLPlans__3d_fullres`, чекпойнт
  бенчмарка ToothFairy2 (`research_3d/datasets/toothfairy2_checkpoints/`). Точнее,
  но тяжелее; локальное дообучение было прекращено (~1000 с/эпоху).

### Гоча 3D

- **Переменные окружения nnU-Net** (`nnUNet_raw` / `_preprocessed` / `_results`)
  выставляются в `cbct_backend.py` **до** любого импорта `nnunetv2`. Не переносить
  импорты наверх файла.
- **multiprocessing nnU-Net на этой Windows ломается**: использовать
  однопроцессный `nnUNetPredictor.predict_single_npy_array` (образец —
  `research_3d/inference/predict_single.py`), CLI `nnUNetv2_predict` не применять.
- **Постпроцессинг маски против металлоартефактов КЛКТ** — три ступени: HU-гейт по
  физическому диапазону ткани (кость ≥300, реставрации ≥800, воздух ≤−300), затем
  фильтр связных компонент, затем форм-правило (тонкая вытянутая компонента =
  streak) плюс отдельная логика для зубов (`opening(2)` и слияние фрагментов по
  расстоянию центроидов). **Все пороги подобраны замерами на конкретных кейсах**
  (client2, client4, кейс клиники) и задокументированы в комментариях; менять только
  с перепроверкой на тех же кейсах.
- **Не сглаживать меш средствами trimesh.** `filter_laplacian` / `filter_taubin` /
  `filter_humphrey` в trimesh 5.0.0 на упрощённых мешах строят оператор со
  строками, сумма которых < 1 (замер: 0.455 вместо 1.0) — вершину утягивает к
  началу координат на десятки мм, и меш обрастает шипами. Это была причина
  «оттеков» в 3D-виде (замер на client5: после decimate ребро max 10.8 мм, после
  filter_laplacian — 46.3 мм и 1161 грань висит вне маски). Сглаживание сейчас
  делается **гауссовым размытием маски** до marching cubes (`MESH_BLUR_SIGMA`).
- Нормали marching cubes смотрят внутрь — `_class_mesh` разворачивает меш по
  знаку `volume`. Без этого фронт с `side: FrontSide` (зубы, нерв, реставрации)
  отсекает лицевые грани и поверхность светится «наизнанку».
- **Пульпа обязана лежать внутри своего зуба** (её класс = класс зуба + 100).
  Модель это иногда нарушает: на client4 пульпа 128 оказалась целиком вне
  зуба, у 123 оторвался кусок. Правило `_filter_pulp`: компонента остаётся,
  если МЕДИАНА расстояния её вокселей до своего зуба ≤ 1.0 мм. Медиана, а не
  минимум (сбойная пульпа может краем касаться) и не максимум (у нормальной
  канал законно выходит за апекс). Замер: у всех здоровых пульп client4 и
  client5 медиана 0.3–0.4 мм, у сбойных 1.2 и 2.5 мм. Контроль чистый —
  на client5 правило не тронуло ни одной пульпы.
- При изменении правил фильтрации **или `_class_mesh`** инкрементировать
  **`POSTPROC_VERSION`** — иначе старые меши и `info` не инвалидируются при
  старте сервера. Инвалидация удаляет `mesh_*.glb` прямо при импорте модуля:
  скрипт, который пересобирает меши, обязан записать `info` через `_save_meta`,
  иначе следующий импорт снова их снесёт.
- **Находки тоже кэшируются — и у них СВОЯ версия, `FINDINGS_VERSION`.**
  Слой находок лежит в `meta.json` рядом с `info`, а `findings_for` раньше
  отдавал что лежит, вообще не сверяя модель: находки, посчитанные другой
  моделью или прошлой версией правил, молча доживали до врача. Симптом
  обманчив — скрипт в консоли показывает новые находки, а демо старые.
  Инкрементировать при изменении находок или порогов в `cbct_findings`,
  `cbct_perio`, `cbct_endo`. `POSTPROC_VERSION` для этого не годится: он
  про маску и меши, а находки могут поменяться при той же маске.
- **Находка на СПИСОК зубов несёт поле `teeth`, а не только `tooth`.**
  Пародонт и эндодонтия относятся к группе зубов сразу. Фронт рисует значок
  на каждый зуб и делает его кликабельным (клик подводит камеру); находка без
  `teeth` показывается прочерком и никуда не ведёт. Заводя такую находку,
  поле `teeth` заполнять обязательно — текста мало.
- Сырая маска на диске не переписывается: фильтрация применяется на лету, при
  рендере срезов и мешинге.
- Кэш массивов `_arr_cache` рассчитан **на один кейс** (том ~300 МБ + маска ~150 МБ);
  переключение кейса вытесняет предыдущий.
- Координаты: nnU-Net/SimpleITK работают в `(z, y, x)`, при экспорте GLB вершины
  переставляются в `(x, z, y)` — ось срезов смотрит вверх в three.js.
- 48 классов ToothFairy2 сгруппированы в 6 групп (`GROUPS`: челюсть, зубы, нерв,
  пазухи, реставрации, дыхательные пути) с цветом и прозрачностью; зубы
  экспортируются отдельными нодами `tooth_<FDI>` для поштучного управления.

## Разметка клинических данных

`annotate_server.py` — цикл model-assisted labeling: загрузка снимков → фоновая
AI-преразметка ансамблем → правка врачом в браузере.

`research/datasets/annotation_sets/<slug>/`:
- `labels/` — AI, **6 полей**: `cls cx cy w h score`
- `labels_human/` — врач, **стандартный YOLO, 5 полей**
- наличие `labels_human/<stem>.txt` означает, что снимок проверен

Загруженные снимки автокропаются (`report_crop.py`) — исходники клиники приходят
как отчётные распечатки Dentium с шапкой и подвалом; тот же модуль использует
`preannotate_clinic.py`. Справочник классов — `annotation_classes.py`
(сервер его импортирует; импорт самого сервера грузит веса моделей).

### Обрезка отчётов РЕЗАЛА ПО КОРНЯМ НИЖНИХ ЗУБОВ (исправлено 17.09)

Прежнее правило искало «чёрные линии рамки» — строки, тёмные на 80% ширины,
и брало первую ниже 65% высоты. Такие строки есть и внутри самой панорамы.
Итог: на 12 отчётах из 13 от снимка (строки 355-2272) оставалось около 1400
строк, нижняя челюсть с корнями в кадр не попадала. **Врач размечал
снимки без нижних апексов** — очаг у нижнего зуба увидеть было нельзя.
Панораму из карточки (не отчёт) правило тоже резало: минус 280 строк сверху.

Обнаружено только при экспорте, когда я нарисовал рамки на снимке. Ни
счётчики, ни предпросмотр в редакторе этого не показывали: обрезанная
панорама выглядит как панорама.

Теперь снимок — самая длинная полоса строк (и столбцов), где белого фона
отчёта меньше 30%. Режется, только если полоса короче 90% кадра, поэтому
DENTEX и панорамы из карточек не трогаются, а правило идемпотентно.
Проверено на всех 13 отчётах: у 12 рамка (35, 355, 3265, 2272), у детского
снимка панорама меньше и с полями — (35, 519, 3265, 2108).

- **Перенос уже размеченного:** рамки врача пересчитаны через координаты
  оригинала; ИИ-разметка пересчитана заново. Старые кадры и рамки лежат в
  `dentium-2026-08-12/images_before_recrop/`.
- **Снимок режется только при ПЕРВОМ анализе** (признак — нет `labels/`).
  Старое правило не было идемпотентным: повторная преразметка 17.09 срезала
  у Report_20260812_184613 ещё треть высоты.
- **Проверенные до перерезки снимки помечены `recheck` и `visible_y`**
  (полоса, которую врач видел: верхние 70-73%). В редакторе у них метка
  «Перепроверить»; сохранение её снимает. Экспорт у зуба, который врач видел
  не целиком, «нет находки» считает «неизвестно».

### Ежедневная разметка врачами (с 17.09)

Каждый врач заводит СВОЙ набор (`POST /api/datasets`, пустой) и каждый день
добавляет в него панорамы (`POST /api/datasets/{slug}/images`). Норма —
`DAILY_GOAL = 2` проверенных снимка в день; счётчик виден на карточке набора
и в редакторе.

- **Имя файла — время добавления и начало md5** (`20260917-191116-72327b.png`),
  исходное имя и время — в реестре `images.json`. Имя пациента из имени
  файла в набор не попадает, а список сортируется по времени.
- **Дубли отсекаются по ВСЕМ наборам** (`annotation_feed.known_hashes`:
  `images.json`, `feed.json` и оригиналы ручной пачки). Один снимок у двух
  врачей — двойная работа и утечка между обучением и проверкой.
- **Норма считается по `first_reviewed_at`**, а не по последнему сохранению:
  пересохранение вчерашнего снимка сегодняшнюю норму не закрывает.
- **Удаление — в корзину**: снимок с разметкой в `<набор>/trash/`, набор
  целиком в `annotation_trash/`. При ежедневной работе случайный клик по 🗑
  иначе стёр бы недели разметки.

### Порог кариеса у ансамбля — 0.40 (17.09)

Врачи: «показывает ненужное». `annotation_classes.ENSEMBLE_MIN_CONF` — ниже

### Экспорт разметки в обучение (`export_annotations.py`)

`labels_human` -> вырезы зубов в формате `tooth_crops2`
(`research/datasets/clinic_tooth_crops/`: `labels.json`, `train/`, `val/`,
`report.json` с замечаниями для врачей). Учить вместе с DENTEX:

```
train_tooth_cls.py --data tooth_crops2 clinic_tooth_crops --out research/output/tooth_cls_clinic
```

`--out` обязателен для проб: по умолчанию пишутся веса, которые читает демо.
Метрики печатаются и по всем наборам, и ПОРОЗНЬ — вопрос в переносе на
аппарат клиники, а не в среднем.

- **Вырез и номер — от детектора зубов**, как на приёме; рамка врача только
  говорит, к какому зубу метка. «Весь зуб» — по IoU 0.5; маленькая рамка
  внутри зуба засчитывается с замечанием («обведён очаг»); пломба, фрагмент,
  имплант — к зубу, где лежит большая часть объекта; коронка или мост — ко
  всем зубам, которые перекрывает по ширине (`box` в справочнике). Зуб,
  которого детектор не нашёл, — вырез по рамке врача с номером 0.
- **Зуб без отметок = здоровый, но только по классам, которые врач видел.**
  Сервер пишет `reviewed_classes` в сайдкар; у проверок до 17.09 его нет —
  считаются по четырём классам. Непроверенный класс — `null`, обучение такой
  вырез для этой головы пропускает.
- **Разбиение — по пациенту (снимки из карточек) или по имени снимка,
  хэшем ключа.** Сначала ключом был хэш содержимого — после перерезки он
  сменился, и один из трёх проверенных снимков молча переехал из проверки в
  обучение.
- Рамки на перерезанных снимках сравниваются с ВИДИМОЙ частью зуба: врач
  рисовал их по обрезанному кадру, и без этого нижние зубы получали второй
  вырез.
- Совместимые поля `caries` (0-2, пульпа считается глубоким) и `apical`;
  полная шкала — `caries_level` (3 = до пульпы) и `bone_loss` (0-3).

Пробный прогон на 3 проверенных снимках: 90 вырезов, из них 37 без меток
кариеса (зубы, видимые врачом не целиком). По 15 новым классам данных пока
нет ни одного снимка.

## Проверка находок на МАСШТАБЕ (`cbct_validate_findings.py`)

Пороги слоя находок калибровались на четырёх клинических кейсах с одного
аппарата. Этого мало, и это уже подтвердилось: на треке сканов такая же
проверка, но на 180 пациентах, перевернула выводы (см. `ios_frame_validate`).
Скрипт гоняет измерения на ЭТАЛОННЫХ масках ToothFairy3 (532 тома с
разметкой) — это отделяет ошибку ИЗМЕРЕНИЯ от ошибки сегментации.

**Первая же проверка нашла системную ошибку, а не съехавший порог.**
`tooth_axis` вшито предполагала, что ось срезов растёт вверх. Наши кейсы лежат
именно так, ToothFairy — наоборот. Ось зуба смотрела от коронки к апексу,
перепад плотности эмаль-дентин выходил ОТРИЦАТЕЛЬНЫМ (−586 вместо +772), и
уровень кости не измерялся вообще:

```
                     до         после
ToothFairy #1     0 из 22     15 из 22
ToothFairy #2     0 из 22     21 из 22
client4 (наш)    18 из 28     18 из 28   (не изменился)
```

Направление теперь берётся из данных — `cb.occlusal_up`, ОДИН детектор на все
модули (был в `cbct_findings`, перенесён в backend; `cbct_findings.occlusal_up`
делегирует туда же). `tooth_axis(idx, spacing, upper, z_up)` — параметр
обязателен по смыслу, значение по умолчанию оставлено только для старых
вызовов.

Мораль, уже вторая такая в проекте: **прежде чем править пороги, проверить
систему координат, в которой живёт измерение.** Первый раз это была вертикаль
дуги на сканах (AUC глубокого прикуса 0.573 -> 0.971), теперь ось зуба на КЛКТ.

Клинической правды в ToothFairy нет («у этого зуба пломба», «здесь убыль
4 мм»), поэтому проверяется то, что проверяется без разметки: двугорбость
распределения у эндодонтии (есть ли ВПАДИНА вокруг порога на сотнях
пациентов, или наш «зазор 342 HU» был удачей четырёх кейсов) и доля
измеряемых зубов с частотой находок у пародонта (если убыль находится у
каждого второго зуба у каждого пациента — это ложная тревога, врач
перестанет читать раздел).

## Уровень костной ткани (пародонт)

`cbct_perio.py` — расстояние от шейки зуба до гребня альвеолярной кости,
ОТДЕЛЬНО с мезиальной и дистальной стороны. Подключено к `cbct_findings`.

Задача числилась заблокированной («нужна разметка рентгенолога, публичной
нет»). **Она не была заблокирована.** У Diagnocat это ИЗМЕРЕНИЕ, а не
классификация: на панораме у каждого межзубного промежутка стоит своё число в
миллиметрах. Обе опорные точки читаются по маскам, которые у нас уже есть.

- **Шейка** — точка наибольшего спада плотности по ВНЕШНЕМУ слою зуба: эмаль
  плотнее дентина (перепад на client4 около 840 HU). Внешний слой, а не всё
  сечение: пломбировочный материал в канале плотнее эмали и забивает сигнал —
  на зубах 21 и 47 детектор из-за этого уезжал к апексу. И точка наибольшего
  спада, а не первое пересечение середины: профиль не монотонен (зуб 13
  давал 0.00).
- **Гребень** — 95-й перцентиль уровня кости в секторе ±50° вокруг нужного
  направления. Перцентиль, а не максимум: одинокий воксель задирал результат.
- **Ось у каждого зуба своя** (главная ось его же вокселей), а не общая
  вертикаль: у наклонённого моляра измерение вдоль общей оси завышает высоту.
- **Отдаём и миллиметры, и долю длины корня** — вторым стадируют пародонтит
  по классификации 2017 года, и это устойчивее к разнице размеров зубов.

**Гоча: ноль маскирует сбой.** Сначала результат ограничивался снизу нулём, и
там, где гребень выходил выше шейки (анатомически невозможно), врач видел бы
«0.0 мм, норма» вместо «не измерено». Теперь такой зуб уходит в непроверенные.
Проверка на client4: зубы 28 и 42 именно так и переехали.

**Чего метод не может:** под металлической коронкой шейку не найти — эмали не
видно. На client4 не измерено 12 зубов из 28, почти все с реставрациями. Это
честный отказ, а не недоработка: человек под коронкой её тоже не увидит.

### Пороги из литературы ОКАЗАЛИСЬ НЕПРИМЕНИМЫ — исправлено

Проверка на 60 пациентах ToothFairy по эталонным маскам (2528 участков):

```
перцентиль   5%   25%   50%   75%   85%   90%   95%   99%
мм          1.9   3.0   3.9   5.0   5.8   6.5   7.3   9.0
```

Литературный порог нормы 2 мм превышают **93% участков**, и медиана убыли
выходила 44 участка на пациента при 46 возможных — то есть тревога почти на
каждом. Это не значит, что больны 93% людей: **у нашего измерения база
3.9 мм**. Шейка у нас — точка наибольшего спада плотности по внешнему слою,
гребень — 95-й перцентиль уровня кости в секторе; обе точки геометрические, и
между ними систематически примерно на 1.9 мм больше, чем между клиническими.

Третий случай подряд с той же природой: класс по Энглю (норма −1.95 мм),
индекс Литтла (1.2 мм на пару), теперь пародонт (3.9 мм). Правило:
**прежде чем брать порог из литературы, замерь базу собственного измерения
на выборке.**

Теперь отдаём миллиметры И ПЕРЦЕНТИЛЬ в референсной выборке, а степень
называем от выборки («выше нормы», «резко выше нормы»), а НЕ клинически.
«Выше 97% участков выборки» — проверяемое утверждение о нашем измерении;
«8 мм = тяжёлый пародонтит» — утверждение о болезни, и прав на него нет:
разметки пародонтолога нет, а сама выборка ToothFairy состоит из пациентов
КЛКТ и потому не здорова. Границы категорий — 85 / 95 / 99-й перцентиль,
специфичность выбрана как на прикусе.

Результат на client4: вместо тревоги по 19 зубам осталась ОДНА — зуб 13
(8.0 мм, выше 97% участков). Остальное было базой метода.

## Корни и каналы: ЗАКРЫТО отрицательно (маска, не снимок)

Подсчёт числа корней и каналов по маске **не работает и порогами не чинится**.
Замер на client4 (счёт связных кусков в слоях 1 мм поперёк собственной оси зуба,
сверка с учебной анатомией):

- у 26 три корня нашлись, у 27 и 46 — нет;
- у ОДНОКОРНЕВЫХ 11, 12, 31, 41 вылезло по два корня (клинически абсурдно).

Две поломки бьют навстречу друг другу, поэтому один порог их не разводит:
у шейки маска корни **сливает** (разделение проступает только в апикальной
трети, настоящая фуркация выше), у апекса — **крошится** на осколки.

**Вина маски, а не снимка** — это проверено, и это меняет вывод. У зуба 27
маска на тех же уровнях даёт 1–2 куска, а сама ПЛОТНОСТЬ (порог посередине
между HU корня и HU окружающей кости) — 3 и больше. То есть корни на КЛКТ
разделены, их сращивает наша сегментация. Значит задача вернётся с лучшей
моделью зубов, а не упирается в железо. Считать корни прямо по плотности тоже
нельзя: она даёт 5–7 кусков там, где корней 3 — шум губчатой кости.

**Каналы не читаются вовсе:** тонкий канал не набирает и десятка вокселей на
слой, у здоровых зубов пульпа видна только в коронковой камере. Число каналов
из этой маски не извлекается ни при каком пороге.

**Побочно найден дефект сегментации:** у зубов 17 и 46 маска — огрызок, длина
корня 3.6 и 2.7 мм вместо ~14. Это не про фуркацию: зубы почти не
сегментированы, и любые измерения по ним недостоверны.

Эндодонтический статус (пролечен канал / выведение за апекс) на этом НЕ
закрыт: он держится на плотности пломбировочного материала, а не на топологии
маски — см. `cbct_endo.py`.

## Дентикли (камни пульпы): ЗАКРЫТО отрицательно (разметка, не модель)

Обызвествления внутри пульпы. Отказ жёстче, чем у корней: там разделение
видно в плотности и вернётся с лучшей моделью, здесь **не поможет никакая
модель, обученная на ToothFairy** — класс так не размечен.

Проверено в три захода:

1. Плотное ВНУТРИ маски пульпы: 0 находок на 40 витальных зубах при
   ожидаемых по литературе 20-30%. Слишком чисто для везения.
2. Дентикль по составу — тот же дентин, поэтому сеть метит его дентином, а
   пульпа должна обнимать его кольцом. Ищем полости: `binary_fill_holes(пульпа)`
   минус пульпа. Результат — **0 полостей на 45 зубах**, ни одной даже в
   5 вокселей.
3. Решающая проверка — ЭТАЛОННАЯ разметка: **0 полостей на 257 пульп**
   (10 кейсов ToothFairy3). Пульпа размечена сплошным телом, обызвествление
   внутри него разметкой не предусмотрено.

Вернуться можно только с другой разметкой (отдельный класс «дентикль» либо
детекция по плотности внутри камеры на размеченных врачом кейсах). До тех пор
пункт закрыт: выдавать «дентиклей не найдено» врачу нельзя — это будет
неправдой, мы их не ищем, а не не находим.

## Корневые каналы недорисованы: меш стирал, модель недометила (17.09)

Врач: «у зубов с 3-4 каналами они не дорисованы — где один, где ни одного».
Замер на client5/sp (премоляры и моляры, число каналов в срезах на 55/66/77%
длины зуба) нашёл ДВЕ причины, и одна из них — наш код.

**1. Меш стирал тонкие каналы.** Размытие маски перед marching cubes
(sigma 0.9) не оставляет каналу в 1-2 вокселя шанса дотянуть до изоуровня:

```
сырая маска модели           85 участков каналов
меш как был                  58   — треть каналов терялась в меше
меш с сохранением тонкого    86
```

Страховка в `_class_mesh` (снижение sigma) смотрит на максимум ВСЕЙ
пульпы, а камера толстая и переживает размытие — поэтому не срабатывала.
Теперь у пульпы (`THIN_GROUPS`) то, что размытие съело бы и что не
прилегает к выжившему телу, размывается мягче (`THIN_SIGMA = 0.45`); форма
камеры прежняя. Упрощение меша (750 граней на пульпу) каналы не схлопывало
(потеря площади в апикальной части до 4%), но лимит поднят до 40 000.

**2. Модель недометила каналы, а на снимке они есть.** Пульпа `sp` доходит
до 72-91% длины зуба, при этом на срезах вдоль зуба тёмные линии каналов
видны до верхушки. `cbct_canals.py` дотрассировывает их по плотности:
от конца каждого обрывка пульпы (и от развилки — для корня без канала)
срез за срезом по самой тёмной точке, затем дорастание вокруг трасс.

- **Порог остановки — в единицах ШУМА дентина этого зуба**, а не в HU и
  не в долях плотности: шум у аппаратов разный (ToothFairy3 108, client5
  139), и абсолютный порог на клинике обрывал канал сразу под маской.
  Контраст к кольцу дентина: у эталонного канала медиана 2.5 шума, у
  дентина без канала 90-й перцентиль 0.9.
- **Затравка в каждом корне.** Каналы соседних корней сходятся выше
  развилки, обрывок пульпы — одна компонента, и одна затравка уводила
  трассу только в один корень.
- **Тело зуба замыкается** (`canal_body`): недорисованный канал модель
  метит фоном, и без этого вдоль канала в зубе была бы дыра.
- **Порог в одиночку не годится:** на эталоне хорош, на клинике канал
  бледнее — либо рвётся, либо (при низком пороге) разрастается в шум: у 16
  выходило пять «каналов» в одном срезе.

Проверка на ToothFairy3 (80 зубов, эталонная пульпа обрезана на половине
длины; `cbct_canals.py --validate 10`): покрытие отрезанного канала 0.85
(медиана 1.00), точность прироста 0.86, ошибка дохода 0.075 длины зуба,
число каналов в срезе совпадает с эталоном в 73%; пульпа, обрезанная у
самой камеры, дотягивается до эталона в 31 из 37; разрыв на 45-70% длины
закрывается целиком у 49 из 79.

**Что пришлось доделать, глядя на 3D, а не на числа** (каждое было видно
только на отрисовке меша, метрики его не ловили):
- трасса рассыпалась «бусинами» — соседние точки соединяются отрезком,
  трубка утолщается кубом 3x3x3 (крест у диагональной линии давал
  переменную толщину);
- рост по порогу давал поперечные шипики — раскрывается только приросшее,
  трубка трассы остаётся целой;
- канал отрывался от камеры в меше — у тонкого в `_keep_thin_parts`
  возвращается скелет маски, размытия складываются;
- на концах каналов были плоские «ножки» — утолщаются только внутренние
  точки линии, концы остаются тонкими;
- модель метит канал кусками — куски в одном корне соединяются мостом
  (`_bridges`).
На client5 каналы удлиняются у 12 зубов из 18 (26: 0.82 -> 0.93, 37: 0.85
-> 0.94, 17: 0.83 -> 0.93); пульпа +24%, обработка маски +13 с. Трассы
соединяются отрезками и утолщаются на воксель — иначе в 3D канал
рассыпался на «бусины»; оторванные крошки меньше 30 вокселей убираются.

**Где предел — в КАНАЛЕ, а не в корне (проверено 19.09).** Сначала я
записал сюда «модель обрезала сам корень»: продолжение плотной ткани за
концом маски вдоль оси зуба давало 3.5-4 мм. Замер оказался негодным — у
верхушки вплотную лежит плотная кость, и порог по плотности утекает в неё.
На ЭТАЛОНЕ DentVoxel (178 зубов, 6 томов, модель их не видела) корень
кончается там же, где у разметчика: медиана расхождения у верхушки
-0.13 мм, 90-й перцентиль 0.26 мм, короче эталона больше чем на 1 мм всего
1% зубов при Dice 0.941.

Не доходит до верхушки САМ КАНАЛ, и это наследство обучающих данных: у
ToothFairy3 пульпа доходит до 85% длины зуба лишь у 46% зубов (медиана
0.84, до 90% — у 18%). Модель повторяет учителя. Значит следующий шаг —
отдельная модель канала на вырезе зуба, обученная там, где канал размечен
до конца: Pulpy3D (96 томов, классы пульпа и нерв) размечает канал полнее
ToothFairy3 — медиана длины компоненты 43 вокселя против 37, длиннее 12 мм
59% против 39%, и сами каналы тоньше (14 вокселей в срезе против 18).

Сглаживание вдоль оси зуба для усиления сигнала проверено и не помогло.

`POSTPROC_VERSION` 20, `FINDINGS_VERSION` 14; пересборка — `cbct_rebuild.py`.

### Модель канала на вырезе зуба: ПОДСКАЗКА НЕ ДОЛЖНА СОДЕРЖАТЬ ОТВЕТ

`cbct_canal_crops.py` нарезает зубы вдоль собственной оси в сетку 128x64x64
(масштаб перестаёт зависеть от вокселя аппарата), `train_canal_net.py` учит на
них 3D U-Net. Отбор в набор — только зубы, где канал размечен до верхушки
(`MIN_REACH = 0.85`): 4069 зубов из 8381 у ToothFairy3 и 822 из 1186 у
Pulpy3D, итого 4891 вырез (4243 обучение / 648 проверка, разбиение по ТОМУ).

**Гоча, стоившая обучения: вторым каналом нельзя подавать маску зуба.**
Она и в эталоне, и у нашей модели пульпу НЕ включает — на её месте дырка, то
есть готовый ответ. Сеть на второй эпохе дала **Dice 0.996**, просто обводя
дырку во входе. Подозрительно высокое число и было единственным признаком:
потеря падала как надо, картинки выглядели правильно.

Подаём ТЕЛО зуба — зуб вместе с пульпой, замкнутый, с заполненными полостями
(`body_of`, то же строит `cbct_backend.canal_body` на приёме). Что тело само
подсказки не несёт — **замерено, а не предположено**: кончик тела отстоит от
конца канала на 10 уровней сетки из 128 (квартили 7..13), в точности
совпадает у 0.4% вырезов, а на уровне конца канала тело шире канала в 100 раз
(220 вокселей против 2). Обводить нечего.

**Отбор по доходу канала в одиночку тоже негоден.** Dice определяется
камерой (60-80% объёма пульпы), поэтому отбирать по нему нельзя — но на
первой же эпохе доход вышел 0.96 против 0.91 у эталона при Dice 0.589:
рыхлое предсказание тянется ДАЛЬШЕ канала и получает хорошую ошибку дохода.
Отбор идёт по сумме `ошибка дохода + (1 - Dice) / 4` — делитель ставит вклад
формы в один масштаб с доходом. Метрики считаются ещё и по источникам
отдельно: Pulpy3D — другой аппарат, другая популяция и зубы от нашей модели,
а не из эталона.

Итог обучения (120 эпох, ~95 с на эпоху, лучшая 99-я): Dice 0.922, ошибка
дохода 0.009, недотянуто больше чем на 0.1 у 3% зубов, перетянуто у 0%.
По источникам: ToothFairy3 Dice 0.927 (недотянуто у 0.4%), Pulpy3D 0.861
(недотянуто у 16%) — на чужом аппарате слабее, и это видно и на клинике.
Порог отсечки роли не играет: от 0.2 до 0.5 Dice 0.916-0.924 при одной и
той же ошибке дохода, то есть сеть уверенная, а не балансирует у границы.

### Модель канала ЛУЧШЕ трассировки по плотности — сверено одним протоколом

`cbct_canals.py --validate 8 --net research/output/canal_net/best.pt`:
эталонная пульпа обрезается на половине длины зуба и дорисовывается, 95
премоляров и моляров, тома ТОЛЬКО из проверочной доли нарезки (иначе сеть
мерила бы себя на своём же учителе).

```
                                  трассировка   сеть   союз
ошибка дохода                        0.089     0.017   0.027
число каналов в срезе совпало         0.71      0.91    0.87
лишних каналов                          40        11      22
покрытие отрезанного канала           0.84      0.99    1.00
точность прироста                     0.86      0.99    0.89
корень без канала дотянут (из 48)       45        48      48
разрыв в середине закрыт (из 94)        57        94      94
```

**Союз двух способов не берём:** он ничего не добавляет к сети, зато роняет
точность прироста до 0.89 и даёт вдвое больше лишних каналов.

**На клинике перевеса нет, и это надо говорить прямо.** client5: медиана
дохода 0.82 у модели, 0.86 у сети, 0.86 у трассировки; client4 — 0.86 /
0.89 / 0.90. Сеть выигрывает на однокорневых (41: 0.69 -> 0.91, 32: 0.68 ->
0.89) и там, где трассировка отказывает вовсе, трассировка — на молярах
(17, 26, 37, 47). Но её «лишняя глубина» частью ложная: на эталоне у неё 40
лишних каналов против 11. Тот же разрыв «эталон против нашего аппарата»
виден и в метриках по источникам, так что это свойство данных, а не случай.
Показательный случай на client2: у зуба 37 каналов в срезе было `[0,0,0,0]`
и у модели, и у трассировки, а сеть дала `[1,1,1,1]` — ровно то, на что
жаловался врач («где один, где ни одного»).

В конвейере (`cbct_backend.canal_net`) канал рисует СЕТЬ; трассировка
остаётся запасным путём, если весов нет. `POSTPROC_VERSION` 21,
`FINDINGS_VERSION` 15.

**Гипотеза, которую замер ОТМЕНИЛ:** «на молярах хуже, потому что их мало в
обучении» — неверно, взято 53% моляров ToothFairy3 (1543 зуба) против 49%
резцов. Состав набора ни при чём.

## Разметка каналов на КЛКТ: свой эталон на своём аппарате

`cbct_canal_prepare.py` (подготовка) + `canal_annotate_server.py` (:7863,
фронт `canal_static/`) — врач размечает каналы на КЛКТ клиники.

**Зачем.** Модель канала повторяет разметчика на эталонных данных (ошибка
дохода 0.017), но на нашем Dentium прибавка частичная: 0.82 -> 0.86 при
«полном» уровне около 0.91. И проверить это нечем: разметки каналов,
сделанной на нашем аппарате, не существует НИ ОДНОЙ. Отсюда и эталон, и
дообучение — из одного набора. Тот же вывод, что по пазухам: **нужна своя
разметка, а не другой алгоритм.**

**Врач размечает В ТОЙ ЖЕ сетке, в которой работает модель** — выпрямленный
вырез 128x64x64 (`cbct_canal_crops.grid_of`), а не сырой том. Иначе разметка и
обучение живут в разных системах координат — в проекте это уже пять раз
стоило отдельного круга.

**Точки хранятся в вокселях ТОМА, а не выреза.** Вырез строится по маске зуба
ТЕКУЩЕЙ модели; станет сегментация лучше — рамка сдвинется, и разметка тихо
уедет вместе с ней. Сервер переводит каждую точку через `frame` (центр, оси,
шаг) в воксели исходного тома и хранит оба представления. Разметка стоит
дороже любой модели и обязана пережить смену модели.

**Черновик от модели обязателен.** Зуб с нуля — две-три минуты, зуб с
предзаполненной линией — 10-20 секунд. При цели в сотни зубов это разница
между «сделаем» и «не сделаем».

**Очередь по РАСХОЖДЕНИЮ сети и трассировки, но каждый пятый зуб —
случайный.** Там, где оба способа согласны, разметка почти ничего не
добавляет. Но набор только из трудных случаев занизил бы измеренное качество,
и честного числа мы бы не получили. Гоча первой версии: случайный зуб
ЗАМЕНЯЛ спорный, и каждый пятый выпадал из очереди совсем.

**Каждый десятый зуб размечают двое.** Без расхождения между врачами нельзя
сказать, ошибается ли модель меньше, чем расходятся люди.

**Правила, без которых набор испортится** (они же в `/guide.html` у врача):
конец канала — последняя ВИДИМАЯ точка, а не анатомический апекс; не
читается — так и отмечать, а не ставить наугад; запломбированный канал
(яркий, не тёмный) — отдельной галочкой; зуб, разобранный не целиком,
помечается неполным — иначе пропущенный канал уйдёт в обучение как «канала
здесь нет», и мы выучим ровно ту болезнь, которую лечим.

**Гоча, найденная ГЛАЗАМИ на первой же отрисовке:** окно плотности по всему
зубу оставляет в корне ровное серое поле — канала не видно. В корне разброс
плотности мал, а шкалу тянут эмаль и коронка. Окно считается НА КАЖДЫЙ СРЕЗ
(перцентили 3/97 внутри тела зуба, сглаженные по соседним уровням, иначе
картинка мигает при прокрутке). Это третий случай в проекте, когда виновато
окно, а не данные.

**Увеличение следует за каналом** (24 вокселя вокруг активной точки, около
2.5 мм). Габарит всего зуба для этого не годится: коронка широкая, и рамка
выходит почти во весь кадр — увеличения не получается.

**ПОЛОВИНА НАШИХ «КЛИНИЧЕСКИХ» КЛКТ ОКАЗАЛАСЬ ДУБЛЯМИ.** Отпечаток тома
(md5 по каждому четвёртому вокселю) показал: из восьми кейсов с аппаратов
клиники разных пациентов всего ЧЕТЫРЕ — `client2` = `case_1788704679`, а
`client5` лежит в четырёх копиях (снимок загружали в демо повторно). Заметно
это стало случайно: у двух кейсов совпали числа расхождения на одноимённых
зубах. Без отсева врач размечал бы один и тот же зуб по четыре раза, а при
обучении один пациент попал бы и в обучение, и в проверку.

`unique_cases` оставляет по одному кейсу на том (именованный предпочтительнее
безымянного `case_<время>`) и удаляет подготовленные зубы дубля. Зубов в
очереди стало 109 вместо 219. **Правило то же, что в подаче панорам: дубли
ловятся по СОДЕРЖИМОМУ, имя кейса ничего не гарантирует.**

### Пакетный ввоз КЛКТ с флешки (`cbct_batch_import.py`)

Снимки приходят пачками по 40-50, и через демо их не залить: у бесплатного
Cloudflare тело запроса ограничено 100 МБ, а КЛКТ весит 300-600. Пачка
ввозится локально — ввоз, сегментация и нарезка зубов идут одной ночью,
около 5 минут на снимок.

- **Меши и находки НЕ строятся.** Для разметки нужны только том и маска
  зубов; меш плюс находки добавляют ещё 7 минут на снимок и никому не нужны,
  пока врач не открыл кейс в демо — оно построит их само.
- **Серии ищутся через GDCM, а не по маске `*.dcm`.** Экспорты аппарата
  кладут файлы без расширения (`IM000001`), в одной папке бывает несколько
  серий, включая обзорные и отчётные картинки. Объёмные отбираются по числу
  срезов и шагу вокселя, остальное уходит в лог с причиной.
- **Дубли — по СОДЕРЖИМОМУ тома** (md5 по каждому четвёртому вокселю), а не
  по имени папки. Проверено на своих данных: из восьми «клинических» кейсов
  разных пациентов оказалось четыре, а в наборе пар figshare два тома
  (pair017 и pair018) тоже совпали байт в байт. Отпечатки кэшируются в
  `research_3d/volume_hashes.json`, иначе каждый прогон перечитывал бы все
  тома по 300 МБ.
- **ФИО и дата рождения в кейс не попадают.** Соответствие «кейс -> пациент»
  пишется отдельно в `research_3d/patient_map.json` (в `.gitignore`): клинике
  надо уметь найти пациента, но эти данные не должны ездить вместе с набором
  для разметки. То же правило, что в подаче панорам.
- **Снимок с аппарата без подтверждённой конвенции сторон ввозится, но в
  разметку не идёт** и перечисляется отдельным списком: номера зубов на нём
  могут быть зеркальны, и врач разметит канал «зуба 16», который на самом
  деле 26.

Проверено сквозным прогоном на собранной из тома DICOM-серии (335 срезов):
серия найдена, кейс заведён, ФИО ушли в отдельную таблицу, повторный прогон
опознал дубль.

## Эндодонтический статус (`cbct_endo.py`)

Пролечен канал или зуб витален. Задача решена там, где подсчёт каналов провалился,
потому что это вопрос ПЛОТНОСТИ, а не топологии маски.

**Главное: сравнивать зуб САМ С СОБОЙ.** Абсолютный порог здесь обречён дважды.
Шкала КЛКТ не количественная — на client4 воздух даёт −1035 (правдоподобно), но
дентин читается 1400–3200 при настоящих 1200–1800, а эмаль 3043. И эмаль сама
плотнее любого разумного порога, поэтому «плотное внутри зуба» есть у КАЖДОГО
зуба: у заведомо живого 11 в корне 3485 вокселей выше 2200 HU. Меряем разницу
медиан «пульпа минус дентин того же зуба» — некалиброванность при вычитании
сокращается.

Замер на client2 + client4 + client5, 51 зуб с читаемой пульпой:

```
живые (45):  медиана -1073, самый высокий  +24
пломбы (6):  медиана +1591, самая низкая  +366
ЗАЗОР между группами 342 HU, перекрытия нет ни одного зуба
```

Порог `FILLED_DIFF_HU = 300` стоит в пустом зазоре — подбирать не пришлось,
любое значение внутри 100..350 даёт тот же результат. Проверено глазами
(`cbct_endo_check.png`): у пролеченного канал светится ярким тяжом, у живого
контроля тот же тяж тёмный. client5 — чистый контроль, 19 зубов, ноль пломб.

**Гоча: близость металла гасит только СЛАБУЮ разницу.** Первая версия правила
гасила любую — и на client2 погасила все пять пломб, включая зуб 44 с разницей
+2028, видимый глазом, потому что там металл лежит в 0.3 мм почти от каждого
зуба. Контроль на том же кейсе: зубы на тех же 0.3 мм, но живые, читаются −630,
−1154, −427. Значит соседство с металлом само по себе плотность внутри канала
не задирает, и гасить им сильный сигнал нельзя.

**Качество пломбирования НЕ оценивается — это проверено, а не пропущено.**
«Пломба не доходит до апекса» померить не удалось: зазор до апекса ОДИНАКОВ у
пролеченных и у живых (2.7 против 2.4 мм на client2, 2.0 против 2.7 на client4).
То есть это не недопломбировка, а маска пульпы не тянет тонкий апикальный канал —
то же ограничение, что закрыло подсчёт каналов. Числа считаются и лежат в
`fill_gap_mm` / `pulp_gap_mm`, но находкой не становятся.

**Отсутствие маски пульпы ≠ «зуб депульпирован».** Уходит в ручную проверку с
явной оговоркой: чаще это провал сегментации (на client4 у 17, 46, 48 маска
зуба — огрызок с корнем 2.7–3.6 мм).

В план идёт ОЦЕНОЧНОЙ позицией («Оценка ранее пролеченных каналов»), а не
показанием к перелечиванию: периапикальные очаги мы на КЛКТ не детектируем,
поэтому назвать перелечивание нечем.

## Пазухи в ToothFairy3 размечены на десятую часть — обучением не лечится

Замер по 60 томам (объём пазухи в эталоне против анатомической нормы ~500 000
вокселей при вокселе 0.3 мм):

```
структура        размечена в     медиана объёма    доля от нормы
левая пазуха     42 из 60          49 304            10%
правая пазуха    40 из 60          54 957            11%
глотка           60 из 60         780 224           целиком
```

Следствие видно прямо в обучении: при старте с нуля пазухи **не оживают
вовсе** — 0.000 на протяжении 200 эпох, тогда как зубы дошли до 0.84, пульпа
до 0.87, а глотка до 0.97. Сеть не может выучить структуру, от которой в
эталоне остались обрывки.

Поэтому пазухи в сводной модели берутся у `pretrained` (ToothFairy2). Это
дополняет уже известное «пазухи у ToothFairy3 слабые» конкретным числом.

**ПОПРАВКА, замерено позже:** «у ToothFairy2 размечены нормально» — неверно.
На client5 `pretrained` даёт 0.2 и 1.2 см³ при норме ~15, то есть не лучше
остальных. Пазуха размечена только по дну у ВСЕХ моделей — см. отдельный
раздел ниже. Донором она остаётся за неимением лучшего, а не потому, что
хороша.

**Общий счёт по неполноте ToothFairy3: зубы (22 из 32 на том), пульпа верхней
челюсти (65%), пазухи (10% объёма).** Три структуры из трёх проверенных.

## У ToothFairy3 НЕПОЛНАЯ разметка — мы принимали её за эталон

Замер по всем томам обоих датасетов (полный список зубов в маске, класс 11-48):

```
                      ToothFairy3 (532)   DentVoxel (100)
зубов на том, медиана        22                30
квартили                   14-27             28-32
томов с 28+ зубами        112 (21%)         77 (77%)
минимум                       0                18
```

**Разницей поля зрения это не объясняется:** высота тома у ToothFairy3
стабильная — медиана 169 срезов, квартили 168-170, протокол почти одинаковый.
Зубы в кадр попадают, а в разметку не попадают.

Вместе с уже замеренной недоразметкой пульпы верхней челюсти (65.2% против
98.7% на нижней) вывод один: **разметка ToothFairy3 неполная, и наши модели
теряли зубы в том числе потому, что учились на ней.** Сеть не может выучить
то, чего нет в эталоне.

Это объясняет и наблюдение, с которого всё началось: `tf3` теряла целые
квадранты, а `pretrained` (обученная на ToothFairy2, где пульпы нет вовсе, но
зубы размечены полнее) находила их.

**DentVoxel** (`research_3d/datasets/dentvoxel`, 100 томов, воксель 0.3 мм,
38 классов, **CC BY 4.0**) размечен существенно полнее и снимает заодно
некоммерческое ограничение ToothFairy3. Пульпы в нём нет — её придётся брать
из другого источника либо принимать разметку ToothFairy3 только там, где она
есть.

## В служебных файлах nnU-Net — ТОЛЬКО латиница

`dataset.json` nnU-Net читает без указания кодировки, и на Windows это cp1252.
Русское описание в поле `description` роняет весь препроцессинг ещё до старта:

```
UnicodeDecodeError: 'charmap' codec can't decode byte 0x81
  ... verify_dataset_integrity -> load_json
```

Симптом обманчив: падает `verify_dataset_integrity`, и кажется, что беда с
самими данными, а дело в одной строке описания. `cbct_prepare_singlepulp.py`
теперь пишет `dataset.json` с `ensure_ascii=True`.

Это тот же класс граблей, что и `PYTHONIOENCODING=utf-8` при запуске наших
скриптов: консоль и служебные файлы на этой машине живут в cp1252, а проект —
в UTF-8.

## Модель `sp`: результат на чужих данных

Обучена 30.08 на `Dataset114` (пульпа одним классом, зеркалирование лево-право
выключено, 829 эпох). Независимая проверка на DentVoxel — 15 томов, 439 зубов,
модель этих данных не видела:

```
                 15 томов (439 зубов)   25 томов (724 зуба)
полнота               100.0%                 100.0%
точность               97.1%                  96.5%
Dice зубов        медиана 0.940          медиана 0.939
по челюстям        100% / 100%            100% / 100%
```

Второй столбец — повторная проверка на выборке в 1.6 раза больше и уже после
того, как в конвейер добавились `orient_sides` и отсев артефактов: числа не
поплыли. Перекоса между челюстями нет ни на одной выборке.

На client5 — кейсе, с которого началась история про пропавший квадрант:

```
модель        зубов   пульп
tf3 (была)      23      19
pretrained      30       0
sp (новая)      31      30
```

**Прямое сравнение с `pretrained` на ОДНОЙ И ТОЙ ЖЕ внешней выборке**
(DentVoxel, 25 томов, 724 зуба, ни одна из моделей этих данных не видела):

```
                    sp        pretrained
полнота           100.0%         96.0%
точность           96.5%         96.3%
Dice медиана       0.939         0.812
Dice среднее       0.914         0.712
```

Разрыв между медианой и средним у `pretrained` (0.812 против 0.712) говорит,
что у неё есть провальные кейсы — на отдельных томах Dice падает до 0.52,
тогда как `sp` держится в 0.90-0.94 на всех.

**Это отменяет прежнее суждение «pretrained лучшая по зубам».** Оно опиралось
на подсчёт зубов на НАШИХ кейсах, то есть на счётную метрику без внешней
проверки — ровно та ошибка, что уже описана в разделе про метрики. На чужих
данных с эталоном `sp` выигрывает по всем показателям.

**Пазухи у неё не работают** — в ToothFairy3 они размечены на 10% объёма (см.
раздел выше), и при обучении с нуля не оживают вовсе. Брать у `pretrained`.

**При сравнении с DentVoxel обязательна перестановка сторон.** Датасеты
противоположно определяют, где право: зуб 11 у DentVoxel лежит левее середины
тома, у ToothFairy3 — правее. Без перестановки квадрантов (1<->2, 4<->3)
измерение даёт recall 97% при Dice 0.000: зуб «найден», но на месте соседа.
Это уже второй раз, когда обратная нумерация DentVoxel едва не увела в сторону.

## DentVoxel — ВНЕШНЯЯ проверка, а не добавка к обучению

Соблазн подмешать DentVoxel в обучающую выборку большой (разметка полнее), но
нумерация классов у двух датасетов **обратная**:

```
структура        DentVoxel        ToothFairy3
id 1             ВЕРХНЯЯ челюсть  НИЖНЯЯ челюсть
id 2             НИЖНЯЯ челюсть   ВЕРХНЯЯ челюсть
каналы           35 правый        3 левый
пазухи           37 правая        5 левая
```

Слепое объединение научило бы сеть путать верх с низом и лево с правом —
ровно та болезнь, от которой мы и лечимся (см. раздел про зеркалирование).
Плюс в DentVoxel нет глотки, реставраций, резцовых каналов и пульпы: на его
томах сеть получала бы сигнал «этого нет», что неверно.

Поэтому DentVoxel используется как **независимый тест**: измеряем на нём, сколько
зубов модель находит, не обучаясь на нём. Раньше такой проверки не было вовсе —
мы оценивали модель на тех же данных, на которых учили, и «число найденных
зубов» приходилось сравнивать между своими же моделями.

## Пульпу надо учить ОДНИМ классом, а не тридцатью двумя

Мы учили сеть различать пульпу каждого зуба отдельно — 32 класса. Замер по
нашим же данным показывает цену: пульпа одного зуба это медиана **665
вокселей, 4% от объёма зуба** (17 149), а у десятой части пульп меньше 250
вокселей. Тридцать два микроскопических класса на томе в 172 млн вокселей.

**Так задачу не ставят сами авторы датасета.** Официальный `evaluation.py`
челленджа ToothFairy3 содержит `convert_pulp_labels()`, схлопывающий все классы
пульпы в ОДИН (id 150) — и в предсказании, и в эталоне — перед подсчётом Dice.
Оценивается 46 классов, пульпа среди них одна. Победитель челленджа учит так же
(`mapping_DS119_singlepulp`) и возвращает номер зуба геометрией после сети.

`cbct_prepare_singlepulp.py` готовит такую разметку: **78 классов -> 47**.
Номер зуба возвращает `assign_pulp_to_teeth` уже после инференса.

**Присваивать надо ПО ВОКСЕЛЮ, а не голосованием по связной компоненте.**
Круговая проверка на client4 (схлопнули настоящую маску и восстановили
обратно) показала разницу:

```
голосованием по компоненте:  восстановлено 20 из 26, потеряны 11,16,17,28,42,43
по ближайшему зубу:          восстановлено 25 из 26, расхождение объёма 3.2%
```

При голосовании соседние пульпы сливаются в одну компоненту и всю её метят
одним номером. По ближайшему зубу граница проходит там, где меняется ближайший
сосед.

**Гоча, стоившая отдельной отладки: идентификатор пульпы не должен совпадать с
номером зуба.** Сначала было взято 46 — и это номер настоящего зуба. Функция
считала всю пульпу зубом 46 и возвращала 1 класс вместо 26. Теперь два разных
значения в двух пространствах нумерации:

- `SINGLE_PULP_ID = 46` — в ОБУЧАЮЩЕЙ разметке (nnU-Net требует классы подряд);
- `SINGLE_PULP_FDI = 150` — после обратного отображения в FDI, где зубы 11-48.

И проверка принадлежности зубу идёт строго по списку `TEETH_CLASSES`, а не по
диапазону 11-48: диапазон захватывает посторонние идентификаторы.

**Реалистичная планка Dice для пульпы у нас — 0.76, а не 0.90.** В литературе
три разных числа называются «Dice пульпы»: 0.86-0.93 получают на ОДНОМ
вырезанном зубе при вокселе 0.125-0.25 мм; на полном томе при 0.3 мм (наш
случай) опубликовано 0.76; только по каналам — 0.62-0.73. Коронковая камера
это 60-80% объёма пульпы, поэтому Dice «пульпы целиком» определяется почти
только ею.

## Зубы «съехали с кости»: ЧЕЛЮСТЬ НЕ ПРОХОДИЛА ЗЕРКАЛО АППАРАТА

Врач с приёма: «зубы сместились с кости или кость с зубов», дыры в лунках,
пульпы будто снаружи. Замер подтвердил и нашёл причину — она в нашем коде.

`build_mesh` строил меш кости из СЫРОЙ маски с диска (`_bone_shell` работает
без HU-гейта, это правильно), но брал её мимо `apply_scanner_mirror`. Зубы
же приходят из `filtered_mask_for` -> `_arrays_for`, где зеркало применяется.
Оба аппарата клиники помечены `mirrored: true`, поэтому **челюсть в меше была
зеркальна относительно зубов**.

Замер на client5 — расстояние от зуба до челюстной кости:

```
                                    медиана   худший   зубов дальше 3 мм
кость без зеркала (как было)         1.56 мм  10.13 мм      9 из 31
кость через ту же цепочку (стало)    1.99 мм   2.39 мм      0 из 31
```

Медиана чуть выросла, и это правильно: раньше часть зубов случайно попадала
близко к зеркальной кости, а разброс был огромный. Теперь все зубы сидят в
кости равномерно.

**Пульпы при этом были ни при чём** — проверено отдельно, все 30 лежат внутри
своих зубов. Они «выпадали» вместе с зубами, потому что зубы разъехались с
челюстью.

**Правило:** любая маска, попадающая в ОДИН КАДР с зубами, обязана пройти ту
же цепочку преобразований. Это третий случай в проекте, когда часть данных
прошла преобразование, а часть нет (были: `orient_sides` только при
инференсе, самопроверка на разных системах номеров).

## Цвет скана: лишняя инверсия V ломала оригинальный вид

Врач просил показать «реальный вид зубов, без насыщения и красок» — на
исходном скане, когда КЛКТ вызывает сомнения. Вместо этого зубы были покрыты
красными крапинами.

**Причина: мы переворачивали V-координату второй раз.** Инверсия нужна там,
где текстура читается САМИМИ через numpy (ветка запекания): массив
индексируется сверху вниз, UV — снизу вверх. В GLB же координаты уходят как
есть, и glTF применяет конвенцию сам. Наш переворот оказывался вторым, и
выборка уезжала в зеркальную по вертикали часть атласа.

Заметить по картинке было почти нельзя: форма оставалась правильной, а цвет
каждого треугольника приходил из случайного места. На розовой десне промах не
виден, на зубах он и давал крапины. Меряется СВЯЗНОСТЬЮ — расхождением цвета
у соседних по ребру вершин:

```
без инверсии   медиана 3.3, среднее  5.8
с инверсией    медиана 3.3, среднее 12.6
```

Медиана одинакова, потому что большая часть атласа — розовая десна, и промах
туда цвет почти не меняет. Разница набирается ровно на зубах.

**Три гипотезы до этого НЕ подтвердились, и все три стоили сборок:**
точечная выборка вместо билинейной (крапины остались), заливка чёрных швов
атласа (лечит другое — попадание в пустоту), ужатие UV внутрь фрагмента
(`_inset_uv`, оставлен в коде выключенным). Общая ошибка была одна: я лечил
фильтрацию, тогда как промахивалась сама координата.

### Атлас сканера — это КАДРЫ СЪЁМКИ, а не развёртка

Замер: участок поверхности размером 3 мм разбросан по атласу на
4350 x 4391 пикселей и попадает в 38-77 разных блоков 64 px. Соседние по
поверхности треугольники берут цвет из разных кадров, снятых под своим углом
и со своей экспозицией, — зуб покрывался мозаикой оттенков, хотя в самом
атласе он гладкий кремовый (проверено вырезкой из текстуры).

Разница между кадрами — шум съёмки, а не свойство зуба, поэтому она снимается
усреднением по РЁБРАМ СЕТКИ (`_smooth_vertex_colors`), а не в текстуре: там
соседний тексель может принадлежать другому кадру.

**Один проход, не два.** Два уже стирают рисунок эмали и превращают зуб в
пластик — врачу нужен реальный вид, а не стилизация. Предел граней поднят с
70 до 160 тысяч на челюсть: на 70 тысячах режущий край и фиссуры огрублены.

**Исходный скан рисуется БЕЗ ОСВЕЩЕНИЯ** (`MeshBasicMaterial`): любой
освещённый материал добавляет свою яркость и оттенок, блики выбеливают эмаль.
Объём при этом не теряется — сканер снимает со вспышкой в упор, и собственные
тени уже записаны в текстуру. Для СЕГМЕНТАЦИИ так делать нельзя: там цвет
условный, и форму читают по светотени.

## Пазуха размечена ТОЛЬКО ПО ДНУ — виновата РАЗМЕТКА ДАТАСЕТА

Врач с приёма показал, «откуда выходит наша пазуха и откуда должна». Замер
подтвердил жалобу и нашёл причину не там, где ожидалось.

```
client5, объём маски пазухи         норма ~15 см3 на пазуху
ours                1.1 и 1.8 см3
pretrained          0.2 и 1.2 см3
combo               0.5 и 0.2 см3
```

**Виновата не наша обработка.** Сырая маска прямо с диска, до фильтрации,
такая же: 0.2 и 1.2 см3. HU-гейт срезает 8-23%, и срезает не воздух. Это НЕ
та регрессия, что была с нижними зубами.

**И не свойство одной модели.** У ToothFairy3 пазухи размечены на 10% объёма
(замерено раньше), но и `pretrained` (ToothFairy2), которую держали донором
пазух именно как «размеченную нормально», даёт не больше. **Прежняя запись
про нормальную разметку пазух у ToothFairy2 неверна.**

**Место при этом правильное.** Внутри маски 92% вокселей — воздух, и лежит
она ровно над корнями моляров. Модель находит ДНО полости, а не промахивается.

**Дорастить по воздуху НЕ ВЫХОДИТ — проверено двумя способами.** Идея верная
по духу (маска для места, граница из плотности — так уже сделано с костью),
но ломается об анатомию: пазуха через соустье соединена с носовой полостью,
та через ноздри с наружным воздухом.

```
свободная заливка от ядра        1297 см3 из 1299 — весь кадр
сужение маски на 1-3 вокселя     связь держится
сужение на 6-8                   рвётся сама пазуха раньше соустья
ограничение боксом вокруг ядра   ядро разбросано, бокс почти во весь том
```

**Практический вывод.** Расстояние корень → ДНО пазухи считается верно и
остаётся: для имплантации нужно именно оно, а дно размечено. Объём пазухи,
утолщение слизистой и признаки синусита посчитать нечем — и это сказано
врачу прямо, отдельной строкой в разделе «что можно посчитать» и оговоркой
в основании находки. Тот же принцип, что с дентиклями: «не измеряем»
честнее, чем пустой результат, который читается как «патологии нет».

**НАЙДЕНА ПРИЧИНА, и она в эталоне.** Замер разметки Dataset112 (ToothFairy2,
40 томов), на котором обучена `pretrained`:

```
класс 5 (левая пазуха):  размечен в 27 из 40 томов, медиана 1.6 см3
класс 6 (правая пазуха): размечен в 25 из 40 томов, медиана 1.6 см3
```

При норме ~15 см3. **Модель не ошибается — она точно воспроизводит эталон.**
Наши 1-3 см3 на выходе и 1.6 см3 в разметке это одно и то же число. Значит
дообучение на ToothFairy2 бессмысленно по построению: сеть не может выучить
структуру, которой в эталоне нет (тот же вывод, что по зубам ToothFairy3).

**ЗАДАЧА РЕШАЕТСЯ, и разрешение тут ни при чём** (проверено по литературе
после справедливого возражения врача, что «невозможно» не проходит):

```
nnU-Net v2, 101 том, воксель 0.40 мм     Dice 0.964   DMFR 2024
U-Net, 90 пазух / 45 пациентов           Dice 0.910   PMC9385721
```

Воксель 0.40 мм КРУПНЕЕ нашего 0.31 — то есть на нашем оборудовании это
заведомо выполнимо. Вторая работа включает ПАТОЛОГИЧЕСКИЕ пазухи (утолщение
слизистой, ретенционные кисты, жидкость) и держит тот же уровень.

**Что для этого нужно: своя разметка, а не новый алгоритм.** В обеих работах
авторы размечали сами; 80 томов обучения дали Dice 0.964. Разметка простая —
воздушная полость с чёткими костными стенками. Это объём работы, а не научная
проблема, и она сразу закрывает объём пазухи, утолщение слизистой и кисты.

**Формулировка «не лечится» была неверной.** Верно: не лечится ЭТИМИ данными.

## Близость корня к пазухе — это НОРМА, а не находка

Мы выдавали тревогу при расстоянии ≤2 мм. Замер на клинических кейсах: срабатывало
у 62% верхних моляров client5 и 40% client4. Это ровно та ловушка, из которой
уже вытаскивали пародонт.

**Своя база, замеренная на эталонных масках ToothFairy3** (341 верхний
премоляр и моляр, 42 тома, `cbct_calibrate_sinus.py`):

```
ближе 0.5 мм — 41% зубов      медиана 0.8 мм
ближе 1.0 мм — 55%            75-й перцентиль 3.0 мм
ближе 2.0 мм — 66%            90-й перцентиль 6.5 мм
```

Литература подтверждает независимо: контакт корня с дном пазухи есть у
**75–78% моляров**, у части людей корень вообще внутри пазухи.

Теперь находка **информационная** (`severity: info`), отдаёт перцентиль и прямо
говорит, что близость патологией не является. В план не идёт: синус-лифтинг
попадает туда по другому основанию — планируемая имплантация в боковом отделе
верхней челюсти. На client4 позиций стало 2 (отсутствующие 15, 16) вместо 4.

**Гоча: градаций в близкой зоне быть не может.** Первая версия ставила порог по
10-му перцентилю выборки — это 0.3 мм, **меньше нашего вокселя 0.31**. Находка
стала физически невозможной. Порог поднят до медианы; ниже неё разрешение не
позволяет различать степени.

**Чего этими данными измерить НЕЛЬЗЯ:** протрузию корня В пазуху — клинически
самое важное. В разметке ToothFairy3 классы взаимоисключающие, воксель не бывает
одновременно зубом и пазухой, поэтому пересечений ровно 0% при литературных 75%.
Это свойство разметки, а не анатомии. Для имплантации правильнее мерить высоту
кости от гребня до дна пазухи (RBH, классификация A>10 / B 7–9 / C 4–6 / D 1–3) —
не сделано.

## Кортикальная стенка канала сильнее расстояния

Метаанализ 18 работ: риск повреждения нижнего альвеолярного нерва при
**отсутствии кортикальной стенки канала — 15.65%, при её наличии — 0.39%**
(отношение шансов 9.87). По одному расстоянию обрыв риска лежит около 1 мм: при
1–2 мм нарушений 0%, при 0–1 мм — 68%.

Наш порог 2.0 мм пришёл из рекомендации 1990 года под **плёночную панораму**,
где 2 мм закладывали на искажение снимка, а не на биологию.

`cortical_wall_fraction` считает долю плотной кости в кольце вокруг канала
**со стороны зуба** — стенка может отсутствовать с одной стороны и быть целой с
другой, а хирургу важна та, через которую пойдёт инструмент. Отсутствие стенки
поднимает находку `canal_close` с предупреждения до тревоги.

**Оговорка в основании обязательна:** стенка 0.68–1.10 мм — это 2–3 вокселя при
нашем 0.31, то есть признак на пределе разрешения, и шум можно принять за
отсутствие кости.

## Зуб-огрызок больше не проходит молча

Зуб, от которого в маске остался огрызок, формально проходил порог присутствия,
и находки по нему считались как по нормальному — а недостоверны они все сразу:
и длина корня, и уровень кости, и расстояния. Раньше ловилось только глазами.

`STUB_VOLUME_MM3 = 70` — порог по объёму. Ориентир из работы на **2312 зубах,
снятых на КЛКТ 0.3 мм с автосегментацией** (наш конвейер): объём корня у самой
мелкой группы (нижний резец) 106 ± 24 мм³, минус три сигмы — 34 мм³ на корень,
с коронкой примерно вдвое больше.

Проверка попала точно: на client4/tf3 порог поймал зубы **17 (68 мм³) и 46
(35 мм³)** — ровно те, что были записаны в этом файле как огрызки с корнем
2.7–3.6 мм, — и не тронул их же у `pretrained`, где они 779 и 884 мм³.

Такие зубы уходят в раздел ручной проверки и **исключаются из клинических
находок**: недостоверное измерение хуже отсутствующего, врач не отличит его от
настоящего. При этом в «отсутствующие» они не попадают — `missing` считается до
отсева.

**Оговорка:** объём на КЛКТ 0.3 мм систематически завышен примерно на 28%
относительно микро-КТ, и порог сегментации влияет на него сильнее, чем тип зуба.
Поэтому литературные числа взяты как форма распределения, а порог намеренно
мягкий — он ловит явные огрызки, а не пограничные случаи.

## Невозможное положение зуба тоже не проходит молча (17.11)

У зуба 28 на кейсе pair001 находка гласила «не дошёл до зубного ряда на
**41.4 мм**». Анатомически это невозможно — сорок миллиметров над
окклюзионной плоскостью это уже дно глазницы, — но проверки на невозможность
не было, и число уходило врачу как обычная ретенция.

**Сначала замер, потом порог.** Сырая маска зуба 28 разорвана на **53 куска**:
два тела по 193 и 103 мм³ плюс десятки крошек по 1-10 вокселей, растянутые на
20 мм по оси срезов. То есть сбой сегментации, а не странная анатомия.

Замер по ВСЕМ кейсам (40 находок ретенции в 18 кейсах):

```
41.4 мм   pair001   зуб 28   <- единственный выброс
15.3 мм   client3   зуб 18
14.6 мм   pair018   зуб 18
...остальные 11-15 мм
```

`RETENTION_ABOVE_MAX_MM = 30.0`. Порог выше заведомо настоящего максимума, и
это главное: у нашей же калибровки ретенции пять настоящих восьмёрок дали
29.5, 19.4, 15.3, 10.8 и 10.7 мм. Значит настоящую ретенцию правило не
погасит никогда. Знак не учитывается: зуб настолько же ниже своего ряда столь
же невозможен.

Такой зуб уходит в раздел ручной проверки (`tooth_position_implausible`) и
клинической находки по нему не получает — тот же приём, что у зуба-огрызка:
недостоверное измерение хуже отсутствующего, врач не отличит его от
настоящего.

**Это общий пробел, а не один случай.** Защиты от физически невозможного
значения у остальных измерений тоже нет; здесь она поставлена там, где
выброс замерен. Заводя новое измерение, стоит спрашивать, какое его значение
означает «маска собрана неверно», а не «у пациента так».

`FINDINGS_VERSION` 16 — после правки обязателен `cbct_rebuild.py`, иначе
врач продолжит видеть находки прошлой версии.

## Слой находок и план лечения (КЛКТ)

Три уровня, их нельзя схлопывать в одну модель:

1. **Структуры** — `cbct_backend.py`, маска nnU-Net.
2. **Находки** — `cbct_findings.py`: измеримые факты на зуб (расстояние корня до
   канала и до пазухи, плотность кости в лунке, ретенция, реставрации). Новых
   моделей нет, всё считается геометрией поверх маски. Отдаётся в UI через
   `/api/cbct/findings/{case_id}` и хранится в `meta.json` рядом с `info`.
3. **План** — `cbct_plan.py`: находки схлопываются в услуги с количеством и
   списком зубов («Удаление зуба мудрости ×2, зубы 18, 38») и раскладываются по
   этапам. Это та форма, в которой клиника выдаёт план пациенту.

**Порядок этапов взят из реального плана клиники** (`План_лечения_*.pptx`), а не
придуман: 1 Терапия (гигиена внутри неё, 1–2 мес) → 2 Хирургия и имплантация
(**параллельно этапу 1**) → 3 Ортодонтия (16–20 мес) → 4 Ортопедия. Гигиенист
отдельным этапом не идёт; хирургия не ждёт окончания терапии.

Клинические правила, которые уже зашиты и которые легко нарушить по незнанию:
восьмёрки не имплантируют; ретенированный клык выводят в дугу ортодонтически, а
не удаляют; при 4+ подряд отсутствующих зубах предлагается не цепочка имплантов,
а консультация ортопеда по протяжённому дефекту.

Всё помечено `draft: True`: пороги и правила врачом не подписаны. Находки на
ненадёжной маске получают пониженное доверие, а артефакты сегментации уходят в
раздел ручной проверки и в план не попадают. Стоимости и фотопротокол — не наша
зона, их считает отдельный сервис клиники.

## Что видит врач: карточка зуба, карта, срезы, подпись

Слой находок отвечает на вопрос «что нашли». Врачу с приёма нужно ещё три:
«где это», «на чём основано» и «кто это подтвердил». Отсюда четыре куска
интерфейса, каждый со своим правилом.

### Карточка зуба (`cbct_tooth.py`)

Три среза вдоль СОБСТВЕННОЙ оси зуба: мезио-дистальный, вестибуло-язычный и
поперечный на уровне шейки. Обычные срезы идут по сетке тома, а зуб стоит
наклонно — на аксиальном срезе моляр попадает косо, корни и канал расползаются
по соседним срезам. Тот же приём, что в панораме: плоскость строится по
анатомии, а не по сетке.

- **Направления берутся из `cbct_perio`, а не считаются заново**: ось зуба —
  `tooth_axis`, мезиальное направление — `site_dirs`. Своя копия разъехалась бы
  с измерением уровня кости, и врач увидел бы срез не в той плоскости, в
  которой посчитано число.
- **Зуб рисуется анатомически** (у верхнего коронка внизу) — так же, как на
  панораме, иначе врач сверяет одно с другим и видит зуб вверх ногами.
- Вестибулярное направление — наружу от центра дуги СВОЕЙ челюсти: по всем
  зубам сразу центр уехал бы вбок.
- У зуба без соседа по номеру подписи «мезиально / дистально» не выводятся:
  направление в этом случае произвольное, и подпись была бы враньём.

### Контуры вместо заливки на срезах

Полупрозрачная заливка закрывает саму плотность, а врач читает срез именно по
ней: кариес под пломбой, границу очага, рисунок губчатой кости. Теперь по
умолчанию рисуется обводка (`overlay_contour`), заливка осталась
переключателем. Свой зуб обводится ярче и толще, остальное приглушено.

**Гоча: корональный и сагиттальный срезы показывались вверх ногами.** Строка 0
рисуется сверху, а ось z у наших кейсов растёт вверх — то есть сверху
оказывался подбородок. Разворот теперь по `zup_for` (кэш на кейс), и фронт по
тому же признаку разворачивает перекрестие. Это третий случай той же природы:
панорама, ось зуба, теперь MPR.

### Основание находки, а НЕ процент уверенности

У Diagnocat на находке стоит процент. У нас его не будет, и это решение, а не
недоделка: процент — это вероятность, а вероятности у нас нет. Находки
считаются геометрией по маске, разметки рентгенолога, на которой её можно было
бы откалибровать, в проекте нет. Нарисованные «87%» врач не может ни
проверить, ни оспорить.

Вместо него каждая находка несёт поле `basis` — что измерено, сколько, при
каком пороге и с какой оговоркой: «расстояние корень → канал 1.2 мм, контакт
≤0.5, близко ≤2.0, воксель 0.31 мм». Это проверяется прямо на срезе. То же
правило, по которому пародонт отдаёт перцентиль выборки, а не стадию
пародонтита.

### Проверка и подпись врача

Отметка по каждой находке (подтверждена / отклонена) и подпись под набором
живут в `meta.json` рядом с находками.

- **Отклонённая находка в план НЕ идёт** — ради этого проверка и нужна.
  В ленте она остаётся видимой (зачёркнутой): врач должен видеть, что уже
  отсмотрел.
- **Любая правка отметок СНИМАЕТ подпись.** Иначе под подписью молча оказался
  бы другой план.
- **В подпись пишется `FINDINGS_VERSION`.** Правила ещё меняются, и подпись
  под прошлой версией к новому набору не относится — интерфейс показывает это
  явно и просит подписать заново.
- Ключ находки — код плюс её зубы, а не номер строки: список пересчитывается и
  меняет длину, отметка уехала бы на чужую строку. У находки без зубов
  («канал слева не сегментирован») к коду добавляется хеш текста — иначе
  отметка на одной такой легла бы сразу на все.
- Это ОТМЕТКА, а не электронная подпись: аутентификации в демо нет, имя врач
  вводит сам. Так и подписано в интерфейсе.

### Адрес экрана: вкладка и зуб

`/cbct/<кейс>/<модель>?tab=<вкладка>&tooth=<FDI>` — ссылка ведёт не на кейс
вообще, а на то, что врач хочет показать («смотри зуб 13»). Адрес
переписывается при каждом переключении вкладки и открытии карточки, так что
строка адреса всегда отражает экран. Побочно это единственный способ проверить
интерфейс без расширения браузера: headless Chrome умеет только открыть URL и
снять картинку.

### Адрес экрана: вкладка и зуб

`/cbct/<кейс>/<модель>?tab=<вкладка>&tooth=<FDI>` — ссылка ведёт не на кейс
вообще, а на то, что врач хочет показать («смотри зуб 13»). Адрес
переписывается при каждом переключении вкладки и открытии карточки, поэтому
строка адреса всегда отражает экран. Побочно это единственный способ проверить
интерфейс без расширения браузера: headless Chrome умеет только открыть URL и
снять картинку, кликать он не умеет.

### Зубная карта и связка экранов

Карта FDI над находками: какие зубы есть, где находки, значками — что именно
(пломбированный канал, реставрация, уровень кости, ретенция, близость к каналу
или пазухе). Клик по зубу где угодно — в карте, в ленте находок, на панораме —
открывает карточку этого зуба И ведёт туда же перекрестие MPR. Клик по строке
находки только наводит камеру: врач листает ленту, и уводить его с неё на
каждый клик нельзя.

## Недостающие классы анатомии: их ВЫБРАСЫВАЛ наш код

Модель tf3 предсказывает больше, чем показывал вьюер. `filter_mask` собирает
результат по `GROUPS`, и класс, не попавший ни в одну группу, исчезал молча —
без предупреждения, без строки в панели, нигде.

Так терялись три класса ToothFairy3:

```
                         client4   client2   client5
103 резцовый канал L        573       619        23
104 резцовый канал R        768       727       424
105 язычный канал           469       140       259   (вокселей)
```

Клинически это не мелочь: имплантат во фронтальном отделе нижней челюсти
ставится ровно там, где идёт резцовый канал. Заведены группы `incisive` и
`lingual`; челюсть разделена на `mandible` и `maxilla` (модель их и так
различает, объединяла только наша группировка — а врачу нужно гасить верхнюю,
чтобы смотреть нижнюю).

- Правило связных компонент для них своё, `canal_small` (120 вокселей): порог
  нерва (500) снёс бы левый резцовый канал client5 (23 вокселя) вместе с
  правым (424).
- Под форм-правило против streak-артефактов они НЕ попадают намеренно: они и
  есть тонкие вытянутые трубки, правило снесло бы их целиком — как и нерв.
- **Десны на КЛКТ нет и не будет**: в разметке ToothFairy3 такого класса нет.
  Она есть на интраоральном скане — это другой трек.

Проверка гипотезы, которая НЕ подтвердилась: я ожидал, что гауссово размытие
маски (sigma 0.9) съест тонкий канал ниже изоуровня 0.5 и уронит marching
cubes. Замер на client4: полутолщина каналов 2.0–2.4 вокселя, максимум после
размытия 0.92–0.98 (у нерва 4.9 и 1.00). То есть проблемы нет. Страховка со
снижением sigma в `_class_mesh` оставлена на случай структуры тоньше этих, но
сегодня она не срабатывает ни разу.

## Обучение nnU-Net на этой машине: две ловушки, стоившие вечера

### Не помещается в видеопамять — но НЕ падает, а тормозит в 50 раз

Дообучение ResEncL на ToothFairy3 шло **6384 с на эпоху** вместо ожидаемых
1046. GPU показывал 100% загрузки, в логе ни одной ошибки. Три гипотезы
подряд оказались неверными: демо отнимает память (нет, освобождение не
помогло), формат данных (у обоих датасетов одинаковый `.b2nd`), число
загрузчиков (по 12 у всех запусков).

Причина нашлась замером с настоящей функцией потерь:

```
вариант                        с/итерацию   пик памяти   эпоха
49 классов, batch 2 (эталон)        33.2      38.8 ГБ    138 мин
78 классов, batch 2 (было)          45.1      53.1 ГБ    188 мин
78 классов, batch 1 (стало)          0.35     27.1 ГБ      1 мин
78 классов, batch 2, окно 96         1.15     34.5 ГБ      5 мин
```

Карта — 34.2 ГБ. Сама сеть занимает 27 ГБ и считает быстро (0.35 с), но
`DC_and_CE_loss` разворачивает разметку в one-hot на КАЖДОМ уровне глубокого
надзора: при 78 классах и окне 112x224x256 только верхний уровень — 4 ГБ.
Итого требуется 53 ГБ. **Windows при исчерпании видеопамяти не роняет процесс
с OOM, а незаметно подменяет её оперативной** — отсюда 100% загрузки, чистый
лог и падение скорости в полтораста раз.

`batch_size = 1` в плане: 119.6 с на эпоху вместо 6384, то есть 8 часов на
250 эпох вместо 18 суток. На качество влияет слабо — сеть нормируется
InstanceNorm, по каждому образцу отдельно, а не по батчу.

**Побочный вывод:** планы ResEncL писали авторы бенчмарка под карту на 80 ГБ.
Эталонные 1046 с/эпоху на ToothFairy2 тоже были следствием спилла (38.8 ГБ не
влезали) — то есть у нас этот план НИКОГДА не работал как задумано.

### Дообучение требует СВОЕЙ скорости обучения

У nnU-Net `initial_lr = 1e-2` — это значение для обучения С НУЛЯ. При
дообучении оно на порядок велико и разрушает перенесённые веса в первых же
эпохах: «дообучение» превращается в обучение заново, только со сбитого старта.

Симптом виден на НУЛЕВОЙ эпохе и стоит того, чтобы смотреть туда всегда:
живыми остались 2 класса из 76, хотя анатомия (челюсти, нерв, пазухи) у
ToothFairy2 и ToothFairy3 ОДИНАКОВАЯ и должна была стартовать высокой.

Итог того прогона (250 эпох, lr 1e-2): 69 полноценных зубов на трёх кейсах
против 74 у исходного чекпойнта ResEncL — то есть модель не догнала
собственный старт. Общий Dice тоже вышел ниже старой tf3 (0.5506 против
0.5624), и это был второй сигнал, который легко списать на «среднее по
78 классам».

Свои тренеры лежат в `research/scripts/nnunet_trainers/` и ставятся в пакет
скриптом `install.py`: nnU-Net ищет класс тренера обходом СВОЕГО пакета, снаружи
файл указать нельзя, а `.venv` в гит не входит — без установки настройка молча
пропадёт.

```
nnUNetv2_train 113 3d_fullres 0 -p nnUNetResEncUNetLPlans     -tr nnUNetTrainer_750epochs_lr1en3 --c
```

**Продолжать, а не начинать заново.** Чекпойнт хранит веса, состояние
оптимизатора и номер эпохи, поэтому `--c` из папки нового тренера подхватывает
наработанное. Расписание полиномиальное от `initial_lr` за `num_epochs`: при
продолжении с 250-й эпохи из 750 скорость стартует с 6.9e-4, то есть мягко.

**Осторожно с `-pretrained_weights` при продолжении:** этот путь ПРОПУСКАЕТ
выходные слои (`.seg_layers.`), и они обнулятся. Для продолжения нужен именно
`--c` с чекпойнтом в папке тренера.

### Метрика должна отвечать на вопрос врача

Дообученную модель я сперва объявил лучшей, посчитав НАЙДЕННЫЕ ЗУБЫ (29.3
против 27.3). Врач открыл 3D и увидел обрывки. Замер по объёму показал правду:

```
зуб   pretrained    tf3l
 13      513 мм3    99 мм3   0.19x  огрызок
 14      438 мм3    45 мм3   0.10x  огрызок
 23      516 мм3   969 мм3   1.88x  раздут вдвое
```

Из 29 «найденных» зубов полноценных (>= 200 мм³) оказался 21. По полноценным
модель проигрывала: 69 против 74.

**Счётная метрика проходит порог присутствия даже на мусоре.** Мерить надо
величину, которой пользуется врач — объём, размер, расстояние — и сверять с
анатомической нормой (резец 350–500 мм³, клык 600–800, моляр 900–1400).
Скрипт для этого — `cbct_compare_models.py`.

### Та же ловушка на ИНФЕРЕНСЕ: карта вероятностей не влезает

Через день после обучения то же самое повторилось на предсказании, и я не
узнал ловушку в лицо. Инференс `tf3l` на client4 шёл **69 минут вместо трёх**,
GPU показывал 100%, ошибок не было.

nnU-Net при `perform_everything_on_device=True` держит на видеокарте тензор
«классы x весь объём». Замер (78 классов, half precision):

```
кейс                срезов   карта вероятностей   влезает в 34.2 ГБ
client2 / client5      348          15.6 ГБ            да
client4                599          26.8 ГБ            НЕТ  (+ сама сеть)
```

То есть ОДНА И ТА ЖЕ модель на одном кейсе считает нормально, а на другом
уходит в спилл — разница только в высоте тома. Заметить это по логу нельзя.

Решение: `_fits_on_gpu(model, shape)` считает размер карты ПЕРЕД каждым
инференсом, и при превышении `PROB_MAP_GPU_LIMIT_GB` (12 ГБ, с запасом от
15.6) предиктор создаётся с `perform_everything_on_device=False` — агрегация
уходит на CPU, где 128 ГБ. Сам счёт остаётся на GPU. Результат: те же
3 минуты. Предикторы кэшируются по ключу «модель + устройство», иначе кейсы
дерутся за один объект.

**Общее правило, выученное дважды:** прежде чем ждать результата от nnU-Net,
прикинуть, сколько памяти требует ЭТА конфигурация на ЭТИХ данных. Windows об
исчерпании видеопамяти не сообщает — он молча меняет её на оперативную, и
единственный симптом это скорость.

### batch 2 не помещается даже при 47 классах — проверено дважды

Сокращение классов с 78 до 47 (пульпа одним классом) память НЕ спасает. Замер:
первая эпоха при `batch_size = 2` заняла **1429 с вместо ожидаемых 120**, то
есть снова спилл. При 1500 эпохах это 25 суток.

Логика «меньше классов -> меньше one-hot в лоссе -> влезет» верна по
направлению, но запаса нет: сама сеть ResEncL занимает 27 ГБ из 34.2, и
экономии двух гигабайт недостаточно.

**Правило для этой машины: с планом ResEncL и окном 112x224x256 ставить
`batch_size = 1` СРАЗУ, не проверяя.** Признак спилла — первая эпоха длиннее
пяти минут; проверять её обязательно, иначе потеря обнаружится через сутки.

### Убивать обучение — только вместе с деревом процессов

После двух принудительных остановок головного процесса осталось **36
осиротевших загрузчиков**, они держали 13 ГБ и съели лимит выделения памяти.
Следующий запуск упал на `numpy._core._exceptions._ArrayMemoryError: Unable to
allocate 57.6 MiB` — при 93 ГБ «свободной» физической памяти: Windows
отказывает по лимиту ВЫДЕЛЕНИЯ (RAM + файл подкачки), а не по свободной.

У nnU-Net 12 обучающих и 6 валидационных процессов-загрузчиков, и родителя они
переживают. Останавливать так:

```
taskkill /T /F /PID <pid>          # /T — вместе с деревом
```

Проверять после остановки: `Get-CimInstance Win32_Process -Filter "Name like
'%python%'"` — если остались процессы с убитым родителем, это сироты.

## Модели ТЕРЯЮТ ЗУБЫ, и по-разному. Ни одна не лучшая

Врач загрузил в демо тот же DICOM-каталог, что открыл в стороннем вьюере
(Rainbow), и увидел у себя почти пустые челюсти: «с каких пор у меня нет
зубов». Проверка по шагам:

1. **Данные и конвертация ни при чём.** Том, собранный демо из DICOM, и наш
   готовый `client5_0000.mha` совпадают полностью: та же форма (335×516×516),
   тот же воксель, тот же диапазон, те же перцентили, то же число вокселей
   выше HU-гейта (5.80 млн). Байт в байт один и тот же пациент.
2. **Маска на диске у обоих одинаковая** — 23 зуба. То есть дело не в
   загрузке, а в сегментации.
3. **Разные модели дают РАЗНОЕ число зубов на одних и тех же данных:**

```
кейс        ours  pretrained  tf3    что tf3 потеряла против pretrained
client2       23        20     23    16, 38, 46
client4       26        32     29    15, 44, 45
client5       26        30     23    12, 42, 43, 44, 45, 46, 47
```

У client5 `pretrained` нашла 30 зубов — ровно то, что видно в Rainbow (все,
кроме 18 и 28), а `tf3` потеряла почти весь четвёртый квадрант. Но на client2
хуже всех оказалась именно `pretrained` (20 против 23). **Победителя нет**,
и выбрать модель раз и навсегда нельзя.

Практический вывод на сегодня: `tf3` берут ради пульпы (эндодонтический
статус без неё не считается), но зубы она теряет чаще других; если у пациента
в 3D недостаёт зубов — переключить модель в адресе (`/cbct/<кейс>/pretrained`)
и сравнить. Правильное решение — считать двумя моделями и объединять: анатомию
и зубы брать у лучшей по зубам, пульпу у `tf3`. Это не сделано: удваивает
время инференса и требует правила «чей это зуб» при расхождении номеров.

**Мораль:** число зубов на модели — это метрика, которую надо показывать
врачу, а не прятать. Врач заметил расхождение за минуту, потому что открыл
тот же файл в другом вьюере; мы бы не заметили никогда.

## Дообучение ToothFairy3 ОСТАНОВЛЕНО: лечили не ту болезнь

Дообучение ResEncL на ToothFairy3 прошло два круга (250 эпох при lr 1e-2 и
100 эпох при 1e-3) и остановлено. Малый lr починил то, для чего брался —
веса перестали разрушаться на старте (0.653 против 0.024 на нулевой эпохе),
но качество зубов не изменилось: за 100 эпох тренд **-0.001 при разбросе
0.067**, то есть плато.

Причина, найденная замером уже после остановки: дело не в длительности
обучения, а в том, ЧТО модель предсказывает. Разложение потерь по этапам
нашей фильтрации (client5, объём зубов):

```
этап                      pretrained   tf3l
сырая маска                    100%    100%
после HU-гейта                  99%    100%
после opening(2)                96%     92%
после отсева далёких кусков     94%     70%   <- здесь
```

Модели на 78 классов дают ФРАГМЕНТИРОВАННЫЕ зубы: из одного куска состоят
73% зубов у `pretrained` и лишь 27% у дообученной. И куски эти не рядом —
**медиана зазора до тела зуба 30.6 мм**, то есть метка «зуб 15» стоит на
другом конце челюсти. Ослабление порога не помогает: при 8 мм вернулось бы
224 мм³ из 3760. Наш фильтр работает правильно, модель метит не туда.

**Вывод: длительность обучения тут ни при чём, и дообучать дальше
бессмысленно.** Задача возвращается либо с лучшей разметкой, либо с другой
постановкой — но не с добавлением эпох.

## Сводная модель: зубы от одной сети, пульпа от другой

Раз лучшей модели не существует, берём у каждой то, в чём она сильна:
анатомия и зубы от `pretrained` (73% зубов одним куском), пульпа от `tf3`
(у `pretrained` такого класса нет вовсе, а без пульпы не считается
эндодонтический статус). Собирается `build_combo_mask`, выбирается в
интерфейсе как «Сводная».

Результат на трёх кейсах — зубы ровно как у `pretrained`, плюс пульпа:

```
кейс      модель       полноценных зубов   пульп   зубов одним куском
client4   pretrained                  31       0          77%
client4   tf3                         21      26           4%
client4   combo                       31      15          77%
client5   pretrained                  29       0          72%
client5   combo                       29      15          72%
```

- **Пульпа принимается, только если её зуб есть у донора анатомии И она
  лежит внутри него.** Иначе вышла бы пульпа без зуба или в чужом зубе, а
  весь эндодонтический статус построен на сравнении «пульпа минус дентин
  ТОГО ЖЕ зуба».
- Допуск здесь свой, `COMBO_PULP_DIST_MM = 2.5` мм, а не 1.0 как внутри одной
  модели: границы зуба у разных сетей смещены. Замер на трёх кейсах: свои
  пульпы дают медиану 1.3–2.2 мм, мусор — 6–60 мм, порог проходит между
  группами с запасом. Отклоняется около трети пульп, и это правильно.
- Резцовый и язычный каналы (103–105) тоже берутся у ToothFairy3.
- Цена: инференс двумя сетями вместо одной.

**Оговорка:** на client2 `pretrained` слабее прочих (14 полноценных зубов
против 19 у `tf3`), и там сводная маска наследует эту слабость. Выбор донора
жёсткий, по кейсу он не подстраивается — это осознанное упрощение, иначе
пришлось бы решать «чей это зуб» при расхождении нумерации.

## Ретенция: одной кости мало, нужен ещё и уровень ряда

Врач показал, что у client4 не прорезались ОБЕ верхние восьмёрки, а находка
выдавалась только на одну. Причина: признак был один — доля коронки,
упирающейся в кость. У зуба 18 она 76%, у 28 всего 27%, потому что часть его
коронки граничит не с костью, а с полостью. При этом оба зуба стоят
одинаково — на 10.8 и 10.7 мм выше зубного ряда.

Добавлен второй признак: **насколько зуб не дошёл до окклюзионной
плоскости**. Уровень ряда берётся по своей челюсти отдельно и БЕЗ восьмёрок —
они и есть проверяемые. Достаточно любого из двух признаков.

Порог откалиброван по разрыву на 115 зубах четырёх кейсов:

```
29.5  19.4  15.3  10.8  10.7   |   6.5  6.3  5.8 ... (остальные 110)
   пять восьмёрок              |   обычные зубы
```

Между 10.7 и 6.5 мм пусто, любой порог от 7 до 10 мм даёт те же пять
находок, и все пять — восьмёрки. `RETENTION_ABOVE_MM = 8.0`.

**Гоча:** первая версия стояла на 4 мм и тянула четыре обычных зуба. Разброс
высоты у нормально прорезавшихся доходит до 6.3 мм — клык длиннее моляра, и
медиана по ряду этого не выравнивает. Порог по разрыву, а не «на глаз».

## Сторону НЕЛЬЗЯ определить по файлу: аппараты пишут заглушку

Врач: «я поставил вид в двух вьюерах в одну сторону и вижу зуб по разные
стороны». Разбор дал три вещи, и первая — методологическая.

**Проверка сторон была замкнута сама на себя.** `orient_sides` берёт
направление «влево пациента» из ориентации в файле и проверяет, что зубы
лежат согласованно с ней. Но обработка использует ТОТ ЖЕ источник. Если
ориентация в файле неверна, проверка подтвердит согласованность данных с
самими собой и ничего не поймает. Это та же ошибка, за которую забракованы
два признака в канонизации сканов (см. раздел про подкову): признак, взятый
из того же места, что и обработка, не может её проверить.

**И источник действительно ненадёжен.** Замер по клиническим кейсам:

```
кейс                        аппарат              IOP            позиция пациента
client2, client4, client5   Dentium rainbowCT    [1,0,0,0,1,0]  (0, 0, 0)
client3                     Dentium brightCT     [1,0,0,0,1,0]  (0, 0, 0)
```

Метаданные ориентации у ВСЕХ одинаковые, и позиция пациента — заглушка.
По файлу отличить укладку одного аппарата от другого невозможно, а врач
заметил расхождение ровно на единственном снимке с другого аппарата.

**Решение: конвенция хранится на АППАРАТ и подтверждается врачом.**
`read_scanner` кладёт в кейс производителя, модель и флаг `position_is_stub`;
`scanner_sides.json` хранит по одному правилу на аппарат;
`scanner_sides_state` отдаёт статус в интерфейс. Подтверждается ОДИН раз, и
дальше правило применяется ко всем снимкам с этого аппарата, включая новые.
Подтверждённое правило ПЕРЕВЕШИВАЕТ ориентацию из файла.

Иначе нельзя: левое и правое на симметричной челюсти алгоритмом не
различаются, это внешнее знание. Если для аппарата правила нет, интерфейс
говорит прямо — «стороны не подтверждены, номерам зубов доверять нельзя», а
не молчит.

**Гоча при записи правила:** конвенцию нельзя выводить из косвенных слов. Я
вывел её из фразы врача про «несостыковку» и включил зеркалирование не в ту
сторону — проверка показала, что до правки было верно. Правило пишется
только по прямому ответу на прямой вопрос: «на какой стороне ПАЦИЕНТА этот
зуб».

## Самопроверка вместо проверки глазами на трёх кейсах

Врач: «ты закрываешь каждую проблему вручную под каждый кейс?». Правила у нас
общие и к кейсу не привязаны, но ДОКАЗАТЕЛЬСТВО их правильности было
выборочным — три-четыре примера, посмотренные глазами. Отсюда все регрессии,
которые находил врач, а не мы.

`cbct_selfcheck.py` гоняет инварианты по всем кейсам разом и возвращает
ненулевой код, если хоть где-то проблема. Проверяет только то, что верно для
любого человека:

* стороны (с допуском у центральных резцов — они на средней линии);
* обе челюсти: если нижняя в кадре, а зубов на ней нет — это отказ;
* не съел ли наш фильтр живое (сравнение с маской ДО обработки);
* огрызки;
* **версии меша и находок** — не забыт ли инкремент;
* подтверждены ли стороны для аппарата этого кейса.

**Запускать после КАЖДОЙ правки фильтрации, ориентации или порогов.**

### Две регрессии, которые он поймал сразу

**Фильтр артефактов съедал живые зубы.** `TOOTH_BONE_MAX_MM` откалиброван на
ЭТАЛОННЫХ масках ToothFairy3, где челюсть размечена полностью, а применялся к
нашей маске ПОСЛЕ HU-гейта, который выгрызает 30-54% кости. Зубы «отдалялись»
от огрызков и попадали под отсев: на client4 терялось 13 настоящих нижних
зубов из 32, находки строились на 19. Исправлено — расстояние меряется до
челюсти из маски модели, а не до того, что осталось после нашей обработки.

Мораль та же, что и с порогами из литературы: **база измерения на эталоне не
равна базе на предсказании.**

**Версия обработки не была поднята.** Фильтр исправили, номер оставили — и
демо честно отдавало врачу меши, собранные до исправления. Пациент в 3D
по-прежнему был без нижних зубов, хотя в коде уже всё правильно. Теперь это
ловит самопроверка.

## Стороны зеркальны: ToothFairy размечен НЕ так, как лежат наши снимки

Врач с приёма: «во вьюере 22-й зуб стоит справа, а должен слева». Проверено —
он прав, и это была самая дорогая из найденных ошибок: план лечения уходил бы
врачу с зеркальными номерами зубов.

**Источник — обучающие данные, а не наш вьюер и не камера.** Замер по
эталонной разметке (80 томов ToothFairy3, 40 томов ToothFairy2): класс,
названный `Left IAC`, ВО ВСЕХ лежит там, где по ориентации из самого файла
правая сторона. Датасет последователен внутри себя — он просто называет
стороны с точки зрения смотрящего, а не пациента.

Истина берётся из DICOM клиники: `ImageOrientationPatient = [1,0,0, 0,1,0]`,
аппарат Dentium. По стандарту DICOM ось X пациента смотрит ВЛЕВО, значит на
наших снимках больший индекс по оси 2 массива = левая сторона пациента. Это
однозначно и проверяется в файле, а не на глаз.

Замер на client5 (31 зуб), сколько зубов стоит НЕ на своей стороне:

```
модель        было   стало     обучена на
sp              30       1     ToothFairy3, зеркалирование L-R выключено
tf3l            25       2     ToothFairy3 (на client2)
pretrained       0       0     ToothFairy2
combo            0       0     ToothFairy2
```

**Две РАЗНЫЕ болезни, и путать их нельзя.** `sp` и `tf3l` зеркалят целиком:
все зубы разом стоят не на своей стороне. А `tf3` (стандартный тренер)
зеркала не даёт, но путает ОТДЕЛЬНЫЕ зубы — 5-7 на кейс (client2 5 из 23,
client4 6 из 29, client5 7 из 23). Стандартный тренер зеркалит лево-право в
аугментации и в TTA, и сеть теряет уверенность в стороне поштучно; `sp`
обучена `nnUNetTrainer_onlyMirror01`, лево-право не зеркалится, и она
СТАБИЛЬНО воспроизводит конвенцию датасета.

Стабильная ошибка лучше плавающей: целиковое зеркало чинится одним
разворотом, а поштучные промахи `tf3` `orient_sides` НЕ исправляет — правило
глобальное по устройству. Это довод в пользу `sp` сверх её метрик.

**Гоча при замере: среднюю линию нельзя брать по парам одноимённых зубов.**
Сначала я так и считал и получил «tf3 зеркалит 19 зубов из 23 на client5» —
неверный вывод. Если часть зубов перепутана, пары считаются не по тем зубам
и медиана уезжает: у client5/tf3 она дала 274 против 258 у центра масс
челюсти, 258 у геометрического центра тома и 253 у центра плотной ткани.
Смещение на 16 вокселей переворачивает вердикт по зубам возле средней линии.
`orient_sides` берёт центр масс челюсти — он опирается на структуру, которую
сторона не затрагивает.

**Чиним голосованием по геометрии, а не свопом по имени модели**
(`orient_sides`): у зубов квадрантов 2 и 3 координата вдоль «влево» обязана
быть больше средней линии; если против этого большинство зубов — переставляем
номера квадрантов у ВСЕХ зубов, их пульп и парных каналов с пазухами разом.
Решение глобальное: зеркало либо есть, либо нет, а поштучный разбор сломал бы
верную модель на зубе, который просто уехал за среднюю линию (у client5 зуб
41 стоит в 0.7 мм от средней линии — по нему судить нельзя).

Правило самокорректирующееся, поэтому включено для ВСЕХ моделей: на верной
маске оно не меняет ничего (проверено — `pretrained`, `combo`, `ours` не
тронуты ни на одном кейсе).

**Что оно НЕ чинит.** Сверка после правок по всем кейсам и моделям: у `sp`,
`pretrained` и `combo` на client5 все 30 зубов на своих сторонах, у `tf3`
на том же кейсе 13 зубов из 23 остаются перепутанными. Глобальный разворот
поштучные промахи не берёт по устройству — либо переучивать без зеркалирования
L-R (как `sp`), либо не полагаться на сторону у `tf3`.

Отдельно: зубы у самой средней линии (11, 21, 31, 41) дают ЛОЖНЫЕ
срабатывания такой сверки — у client5 зуб 41 стоит в 0.7 мм от неё. На
client4 «спорный 41» у трёх моделей сразу — это ровно тот случай, а не
ошибка модели.

Вызывается в двух местах: при инференсе (`predict`) и в `_arrays_for` —
второе обязательно, иначе маски, уже лежащие на диске, остались бы
зеркальными. `split_paired_sides` тоже получил знак оси: он раскладывал
парные структуры по средней линии, молча считая, что лево всегда справа
на изображении.

**Мораль, уже четвёртая в проекте:** прежде чем править пороги, проверь
систему координат. Раньше это была вертикаль дуги на сканах (AUC 0.573 ->
0.971), ось зуба на КЛКТ, разворот MPR; теперь — сторона пациента. И общий
вывод про источник: ориентация, записанная в файле датасета, и смысл его
меток — разные вещи, сверять их надо замером.

## Зуб и коронка сидят В КОСТИ: отсев артефактов по расстоянию до челюсти

Тот же разбор нашёл вторую вещь: у client5 кусок в 228 вокселей был помечен
зубом 28 и висел в 21.9 мм от челюстной кости, за её пределами; рядом с ним
лежал мусорный кусок «реставрации» на 126 вокселей в 26.8 мм.

Порог откалиброван на эталоне ToothFairy3, а не подобран:

```
                      зубы (790 шт, 30 томов)   реставрации (31 компонента)
медиана                       2.0 мм                     4.6 мм
99-й перцентиль               5.4 мм                     7.2 мм
максимум                      8.4 мм                     7.3 мм
дальше 12 мм                  НИ ОДНОГО                  НИ ОДНОЙ
```

`TOOTH_BONE_MAX_MM = 12.0`, группы `BONE_ANCHORED_GROUPS`. Наши настоящие
зубы укладываются в эталон (самый дальний — 48-й у client2, 7.8 мм), а мусор

томе законно лежит несколько коронок, и дальний мусор не должен уносить
соседнюю настоящую пломбу. Пульпа удалённого зуба отпадает следом сама —
правило «пульпа внутри своего зуба» не находит зуба.

Оговорка: эталонных компонент реставраций всего 31, поэтому запас для них
определён слабее, чем для зубов.

**Чем это НЕ является.** У client5 между режущими краями 11 и 41 лежит
плотный объект (18.3 мм³, плотность 3842 при эмали ~3043, прилегает к 11 на
66% и к 41 на 34%). Он виден на срезах ярким пятном — то есть реален, это не
артефакт сегментации, и фильтром его убирать нельзя. Врачу он показывается
как есть.

## Ложный «мост» между режущими краями (артефакт смыкания)

Врач: «между 11 и 41 металлическая штука, которой нет в стороннем вьюере».
Проверено — её нет и у остальных наших моделей: в этой зоне 0 вокселей у
`ours`, `pretrained`, `tf3`, `tf3l`, `combo` и 604 у `sp`.

**Плотность тут не улика, и на этом я один раз ошибся.** Сначала объект был
объявлен настоящим по «плотности 3842 при эмали 3043» — но 3043 замерено на
ДРУГОМ кейсе. У client5 эмаль резцов доходит до 4800, то есть объект
неотличим от эмали тех самых зубов, между которыми зажат. Плотность
реставраций вообще не разделяет: замер по трём кейсам даёт отношение к эмали
0.32–1.08 у настоящих (композит и керамика РЕЖЕ плотнее эмали) против 1.18 у
артефакта.

Разделяет геометрия: моста между верхней и нижней челюстью не бывает, они
двигаются. Доля вокселей компоненты в пределах 1.5 мм от зубов каждой челюсти:

```
настоящие пломбы (14789, 8105, 228 вокс)   min(верх,низ) = 0 .. 17.5%
артефакты смыкания (604, 314, 56 вокс)     min(верх,низ) = 50 .. 100%
```

`BITE_ARTIFACT_JAW_FRAC = 0.35` стоит в разрыве. Правило ограничено МЕЛКИМИ
кусками (`BITE_ARTIFACT_MAX_VOX = 2000`): компонент всего восемь на трёх
кейсах, поэтому крупная реставрация не удаляется никогда, какой бы ни была её
доля касания. Эталоном это не калибруется — см. раздел про разомкнутые челюсти.

## Кость разваливалась на куски: виноват НАШ HU-гейт, а не модель

Врач: «внутри челюсти кости разваливаются на куски». Гейт по плотности нужен
для ИЗМЕРЕНИЙ (иначе мягкие ткани сойдут за кость), но для МЕША он губителен:
губчатая кость местами тоньше порога, гейт выгрызает её изнутри, и marching
cubes честно обводит каждую полость.

```
                              выгрызено гейтом   оболочек в меше   площадь
нижняя челюсть client5              19%              174           345 см2
верхняя челюсть                     38%              174           187 см2
после правки                         —                 2           250 см2
```

`_bone_shell`: меш челюсти строится по маске БЕЗ гейта, с замыканием и
заполнением полостей. Компоненты отбираются по ДОЛЕ от крупнейшей
(`BONE_SHELL_MIN_FRAC = 0.10`), а не фиксированным числом: у верхней челюсти
вторая по величине часть держит 15–17% объёма, выбрасывать её нельзя, а
мелкие осколки — шум. Работает на кропе по bbox: по всему тому замыкание
занимает минуты.

Маска для измерений остаётся гейтованной — правка касается ТОЛЬКО меша.

## Полоса заполнения у ползунков (фронт)

CSS не рисует заполненную часть `input[type=range]` сам — цвет задаётся
переменной `--fill`. Её выставлял ТОЛЬКО слайдер порога 2D, поэтому на
прозрачности, срезах зуба и MPR полоса стояла на месте (дефолтные 22%),
сколько бегунок ни двигай. Врач заметил это раньше нас.

Теперь `syncSliderFill` вызывается делегированным слушателем на document
(ловит и ползунки, созданные позже), MutationObserver задаёт начальное
положение динамически отрисованным, и он же вызывается вручную там, где
значение ставится программно — присвоение `value` события `input` не шлёт.

## Порог эндодонтии проверен на 499 чужих пульпах — но только с одной стороны

`FILLED_DIFF_HU = 300` стоял на 51 зубе трёх пациентов с одного аппарата.
Проверка на Pulpy3D (96 томов с эталонной разметкой пульпы, скачивается через
`kagglehub.dataset_download("gingeryy/pulpy3d")` БЕЗ ключа и аккаунта):

```
1212 пульп, 91 том (весь набор)
перцентили: 1%=-1175  25%=-854  50%=-688  75%=-487  95%=-237  99%=-36
выше порога 300: НИ ОДНОЙ, самая высокая +10
```

Выборка в 24 раза больше исходной (1212 против 51 зуба), и порог не задет ни
разу: до него не дотягивает даже самая плотная живая пульпа во всём наборе.

**Что это подтверждает: специфичность.** Ложных «канал пролечен» нет ни одного
на 1212 живых зубах — против 45 в исходном замере. Порог не трогаем.

**Гоча замера:** скрипт сперва объявил распределение двугорбым и потребовал
пересмотра порога — «второй горб» состоял из 10 пульп при выборке 1212, то
есть был шумом хвоста. Теперь второй горб засчитывается только при доле от
2% выборки. Правило общее: на большой выборке любой хвост выглядит горбом,
если не требовать от него значимости.

**Чего эти данные проверить НЕ МОГУТ, и это надо понимать:** пролеченного зуба
в наборе с разметкой пульпы нет ПО ПОСТРОЕНИЮ — канал заполнен пломбировочным
материалом, пульпы там нет, размечать нечего. Положительного класса не
существует, поэтому чувствительность по-прежнему держится на шести пломбах
client2/client4. Это не недоработка проверки, а свойство любого набора,
размечающего пульпу.

**Гоча метода: масок ЗУБОВ в Pulpy3D нет**, а наш способ сравнивает пульпу с
дентином того же зуба. Дентин взят КОЛЬЦОМ вокруг пульпы (дилатация на 3
вокселя минус сама пульпа) — оно лежит внутри того же зуба по построению.
Способ сверен с нашим на 60 зубах client2/4/5: вердикт совпал у 60 из 60,
корреляция 0.982. Без такой сверки числа на чужих данных не значили бы ничего.

**Гоча данных: у Pulpy3D потеряны метаданные о вокселе** — везде записан
1.0 мм при реальных ~0.3. Миллиметры оттуда брать нельзя; порогу это
безразлично, он в единицах плотности.

## Совмещение скана и КЛКТ: точность ИЗМЕРЕНА, но пациента метод не узнаёт

Взяты 289 пар «КЛКТ + скан одного пациента» (figshare 26965903, CC BY 4.0) —
в проекте было записано, что таких пар нет и точность измерить нечем.

**Итог на 20 парах, впервые за проект настоящие числа:**

```
                 медиана по зубам      разброс
свои пары            1.82 мм         0.28 .. 4.45
чужие (контроль)     1.74 мм         0.77 .. 7.64
```

Совмещение РАБОТАЕТ: лучшие пары дают 0.28 мм при вокселе КЛКТ 0.25 мм.
**Но пациента метод не узнаёт совсем:** медиана на ЧУЖИХ парах оказалась даже
НИЖЕ, чем на своих. Дуги у разных людей слишком похожи, ICP садится на чужую
почти так же охотно.

Зато выяснилось, что порог `GOOD_TOOTH_MM = 0.5` работает как ЗАЩИТА, и это
проверено:

```
порог     своих принято    чужих ошибочно
0.5 мм        25%               0%          <- текущий
1.0 мм        30%              20%
2.0 мм        65%              55%
3.0 мм        90%              85%
```

Ни одна из 20 чужих пар порог не прошла. Цена — три четверти верных
совмещений тоже отбраковываются. Это осознанный размен: принятое совмещение
можно показывать врачу, непринятое означает «не проверено», а не «неверно».
Ослаблять порог нельзя ни на шаг: уже при 1.0 мм чужие проходят.

**Практический вывод: проверять тождество пациента этой метрикой нельзя.**
Совмещать — можно; убеждаться, что скан и КЛКТ от одного человека, надо
другим способом, а не остатком ICP.

### Отпечаток зубного ряда тоже не подходит (`ios_cbct_identity.py`)

Проверены три признака, которые совмещение НЕ выравнивает, потому что они не
про положение, а про состав и размеры ряда. Замер на тех же 20 парах:

```
признак                медиана свои / чужие     AUC
шаг дуги                   0.34 / 0.58 мм      0.718
состав ряда (Жаккар)       0.92 / 0.89         0.578
размер зуба                0.30 / 0.37 мм      0.468
шаг + размер вместе                            0.671
```

Сигнал есть только у шага дуги, и он слабый: при пороге 0.3 мм принимается
40% своих ценой 5% чужих, при 0.4 мм — 70% своих ценой уже 35% чужих.
Комбинация признаков хуже лучшего из них по отдельности.

**Оговорка, важная для клиники:** состав ряда почти не работает по конкретной
причине — у всех пациентов набора figshare 26965903 ПОЛНЫЕ ряды по 28 зубов
(возраст 19-28 лет). Различать таких людей по составу нечем. У пациентов
клиники, где есть удалённые зубы, импланты и коронки, признак должен работать
заметно лучше, но на этом наборе проверить нельзя. До тех пор тождество
подтверждается по карточке, а не расчётом.

### По дороге починена канонизация сканов

Первый прогон дал 6–11 мм и полное перекрытие групп. Причина была не в
совмещении, а раньше — в ориентации:

* **Кандидатов было четыре — развороты на 180°.** Они покрывают только случай,
  когда вертикаль скана уже совпала с осью Z. У сканов figshare вертикаль
  лежит по оси Y, нужен поворот на 90°, которого в списке не было: выбирался
  лучший из заведомо неверных. Теперь вертикаль определяется геометрически
  (у челюсти она самая короткая ось: доля от средней 0.40 при максимуме 0.64
  на 16 сканах датасета и нашем), а кандидаты строятся вокруг неё — восемь
  штук, все с определителем +1. Результат: **28 зубов вместо 22.**

* **Поворот вокруг вертикали ничем не ловился.** Дуга остаётся дугой,
  `arch_score` и `chirality` к нему слепы. ДВЕ ПОПЫТКИ ПРОВАЛИЛИСЬ, и обе по
  одной причине — они опирались на метки сети, а сеть переприсваивает их под
  каждый поворот заново: направление «к резцам» давало +0.91..+1.00 у всех
  восьми кандидатов, отношение размеров «задние к передним» держалось около
  1.67 независимо от поворота. Работает только признак, вообще не касающийся
  меток: **подкова открыта назад**. Асимметрия облака вдоль оси перед-зад
  положительна у 100% из 60 сканов Teeth3DS (медиана +0.23), и она же вдвое
  сокращает перебор — половина кандидатов отсеивается без прогона сети.

### Проверка на регрессию: клинический скан не пострадал

Правки канонизации проверялись на чужих данных, поэтому клинический кейс
пересобран отдельно и сверен с резервной копией:

```
                     было      стало
зубов                  30         30
резцы-моляры    +1.4,+2.8,+30.3   +1.2,+2.8,+30.3
лево-право     +38.0,+0.0,-4.6   +38.0,+0.0,-4.5
смещение центров зубов: медиана 0.023 мм, максимум 0.793 мм (зуб 38)
```

Максимум приходится на восьмёрку, где сегментация нестабильна и без правок.
Правило на будущее: расширяя канонизацию под новые данные, ОБЯЗАТЕЛЬНО
пересобирать клинический кейс в отдельный файл и сверять — он единственный,
по которому врач уже смотрел результат.

### Гоча, стоившая отдельного круга: геометрию поворачивать НЕЛЬЗЯ

Соблазн большой: раз сканеры кладут скан в разные оси, привести геометрию к
общей системе. Я так и сделал — и это была ошибка. **Канонизация считается
для каждой челюсти ОТДЕЛЬНО и даёт им разные матрицы** (у нашего клинического
скана верхняя получает разворот, нижняя — тождество). Повёрнутая геометрия
разваливает взаимное положение челюстей, а на нём держится вся карта
окклюзионных контактов.

Замер до и после отката на паре 001:

```
                          с поворотом    без поворота
зубов на чужой стороне      14 из 28        2 из 28
RMS совмещения               0.83 мм        0.27 мм
по зубам                     8.59 мм        0.28 мм
```

Ориентацию под КЛКТ ищет Kabsch при совмещении — ему произвольный поворот
скана не помеха, мешало только зеркало. Поэтому в `segment_full` поворот
применяется к облаку ДЛЯ СЕТИ и не применяется к экспортируемым вершинам.

## Зуб из двух частей: отсев кусков — по ЗАЗОРУ, а не по центроидам

Врач с приёма: «как зуб может состоять из двух частей». Причина была в нашем
фильтре, а не в модели. `_filter_tooth` принимал второй кусок, если расстояние
между ЦЕНТРОИДАМИ меньше 70 вокселей — это 22 мм. Замер по трём клиническим
кейсам: принимались куски с зазорами 2.3, 4.7, 6.3, 7.3, 10.1, 10.6, 12.8,
16.1 и 17.0 мм.

**Порог откалиброван по эталону, а не подобран.** ToothFairy3, 790 зубов с
разметкой: из двух кусков состоят ВСЕГО 2 зуба (0.3%), и зазор у них не
превышает 1.5 мм. То есть анатомически разорванный зуб — редкость, а разрыв на
сантиметр анатомией не бывает вовсе. Порог `TOOTH_GAP_MM = 2.0` покрывает
эталон с запасом и совпал с `COMPONENT_GAP_MM` трека сканов, где та же задача
калибровалась независимо (776 компонент на 30 сканах). Оговорка: эталонных
случаев всего три, поэтому «максимум 1.5 мм» определён слабо — 2.0 выбран как
согласие двух треков, а не как точная граница.

Результат: на client2 вместо семи «двойных» зубов остался один (зазор 1.5 мм),
на кейсе клиники — два (0.9 и 2.0 мм).

**Гоча по дороге:** сама маска рвётся у 15–24 зубов на кейс, и это НЕ наш
фильтр (проверено: `binary_opening(2)` добавляет разрыв всего у 0–2 зубов).
Мы всего лишь перестали показывать чужие куски как часть зуба.

## Пузырчатая поверхность зубов: виноват МАТЕРИАЛ, а не геометрия

Та же жалоба с приёма: «текстура как будто шарики лопаются». Проверены четыре
гипотезы о меше, все ОПРОВЕРГНУТЫ (замер на 8 зубах client4):

```
                                        площадь   объём   отход от маски
размытие маски 0.9 (как было)              100%     99%        0.31 мм
размытие 1.5                                93%     97%        0.44
поле расстояний вместо размытой ступеньки  113%    100%        0.31   ХУЖЕ
сглаживание Тобина (12 итераций)           100%     99%        0.33   без эффекта
упрощение до 7000 граней                   100%      —         0.31   не виновато
```

Сглаживание Тобина написано вручную (в trimesh 5.0.0 оператор сломан, см.
выше) — с проверкой, что строки оператора суммируются в 1. Оно не изменило
ничего: **ряби в меше нет, убирать нечего.** Поверхность после marching cubes
уже гладкая.

«Шарики» оказались бликами: реставрации рисовались с `metalness 0.85` и
`roughness 0.3`, то есть зеркалом, и в тёмной сцене коронки читались как капли
ртути. Стало 0.35 / 0.45; у зубов блеск тоже приглушён (0.35 -> 0.5), потому
что поверхность имеет рябь около 0.3 мм и резкий блик лепит из неё бугры.

**Остаточная бугристость — это форма самой маски.** Пост-обработка выжата
досуха, ровнее станет только с лучшей моделью сегментации.

## Материал зубов: «бетон» лечится НОРМАЛЯМИ, а не блеском

Врач: «как будто залили бетоном и забыли выровнять, а зубы на самом деле
немного скользкие». Это уже вторая жалоба на материал после «шариков» — и
причина оказалась не та, что в первый раз.

**Что было сделано неправильно.** После жалобы на «шарики» блеск зубов
приглушили (roughness 0.35 -> 0.5), потому что резкий блик подчёркивал рябь
поверхности около 0.3 мм. Это лечение симптома: рябь видна ГЛАЗУ через
нормали, а не через материал, и глушение блеска просто превратило зуб в
матовый камень.

**Как правильно.** Рябь убирается сглаживанием НОРМАЛЕЙ, а геометрия
остаётся нетронутой: силуэт, объём и границы — те же, по ним считаются
находки. `smoothNormals` усредняет нормаль по соседям через рёбра
треугольников, 2 итерации. Делается во вьюере, а не при экспорте: меши это не
трогает, значит не нужна пересборка кейсов и смена `POSTPROC_VERSION`.

**Материал теперь физический.** Эмаль — диэлектрик под плёнкой слюны, поэтому
у зубов `MeshPhysicalMaterial` с `metalness: 0` и `clearcoat`, а не
полуметаллический `MeshStandardMaterial`. Именно clearcoat даёт «скользкость»:
тонкий гладкий слой поверх матовой основы. Прежние `roughness 0.5` и
`metalness 0.05` размазывали блик по всей поверхности, отдельного отражения
не возникало вовсе.

**Ползунок «Блеск зубов» вместо одного правильного значения.** Вид эмали
зависит от освещения кабинета и от вкуса смотрящего, а проверить его на своей
стороне нельзя: расширение Chrome в этом окружении не открывает локальный
сервер (curl отдаёт 200, браузер — «не удаётся подключиться»). Ползунок
двигает две величины сразу — шероховатость эмали и гладкость лакового слоя,
потому что порознь получается либо пластик, либо мокрый камень.

**Как проверять правки фронта без браузера:** вырезать `<script>` из HTML и
прогнать `node --input-type=module --check`. На этом файле уже ловилась ошибка
дороже: функция, вставленная внутрь другой функции, не видна из места вызова,
и модуль падает целиком — а симптом выглядит как «пустая сцена без ошибок».
Плюс проверка баланса `<div>` регуляркой: разметка тут собирается строками.

## Версия меша — своя у КАЖДОЙ модели

`info` и находки в кейсе одни, а мешей три. Пока меш всегда строился заново,
хватало общей инвалидации по `info.postproc`. С переиспользованием готового
GLB этого стало мало: пересборка одной модели проставляет `info` ей, и меш
другой модели, собранный по прошлым правилам, выглядел бы актуальным и молча
уехал бы врачу. Теперь версия пишется на каждый меш (`c["meshes"][model]`),
`_load_persisted` сверяет её отдельно, а кейсы старого формата мигрируют по
правилу «верим `info`, но только для ЕГО модели».

## Переключение модели КЛКТ: меш больше НЕ пересобирается заново

`info` и находки хранятся по одному комплекту на кейс, а меши — по одному на
модель. Из-за этого возврат к уже посчитанной модели гнал `build_mesh` заново:
четыре минуты вместо сорока секунд на пересчёт находок. Теперь готовый GLB
переиспользуется — устаревшие всё равно удаляет `_load_persisted` при старте,
так что лежащий на диске файл заведомо соответствует текущей
`POSTPROC_VERSION`.

**Гоча рядом:** открытие `/cbct/<кейс>` БЕЗ модели в адресе означает модель по
умолчанию (`ours`), и если кейс последний раз считался другой моделью, находки
пересчитываются. Чтобы попасть в конкретную модель, ссылку давать с ней:
`/cbct/client4/tf3`.

## Совмещение скана и КЛКТ (`ios_cbct_register.py`)

У скана точная коронка без металлических артефактов, у КЛКТ — корни, кость и
нерв. Планирование идёт по обоим сразу.

**Это не слепой ICP.** С обеих сторон уже есть сегментация с номерами зубов,
то есть соответствие ИЗВЕСТНО: преобразование считается по парам одноимённых
зубов (Кабш), ICP остаётся уточнением. Слепой ICP на симметричной дуге любит
сойтись в зеркало — здесь такой развилки нет.

- **Пары центроидов нельзя брать целиком**: у скана только коронка, у КЛКТ
  коронка с корнем, и центр масс зуба на КЛКТ сидит глубже. С КЛКТ берётся
  коронковые 45% длины зуба.
- Отражение в `_kabsch` запрещено явно (`det` приводится к +1). На почти
  плоском наборе точек SVD легко даёт решение с определителем −1, и левая
  сторона садится на правую. Это уже третье место в проекте, где знак
  определителя решает всё.
- ICP отбрасывает 20% худших пар на итерации: у скана есть десна, у КЛКТ её
  нет вовсе, и эти точки тянут решение на себя.
- Матрица считается офлайн и кладётся к кейсу скана
  (`register_<кейс КЛКТ>.json`); на запрос ICP не вешаем.
- **ICP обязан сводить ПОВЕРХНОСТЬ с поверхностью.** Первая версия сравнивала
  сплошные облака вокселей, и ближайшим соседом для точки скана оказывался
  воксель ВНУТРИ зуба. Замер самопроверкой (client4, 5 сидов): ошибка сдвига
  доходила до 0.60 мм при вокселе 0.31 — то есть ICP УХУДШАЛ и без того точное
  совмещение по центроидам. С поверхностными точками — 0.001–0.004 мм.
- **Общему остатку ICP доверять нельзя, судим ПО ЗУБАМ.** Прогон на заведомо
  разных пациентах (client4 + скан batir): общий RMS вышел 1.02 мм — всего
  вдвое выше порога, потому что ICP отсекает 20% худших пар и промахи прячутся
  именно в них. Медиана по зубам в том же прогоне 4.47 мм, отдельные зубы 90.9
  и 109.6 мм. Дуги у разных людей похожи, и по общему числу метод «принял» бы
  чужого пациента. Критерия теперь два, главный — по зубам (`GOOD_TOOTH_MM`).
- **Пары «скан и КЛКТ одного пациента» у нас НЕТ**, поэтому настоящая точность
  не измерена и измерить её нечем. `--selftest` проверяет только математику.
  Копию «как есть» подсовывать бессмысленно: ICP сводит точку саму с собой и
  выдаёт ровный ноль (проверено — 0.000 мм на пяти сидах), поэтому «скан»
  портится шумом 0.05 мм, потерей 30% зубов и прореживанием точек. Результат:
  19 зубов из 27, RMS 0.071 мм, ошибка сдвига 0.001–0.004 мм, угла
  0.001–0.004°.
- Непринятое совмещение во вьюере показывается строкой «не принято» с числом,
  а не прячется — иначе пустой список читается как «сканов нет».

### Качество сегментации: что проверено и чем это НЕ лечится

Раздутые меши зубов на клиническом скане (у 44 габарит вдвое больше самого
зуба) разбирались отдельно. Итог: **это не свойство модели, а поведение на
чужом распределении**, и правилами оно не чинится.

- **Систематического перекоса у сети нет.** Замер на 60 тестовых сканах
  Teeth3DS (`ios_seg_bias.py`): полнота 0.938, точность 0.932, разница 0.006.
  Из лишнего 66% приходит с соседних зубов, 34% с десны — то есть ошибки
  живут на границах между зубами, как и ожидалось.
- **Усиленное голосование раздутие не убирает.** Удвоение раундов TTA с 7 до
  15 не изменило ничего: у зуба 44 раздутие 1.97 в обоих прогонах. Это
  уверенная ошибка, а не разброс выборки. Утроение (21 раунд) снимает один
  пограничный зуб из пяти — этот выигрыш взят, больше там нет.
- **Разброса между запусками НЕТ.** При фиксированном числе раундов разные
  сиды дают одинаковый набор проблемных зубов. Предположение о нестабильности
  оказалось неверным.
- **Отсев компонент здесь бесполезен**: у зубов 43 и 44 меш ОДНОСВЯЗНЫЙ,
  метка расползлась непрерывно, отсеивать нечего. Фильтр по расстоянию всё
  равно добавлен — он откалиброван на эталоне и помогает в других случаях, но
  на этом скане не срабатывает ни разу (проверено чистым A/B: площади
  совпадают до десятых).

**Вывод:** сплошное расползание метки на данных чужого сканера правилами не
берётся — правила калибруются на Teeth3DS, а там этой болезни нет. Нужны
клинические сканы для дообучения, а он у нас ровно один. Это тот же блокер,
что и с пародонтитом: упирается в данные от клиники, а не в алгоритмы.
Пока защита работает так: `mesh_quality` помечает такие зубы, и находки по
ним идут с пониженным доверием либо не идут вовсе (индекс Болтона).

### Ориентиры на зубе (3DTeethLand)

Разметка лежит в `research_ios/datasets/teeth3ds/landmarks/<jaw>/<пациент>/`,
340 файлов, ~30 500 точек. Координаты в системе самих сканов Teeth3DS: точки
лежат НА поверхности (медиана 0.06 мм), подгонять ничего не нужно. Привязки
точки к номеру зуба в разметке НЕТ — её даёт сегментация ближайшим зубом.

Что означает каждый класс — установлено замером положения на зубе (доли
габарита: вдоль дуги / наружу / вверх):

```
МОЛЯР            вдоль дуги  наружу  вверх   смысл
Cusp (4-5 шт)       0.40      0.52    0.86   вершины бугров
Mesial              0.89      0.40    0.69   контакт с передним соседом
Distal              0.11      0.39    0.62   контакт с задним соседом
FacialPoint         0.52      0.83    0.64   ЩЁЧНАЯ борозда (FA-точка)
InnerPoint          0.51      0.03    0.08   язычный край десны
OuterPoint          0.52      0.98    0.30   щёчный край десны
```

У резца Cusp нет вовсе, Mesial/Distal сидят у режущего края (0.89-0.96).

Зачем это нужно: класс по Энглю строится на мезиально-щёчном бугре верхней
шестёрки (`Cusp`, самый мезиальный и щёчный) против щёчной борозды нижней
(`FacialPoint`). Средняя линия — по `Mesial` зубов 11 и 21.

**ГЛАВНОЕ: ориентиры проверены и НЕ ПОМОГЛИ.** Гипотеза была такая: класс по
Энглю слаб потому, что считается по центроидам, а не по анатомическим точкам.
Проверка на 180 пациентах Bits2Bites её опровергла — по всем пяти сравнениям
стало хуже:

```
                     центроиды   ориентиры
II класс справа        0.761       0.669
III класс справа       0.719       0.640
II класс слева         0.778       0.651
III класс слева        0.832       0.724
средняя линия          0.677       0.564
```

Разбор показал, что измерение по ориентирам при этом КОНЦЕПТУАЛЬНО ВЕРНОЕ:

```
                   медиана I класса   разброс внутри I класса
центроиды, справа       -1.95                1.83
ориентиры, справа       -0.58                3.66
зазор II-III:  центроиды 4.74    ориентиры 4.72
```

База ушла к нулю — ровно как предсказывает анатомия (бугор стоит в борозде), и
полезный сигнал тот же. Но разброс внутри нормы вырос ВТРОЕ: ориентир — одна
точка, её положение считается в габаритах зуба и потому напрямую зависит от
границ сегментации, а центроид усредняет тысячи вершин и к тем же ошибкам почти
нечувствителен. Сигнал прежний, шум тройной — AUC падает.

**Вывод для планирования: узкое место не в определении измерений, а в
устойчивости сегментации.** Смещение центроида безвредно, его снимает
калиброванная база. Поэтому `landmark()` и таблица оставлены в модуле как
рабочий и проверенный инструмент, но в продуктовые измерения НЕ подключены.
Возвращаться к ним имеет смысл после того, как станет стабильнее сегментация
(меши зубов раздуваются до 2x, см. `mesh_quality`), либо усредняя ориентир по
нескольким зубам вместо одного.

**Грабли, уже оплаченные замерами:**
- **Наш способ «ближайшая точка двух поверхностей» контактный пункт НЕ даёт**:
  расхождение с разметкой 1.5-1.8 мм, и ограничение поиска верхней частью
  коронки почти не помогает (1.77 -> 1.50). Причина не в точности, а в
  определении: ближайшая точка — это всегда минимум расстояния, а индекс
  Литтла требует СОБСТВЕННУЮ точку каждого зуба, которая при повороте зуба
  как раз и уезжает. Правилом это не берётся.
- **Индекс Литтла меряется параллельно окклюзионной плоскости**, а не в 3D:
  разница высот у соседних зубов анатомическая. Учёт этого убирает 0.8 мм.
- **У индекса ненулевая база.** Даже в плоскости смыкания сумма по пяти парам
  даёт медиану 6.8 мм, и ни один пациент не попадает в норму — то есть база
  около 1.2 мм на пару. Та же ловушка, что с классом Энгля (норма −1.95 мм,
  а не ноль). Откалибровать базу НЕ НА ЧЕМ: разметки скученности нет ни в
  Teeth3DS, ни в Bits2Bites. Отдавать индекс врачу до этого нельзя.

### Карта окклюзионных контактов

`ios_occlusion_map.py` — слой находок для скана, устроен как `cbct_findings`
для КЛКТ: новых моделей нет, всё считается геометрией поверх готовой
сегментации. Для каждой вершины зуба берётся расстояние до поверхности зубов
противоположной челюсти; из него выходят и заливка во вьюере, и таблица
«зуб — зазор — площадь контакта — число пятен».

- Строится офлайн, кладётся в кейс как `occlusion.json` (~60 КБ), отдаётся
  через `/api/ios/occlusion/{case}`. На запрос расчёт не вешать: он занимает
  десятки секунд.
- Зазоры на вершину лежат в base64 по одному байту (сотые доли миллиметра,
  потолок 2.55 мм) — ключ `vertex_gap_b64`, имена совпадают с именами нод GLB.
  Вьюер раскладывает их в `BufferAttribute` цвета. **Порядок вершин обязан
  совпадать с GLB**: при пересборке `scan.glb` карту надо пересчитать, иначе
  длины разойдутся и раскраска молча выключится (во вьюере есть предупреждение
  в консоль).
- Расстояние считается до выборки в 600 тыс. точек, а не точным поиском по
  треугольникам (тот в trimesh занимает минуты на 70 тыс. вершин). Шаг выборки
  около 0.07 мм, поэтому зазоры завышены примерно на 0.03 мм — во вьюере
  поэтому дискретные полосы, а не плавный градиент.
- Признак «есть контакт» берётся по ПЛОЩАДИ, а не по минимальному зазору: одна
  вершина может подойти на 0.29 мм, при этом не соприкасается ни один участок
  поверхности. Врачу важно второе.
- Зуб без одноимённого антагониста (у batir это 38 и 48 при отсутствующих
  18, 28) в нарушения прикуса НЕ записывается — отсутствие контакта там
  ожидаемо. Проверять это надо до того, как называть зуб выключенным из
  окклюзии.
- Пороги (0.1 / 0.3 / 0.6 мм) — черновик, всё помечено `draft: True`.
  Проверяется копиркой на приёме: это единственная наша метрика, которую врач
  может подтвердить без разметки рентгенолога.

### Геометрия дуги и находки по скану

`ios_geometry.py` — общий фундамент (оси дуги, соседи, размеры зуба, качество
меша), `ios_findings.py` — находки четырёх специальностей (ortho, prostho,
perio, gnatho) -> `findings.json` -> `/api/ios/findings/{case}`. Вьюер сводит
их с картой контактов в одну панель по ролям врачей.

Грабли, каждая оплачена замером:

- **Вертикаль дуги — это PCA центров зубов, а не разница «верх минус низ».**
  Эталон — нормаль плоскости смыкания (её задают точки контакта). Отклонения:
  разница центров верх/низ **28.8°** (плечо всего 4 мм), «от десны к
  коронкам» **17.4°** (зависит от того, сколько нёба попало в скан), PCA
  центров зубов **0.8°**. Дуга плоская (0.03–0.04 на челюсть), поэтому
  перпендикуляр определяется устойчиво.
  **`ios_occlusion.build_frame` считал вертикаль первым способом — это и была
  причина провала измерений прикуса.** Проверено на 180 пациентах Bits2Bites
  (`ios_frame_validate.py`): AUC глубокого прикуса 0.573 -> 0.971, класса по
  Энглю 0.56-0.65 -> 0.74-0.81, средней линии 0.544 -> 0.692. Исправлено,
  вертикаль там теперь берётся отсюда. Мораль общая: прежде чем править
  определение измерения, проверять систему координат, в которой оно живёт.
- **Мезио-дистальный размер — между контактными точками, а не габарит зуба.**
  Сегментация цепляет к зубу посторонние лоскуты: у 44 габарит 14.0 мм против
  7.1 по контактам при норме 7.1. Отношение «габарит / контакты» оставлено как
  признак качества меша (`mesh_bloat`).
- **Линия дуги — сплайн по ПОРЯДКУ зубов, не парабола `fwd = f(lat)`.**
  Парабола не умеет повторять подкову: RMS отклонений 2.22 мм против 0.39 у
  сплайна, и она сама выдаёт клыки «вестибулярно», а резцы и моляры «язычно».
  На параболе выходили фантомные «скученность 19.5 мм» и семь зубов «вне дуги».
- **Дефицит места в мм не считаем.** Точность метода ±2–3 мм, столько же и сам
  дефицит. Настоящая мера — индекс Литтла по анатомическим контактным точкам,
  он появится с моделью ориентиров (`3DTeethLand`). Отдаём только RMS
  неровности ряда и зубы, выбитые из линии.
- **Высота до антагониста в дефекте НЕ ПРОВЕРЕНА.** Мерить надо строго по
  вертикали от гребня: свободное расстояние в 3D цепляется за щёчную десну
  преддверия и даёт 1.6 мм вместо 6–8. Гребень ищем в середине дефекта —
  у краёв стоят межзубные сосочки, они поднимаются почти до контактных пунктов.
  Проверить это на нашем пациенте нечем: у него нет удалённых зубов, а
  смоделированный дефект гребня не воспроизводит (в сетке на месте зуба дыра).
  Стоит защита: результат меньше 2 мм не сообщается вовсе.
- **Прикус считается в двух местах и ими не разъезжается.** Сами измерения
  живут в `ios_geometry.occlusion_measures`, а `ios_occlusion` (CLI по OBJ) и
  `ios_findings` (по кейсу из scan.glb) — только входы. Пути дают немного
  разные числа: точки зуба берутся либо прямо из сегментации, либо из
  очищенного меша, и смещение моляров расходится до 1.5 мм. Поэтому пороги
  проверены на ОБОИХ путях (`ios_frame_validate.py --pipeline raw|case`) —
  расхождение чувствительности и специфичности в пределах нескольких
  процентов, вывод по клиническому скану совпадает.
- **Пороги прикуса выбраны на СПЕЦИФИЧНОСТЬ ~90%, а не по максимуму
  разделения.** В скрининге ложная тревога дороже пропуска: врач всё равно
  смотрит пациента сам, а отчёт, тревожащий на каждом втором здоровом, он
  просто перестанет читать. Замер: пороги по максимуму Юдена оставляли
  нетронутыми лишь 54% пациентов I класса, выбранные — 80-85%.

      величина            чувствительность / специфичность
      глубокий прикус          92-93% / 89-92%
      открытый прикус             95% / 85-86%
      II класс                 52-62% / 90-92%
      III класс                44-53% / 86-95%
      средняя линия            46-54% / 80-82%

  Класс по Энглю формулируется как «похоже на II класс», а не как диагноз:
  измерение по центроидам зубов — ориентир. Настоящий класс строится на
  ориентирах (мезиально-щёчный бугор против щёчной борозды) и появится с
  моделью точек (3DTeethLand).
- **Рецессия — только через асимметрию с одноимённым зубом.** Абсолютная длина
  коронки у людей разная; у здоровых пар расхождение 0.0–0.6 мм (16/26: 6.60
  против 6.61), поэтому порог 1.5 мм заведомо выше разброса метода.
- **Фасетка стирания = плоскость И контакт одновременно.** По отдельности не
  значит ничего. Отличить стирание от анатомии по одному скану нельзя —
  отдаём измеренную площадку, а не диагноз.
- Зуб, не прошедший `mesh_quality` (тонкий обрывок, раздутый меш, площадь
  сильно меньше парного), в находки не идёт или идёт с пониженным доверием.
  Индекс Болтона при таком зубе не считается вовсе — ошибка ушла бы в план.

Модель — DGCNN-подобная на чистом PyTorch (граф соседей через `cdist`+`topk`):
`torch_geometric`/`torch_cluster`/sparse conv под torch 2.11+cu128 не ставить,
готовых сборок нет. Классов 17: 0 десна, 1–8 правая сторона, 9–16 левая;
челюсть известна из имени файла, обратно в FDI — `pos_to_fdi`.

Чекпойнты в `research/output/ios_runs/`: **dgcnn_v2** (mIoU 0.9366) и
**dgcnn_v3** (0.8762, но устойчива к сдвигу). `dgcnn_v1` — затёртый смоук-тест,
не использовать.

### Гоча IOS

- **Ориентация — главная ловушка.** Teeth3DS хранит челюсть коронками ВВЕРХ,
  Exocad и Bits2Bites — анатомически (верхняя коронками вниз). Разница 180°.
  Без канонизации центральный резец пропадал на **25 сканах из 25**; с ней —
  0 из 25, дуга собирается на 24 из 25. Всегда прогонять `canonical_transform`
  перед инференсом. Проверять надо не «какая ось короче», а **куда направлена**.
- **Перестановка осей при экспорте: проверять определитель.** Перевод Z-up →
  Y-up для three.js писался как `verts[:, [0, 2, 1]]` — это транспозиция двух
  осей, определитель **−1**, то есть зеркало, а не поворот. Модель уходила в
  отражение (зуб 11 вставал на место левого резца), нормали выворачивались
  внутрь: замер на скане клиники — объём +5983 мм³ до и −5983 мм³ после.
  Во вьюере это не видно, потому что материалы стоят `DoubleSide`. Правильно —
  `(x, z, −y)`, определитель +1; общий помощник `ios_canonical.to_viewer_axes`,
  использовать его в обоих сборщиках. В КЛКТ (`cbct_backend.build_mesh`)
  перестановка `[2, 0, 1]` циклическая, определитель +1 — там ошибки нет.
  На глаз обе выглядят одинаково безобидно, различает их только определитель.
- **`predict_scan` не сеет ГСЧ** (`np.random.permutation` по кускам), поэтому
  две сборки одного скана дают слегка разную сегментацию. В `ios_build_mesh`
  выставлен `np.random.seed(0)`; если кейс надо пересобрать байт-в-байт —
  не убирать. Кейс во `web_cases` — клинический артефакт, а не черновик.
- **Аугментация поворотами только ±20°.** Шире — сеть перестаёт отличать левое
  от правого (та же беда, что с парными структурами на КЛКТ).
- **Аугментация сдвигом ±10 мм обязательна.** Без неё сеть запоминает
  абсолютные координаты: v2 падает с 98.7% до 56.5% при сдвиге на 10 мм,
  v3 держит 96.9%. Проверяется `ios_shift_test.py`.
- **Центровать `robust_center` (2–98%), не средним** — среднее тянется за
  выбросами: расхождение до 4.8 мм на клиническом скане.
- **OBJ с текстурой дублирует вершины по швам развёртки.** У клинического
  скана 20 462 дубля, поверхность разрезана на 1205 топологических кусков,
  и связность рассыпается. `trimesh.merge_vertices()` их НЕ сливает (бережёт
  UV) — сливать по округлённым координатам вручную.
- **Упрощать челюсть целиком ДО разрезания на зубы.** Если резать первым, а
  упрощать части по отдельности, границы расползаются и налезают друг на друга.
- **Отсев кусков зуба — по РАССТОЯНИЮ, а не по размеру** (`COMPONENT_GAP_MM`).
  Замер по 776 вторичным компонентам на 30 сканах Teeth3DS с эталоном: у своих
  кусков зазор до основного тела медиана 0.23 мм, у чужих 2.28 мм. Порог 2.0
  убирает 55% чужих ценой 9% площади вторичных компонент; основное тело зуба
  не трогается никогда.
- **Не оставлять только крупнейшую компоненту зуба** — съедало до 70%
  поверхности (зуб 11: 1612 граней → 490). Всё, что не ушло в зуб, обязано
  достаться десне, иначе в сетке остаются дыры.
- **Официальное разбиение Teeth3DS — по сканам, а не по пациентам**: 382
  пациента попадают и в train, и в test (верх в обучении, низ в тесте).
- **Bits2Bites и Bite2Text не содержат разметки зубов** — только оценка
  прикуса на пациента (CSV) и текстовые заключения. Обучать сегментацию на них
  нечем; годятся для проверки и для самообучения по псевдоразметке.

## Стороны разворачиваются В ДАННЫХ, а не во вьюере (галочки больше нет)

Врач восемь раз повторил, что стороны неправильные, и трижды я «чинил» не то.
Развязка: зеркальна была **сама геометрия**, а не нумерация. Пока разворот
жил во вьюере галочкой «зеркальный вид», правильную картинку видел только
тот, кто её включил, — а находки, план лечения, PDF-отчёт и срезы оставались
зеркальными, потому что считаются на сервере.

Теперь разворот применяется ОДИН раз, на входе, к тому и маске сразу
(`apply_scanner_mirror` в `cbct_backend`), вместе с номерами зубов, пульпами и
парными структурами. Конвенция хранится по аппарату в
`research_3d/scanner_sides.json` и подтверждается врачом однократно: оба
аппарата клиники (Dentium rainbowCT и brightCT) пишут позицию пациента
заглушкой (0,0,0), поэтому определить сторону из файла нельзя в принципе.

**Галочка из интерфейса убрана, `fdiShown`/`fdiData` стали тождественными.**
Оставлять её было опасно вдвойне: включённая поверх исправленных данных она
даёт ВТОРОЕ зеркало, то есть снова неверные стороны. Ключ `mirrorOverride`
чистится из localStorage при старте страницы.

**Гоча, вскрывшаяся сразу после: сравнивать наборы зубов можно только в
ОДНОЙ системе номеров.** `cbct_selfcheck` брал маску модели без разворота, а
обработанную — уже с ним, и на client2 отрапортовал «фильтр съел 5 зубов»
(24, 26, 38, 45, 46). На деле ровно те же пять появились под зеркальными
номерами (14, 16, 48, 35, 36), а всего зубов как было 25, так и осталось.
Ложная тревога инструмента опаснее молчания: она маскирует НАСТОЯЩУЮ потерю
зубов, ради которой скрипт и написан. Проверка сама должна проходить тот же
путь, что и данные.

**Мораль, которая стоила дороже всех:** проверка была циклической. Я сверял
стороны правилом правой тройки по той же матрице ориентации, которая и была
источником ошибки, — на зеркальной модели такая проверка возвращает
зеркальный ответ и всегда «подтверждает». Разорвать круг смог только врач,
открывший тот же снимок в стороннем вьюере.

## Симметрия дуги: измерение есть, «идеальной дуги» не существует

Рентгенолог показал то, чего мы не считали: у здорового ряда правая половина
совпадает с зеркальной левой. Наша «неровность ряда» отвечает на другой
вопрос — насколько зуб выбился из ПЛАВНОЙ линии; ряд может быть гладким и при
этом перекошенным целиком.

`ios_geometry.arch_symmetry` берёт одноимённые пары зубов, отражает левый
через среднюю линию и раскладывает расхождение на две части: ПОПЕРЁК (перекос
ряда) и ВПЕРЁД (разворот дуги). Меряется по центрам зубов — центр усредняет
тысячи вершин и потому устойчив к неточностям сегментации, ровно по той же
причине, по которой класс Энгля считается по центроидам, а не по ориентирам.

**Порог взят из СВОЕЙ базы, а не из литературы** — четвёртый раз подряд, и
снова не зря. Замер на 220 сканах Teeth3DS:

```
                   50%    75%    85%    90%    95%
медиана по скану   0.73   1.32   1.89   3.32   4.13   мм
худшая пара        1.66   2.65   4.54   6.37   7.77   мм
```

Порог по 90-му перцентилю (специфичность ~90%, как на прикусе). Находка
отдаёт миллиметры И место в выборке, а степень называется от выборки («выше
нормы»), а не клинически: разметки ортодонта у нас нет.

**Гоча при калибровке:** в `teeth3ds_npz` координаты НОРМАЛИЗОВАНЫ (ключи
`center` и `scale`), и первый прогон дал медиану 0.01 — «идеальную симметрию»
у всех подряд. Пороги в условных единицах выглядят как обычные числа и
молча врут; восстанавливать миллиметры обязательно.

Линия во вьюере (`arch_ideal_line`, тумблер «Симметричная линия дуги» и
`?arch=1` в адресе) строится по симметризованным парам и потому проходит
через реальные зубы пациента. Это НЕ «как должно быть у здорового»: такой
эталон потребовал бы нормы, которой нет. Это ответ на вопрос «как выглядел бы
ЭТОТ ряд, будь он симметричен». Линия только по парам — непарный зуб задавал
бы одну сторону и лишил бы линию симметрии, ради которой она и строится.
Проверка на клиническом скане: линия отходит от центров зубов на 0.5 мм при
отклонениях отдельных зубов до 1.6 мм — то есть показывает именно асимметрию,
а не ошибку построения.

## Язык интерфейса: русский по умолчанию, каракалпакский переключателем

`demo_static/i18n.js` — один словарь на оба вьюера (статика обеих страниц
отдаётся из `demo_static`, поэтому копий не заводим). Переключатель РУС/QQ в
шапке, выбор живёт в localStorage, плюс `?lang=kk` в адресе — ссылку врач
пересылает целиком, и получатель должен увидеть тот же язык.

**Переводится обвязка, а НЕ клинический текст** — это решение, а не
недоделка. Находки приходят с сервера собранными строками с числами и
порогами («расстояние корень → канал 1.2 мм, контакт ≤0.5»); их перевод — это
перевод заключения, а не интерфейса, и неточный термин в диагнозе опаснее
непереведённого. Документация клиники и план лечения ведутся на русском.

Каракалпакский набран латиницей и **требует вычитки носителем**: анатомические
термины взяты по аналогии с казахским и узбекским. Правится прямо в словаре.

Две грабли фронта, обе уже сработали:
- **Нельзя вешать `data-i18n` на `<label>` с `<input>` внутри**: перевод идёт
  через `textContent` и снёс бы сам чекбокс. Текст оборачивается в `<span>`.
- **Обёртка ради перевода наследует стили родителя.** `<h2>` красит вложенный
  `span` акцентным градиентом — новый span сделал весь заголовок цветным.
  Отсюда класс `.plain`.
- Текст в разметке переносится по строкам, в словаре ключ записан одной
  строкой: сравнение идёт по схлопнутым пробелам, иначе перевод молча
  отключается, а заметно это только глазами.

## Слой находок упирался в ОДНУ строку: полный SVD

Кейс client3 (аппарат brightCT, воксель 0.2 мм) считался больше часа, тогда
как кейсы с вокселем 0.31 мм — пять-семь минут. Списать это на «том больше»
было легко и неверно: вокселей в нём всего втрое больше.

Профилировщик (`cProfile` по `compute_findings`, client4) показал точное
место: из 466 с **180 с уходило в `numpy.linalg.svd`** — 64 вызова по 2.8 с,
все из `cbct_perio.tooth_axis`, где считается главная ось зуба.

Причина — значение по умолчанию `full_matrices=True`: numpy строит матрицу U
размера N x N, где N это число ВОКСЕЛЕЙ зуба, хотя нужен только первый из
трёх правых сингулярных векторов. Замер на синтетике:

```
вокселей   полный svd   full_matrices=False   расхождение оси
   5 000      0.21 с          0.0004 с             0.0 град
  30 000      9.24 с          0.0010 с             8.5e-07
 120 000    MemoryError       0.0010 с                —
```

То есть на крупных зубах старый вариант не просто медленный — он падает по
памяти. Именно поэтому болезнь вылезла на кейсе с мелким вокселем: там
зубы дают в разы больше вокселей.

Результат после правки: client3 пересобран **за 488 с вместо часа с лишним**,
находки на client4 совпали 8 из 8 (A/B со старым файлом).

Заодно `cortical_wall_fraction` переведена на кроп: она вызывается на каждый
нижний зуб и каждый раз считала два `distance_transform_edt` по ВСЕМУ тому,
хотя кольцо стенки имеет толщину около миллиметра.

**Правило:** `np.linalg.svd` на облаке точек всегда с `full_matrices=False`.
Проверено и исправлено также в `ios_geometry` и `ios_frame_validate`; в
`ios_cbct_register` матрица 3x3 (Кабш) — там полное разложение дёшево.

**Мораль:** прежде чем объяснять медленность свойствами данных, запустить
профилировщик. Гипотеза «том больше — считает дольше» звучала разумно и
увела бы в оптимизацию не того места; настоящая причина была в одном
аргументе по умолчанию.

## Аппарат терялся у КАЖДОГО загруженного кейса

`import_upload` читал метаданные аппарата строкой `read_scanner(names[0])`,
стоявшей ПОСЛЕ `shutil.rmtree(raw)` — то есть после удаления распакованных
срезов. Файла к тому моменту уже не было, `read_scanner` ловил исключение и
возвращал пустой словарь. Молча.

Проявлялось только на кейсах, загруженных через демо: у client2..client5
поле `scanner` заполнено с прошлых прогонов, и по ним всё выглядело
исправным.

**Последствие тяжелее, чем пустая строка в панели.** Без производителя и
модели не находится подтверждённая конвенция сторон
(`scanner_sides.json` хранит правило НА АППАРАТ), зеркало не применяется, и
номера зубов уезжают на чужую сторону. Замер на архиве client2
(Dentium rainbowCT, теги в файлах на месте): аппарат «неизвестен», зеркало
False, стороны не подтверждены — при том что для этого самого аппарата
правило врачом подтверждено.

Мораль та же, что и с проверкой, питающейся источником ошибки: сбой был
тихим, а признак его — не ошибка, а пустое поле, которое легко принять за
особенность конкретного снимка.

## Толщина мягких тканей: РАБОТАЕТ, но на пределе разрешения

Первое измерение, которое даёт только совмещение скана с КЛКТ: скан видит
десну и не видит кость, КЛКТ видит кость, а мягкие ткани на нём почти не
отличаются от воздуха. Разница двух поверхностей и есть толщина.
`ios_cbct_soft.py`. На клиническом кейсе: 0.7–1.0 мм у передних верхних,
2.3 мм у 17-го.

**Главная оговорка: погрешность совмещения (0.51 мм на верхней челюсти,
0.71 на нижней) СОПОСТАВИМА с измеряемой величиной.** Поэтому всё тоньше
этого порога отдаётся как «тоньше 0.51 мм», а не числом: метод различает
толстую и тонкую десну, но десятых долей миллиметра не даёт. Тот же принцип,
по которому пародонт отдаёт перцентиль выборки, а не стадию.

Четыре ошибки, каждая найдена замером и стоила отдельного круга:

- **Меряли всю десну подряд** — нёбо (слизистая там законно 3–7 мм) и щёчную
  складку. Медиана выходила 5.8 мм. Зона ограничена местом, где биотип и
  смотрят: у шейки, вестибулярно.
- **Зона и толщина считались в РАЗНЫХ системах координат** — до «ближайшей»
  точки десны получалось 70 мм. Пятый случай той же природы в проекте.
- **Порог «это кость» брали из литературы** (300 HU). Шкала КЛКТ не
  количественная: замер дал кость 1770 (медиана) против мягких тканей до 180,
  и порог 300 попадал в шум — ему соответствовало 45% точек прямо на
  поверхности десны. Стоит 500, в разрыве.
- **Требовали, чтобы кость лежала в маске челюсти.** Маска не покрывает
  альвеолярный гребень вовсе: на глубине 0–3 мм от десны в неё попадает 0%
  точек.

Плюс шейка зуба определяется НЕ формулой по оси, а по факту — там, где к зубу
прилегает десна: замер показал, что правило «у верхних сверху, у нижних снизу»
на реальных данных не выполняется.

## Высота и ширина кости под имплант: НЕ ДОВЕДЕНО

`cbct_bone_site.py` помечен в самом файле как недостоверный. Высота до
нижнечелюстного канала выходит 31–64 мм при клинических 12–18. За десять
итераций каждая исправленная ошибка вскрывала следующую — это признак того,
что подход неверен в основе: меряем в объёме, а надо на СРЕЗЕ вдоль оси
будущего импланта, как это делает врач линейкой.

Что выяснено по дороге и останется верным при переделке: гребень не ищется по
маске челюсти (она его не покрывает); на КЛКТ рот закрыт, и кость непрерывна
между челюстями, поэтому поиск вверх уезжает в чужую челюсть; канал идёт не
под зубом (смещение 6.3 мм на позиции 46); позицию отсутствующего зуба надо
брать по дуге ряда, а не экстраполяцией от соседа; пазухи у моделей
ToothFairy3 размечены на десятую часть объёма, и мерить по ним нельзя —
нужна `pretrained`.

## Что просил врач с приёма и что из этого выполнимо (проверено ресёрчем)

После визита в клинику пришёл список: MB2, тип кости D1-D4, пазухи, нервы,
ВНЧС, ортодонтия — по КЛКТ; кариес, пульпит, периодонтит, ре-эндо, корни,
пародонтит со степенью — по ОПТГ. Проверено по литературе и по тому, что
делает Diagnocat (его официальная инструкция для регулятора плюс боевой код
приложения). Итог: **половины этого нет и у Diagnocat**, а часть невозможна
по разрешению.

### Что упирается в ДАННЫЕ, а не в алгоритм

Итог после проверки всех пунктов по первоисточникам: **невыполнимых по
алгоритму пунктов не осталось.** Осталось три вида ограничений, и ни одно из
них не снимается выбором модели:

1. **Чего нет в кадре** — ВНЧС: сустав лежит выше поля зрения наших снимков.
   Снимается протоколом съёмки, не архитектурой.
2. **Чего нет в разметке** — пазухи (эталон ToothFairy2 сам содержит 1.6 см³
   вместо 15), дентикли. Снимается своей разметкой.
3. **Чего нет в модальности** — пульпит как ДИАГНОЗ и число каналов на 2D:
   плотность воспалённой пульпы не отличается от здоровой, а каналы верхних
   моляров на панораме накладываются физически. Снимается другим входом
   (жалобы пациента для пульпита — с ними 96-98%; прицельный снимок или КЛКТ
   для каналов), а не другой сетью.

Ниже — пункты с оговорками, каждый со своей.

- **MB2: «нельзя» было СЛИШКОМ КАТЕГОРИЧНЫМ — поправка по первоисточникам.**
  Верно, что канал 0.24 мм при вокселе 0.31 мм и что разрешение решает: одни
  и те же зубы дают 72% на обычном КЛКТ, 92% на супер-разрешении и 100% на
  микро-КТ (Ji 2024). Но 72-92% на ОБЫЧНОМ КЛКТ достижимы, и вот таблица
  работ (обзор Attahadi 2026):

  ```
  Duman 2024     YOLOv5x                        чувствительность 92%
  Shetty 2025    Inception v3 + SVM                             92.5%
  Altunkum 2026  —                                96.6% / спец. 99.4%
  Lin 2026       VGG16 + ConvNeXt-Transformer      84% / 86%, AUC 0.9
  Albitar 2022   3D U-Net                           80% / спец. 98%
  Güllü 2026     nnU-Net v2                        53.8%, AUC 0.80
  ```

  **Решает ПОСТАНОВКА, а не модель.** Высокие числа дают КЛАССИФИКАТОРЫ
  аксиального среза («есть ли MB2 на этом срезе») — им не нужно разрешать
  канал, они ловят косвенные признаки плотности. Единственная работа на
  nnU-Net v2, то есть на нашем инструменте и с нашей постановкой
  (сегментация), — ХУДШАЯ в таблице: 53.8%.

  Вывод: сегментацией канала не берётся, классификацией берётся. Делать надо
  отдельный классификатор по срезам мезиально-щёчного корня, а не ждать
  снимков ≤0.125 мм. Прежняя запись «не браться» отменяется.
  **Как это решает Diagnocat:** не детектором, а типизацией корней
  (M/MB/MB2/ML/D/DB/DL/P), к которой привязываются очаги. Врач видит
  «3 корня, 4 канала». Надёжность низкая и у них: чувствительность
  «4 канала» 0.654, «4 корня» 0.0 — эти градации из заявленного списка убраны.
  То есть **наш отрицательный вывод по корням и каналам совпадает с их же
  цифрами.**
- **Тип кости D1-D4: нельзя ЧУЖИМ порогом, можно СВОИМ измерением.**
  Поправка по первоисточникам — исходная формулировка «нельзя» была слишком
  широкой.

  Что подтвердилось: абсолютные значения переносить нельзя. Ошибка после
  перекалибровки 35..1562 на 13 аппаратах — шире всего диапазона D1-D4;
  значение плывёт от поля зрения, укладки, металла ВНЕ кадра и даже от
  программы просмотра. Обзор PMC4075265 заключает то же и рекомендует
  «калибровку и ВНУТРЕННИЕ РЕФЕРЕНСЫ вместо абсолютных значений» — то есть
  ровно то, что уже сделано в `cbct_bone_quality` (порог от медианы дентина
  этого же скана).

  **Что опровергает категоричность — измерение клинически работает.**
  PMC12156841, 118 имплантов у 73 пациентов на ОДНОМ аппарате: корреляция
  плотности с моментом введения импланта **r = 0.927** (p = 0.001); у
  шести неудачных имплантов плотность 359 против 702 у успешных. И значения
  по зонам сами ложатся в диапазоны Миша: передняя нижняя 816 (D2), передняя
  верхняя 567 (D3), задняя верхняя 337 (D4).

  **Это ровно тот порядок, который получил наш BV/TV** (низ фронт 0.95,
  верх фронт 0.86, верх жеват 0.72) — две независимые меры воспроизводят
  один анатомический градиент. То есть мера верна, а непереносим только
  абсолютный порог.

  **Путь к настоящей калибровке существует.** QCBCT-NET (PMC10366160):
  Cycle-GAN + U-Net на 7500 парных срезах КТ/КЛКТ 30 пациентов, эталон —
  количественная КТ с фантомом гидроксиапатита. Результат R² 0.85,
  корреляция 0.92, ошибка 8.3% — против R² 0.24 и ошибки 54% у обычной
  калиброванной КЛКТ. Требует парных снимков КТ+КЛКТ с фантомом.

  Классификация обучением тоже делается: Nested-UNet на 5 классов плотности,
  70 пациентов, Dice 0.75 (PMC9329319) — но эталоном там служат сами HU с
  КЛКТ, то есть методологически это слабее, и авторы отмечают отсутствие
  проспективной клинической проверки.

  **У Diagnocat такой находки нет вообще** (ни HU, ни Misch, ни Lekholm) —
  это по-прежнему верно.

  Практический вывод для нас: BV/TV оставляем как основную меру (протокол-
  независима, +5% при переносе), но **можно добавить и плотность в единицах
  своего аппарата** — она предсказывает момент введения, а клиника у нас
  одна и аппарата два, то есть база строится на своих снимках. Чего делать
  нельзя — называть результат «D3» по чужим порогам.
- **Пульпит по 2D.** Диагноз ставится по боли и тестам чувствительности;
  сами тесты против гистологии дают 62-78%. Модель училась бы на метке,
  ошибающейся на треть. У Diagnocat кода `pulpitis` нет.
- **Полная стадия пародонтита по классификации 2018.** По определению самой
  классификации требует зондирования, потери прикрепления и ПРИЧИНЫ утраты
  зубов. Со снимка стадия систематически занижается. У Diagnocat тоже нет —
  только mild/moderate/severe.
- **Число каналов по 2D.** Работ не существует вовсе; задача признана
  нерешаемой. Согласуется с нашим выводом по КЛКТ.

### Делать — база есть

- **Структура кости вместо плотности.** Стабильность импланта предсказывает
  не плотность, а доля костной ткани в объёме: BV/TV даёт R² 0.61 против
  0.39 у плотности, обгоняя момент вкручивания (0.50) и ISQ (0.38). Ключевое
  для переносимости: BV/TV и площадь кортикала при переходе микро-КТ -> КЛКТ
  смещаются на +5% и -0.3% и НЕ зависят от напряжения съёмки, тогда как
  толщина трабекул уезжает на +65%, а расстояние между ними на +43..54%.
  Обе величины считаются геометрией по нашей маске. Класс кости — только
  двумерный (толщина кортикала x плотность губчатой, Wang 2023), а не одна
  буква.
- **Пазухи.** Сегментация воздуха решена (Dice 0.92-0.97), расстояние до
  корня автоматизируется с ошибкой 0.63 мм, утолщение слизистой считается
  вычитанием воздуха из пазухи (Dice 0.875). Порог 2 мм замерить на своей
  выборке: в литературе при одном пороге получают от 15% до 73%.
- **Убыль кости в процентах длины корня по 2D** — то же измерение, что уже
  работает в `cbct_perio`, ICC с врачами 0.81-0.91. Мерить надо именно в
  долях длины корня, а не в мм: у ОПТГ увеличение неравномерно.
- **Фуркации нижних моляров** — 92-98%. У верхних фуркация перекрыта нёбным
  корнем.
- **Объём периапикального очага в мм³** — у Diagnocat это ЕДИНСТВЕННОЕ
  числовое свойство находки, всё остальное категориально. У нас на КЛКТ
  считается той же геометрией.
- **Дентикли.** Diagnocat их выдаёт (`Pulp stone` в официальном списке).
  Значит наш отрицательный вывод упирался в разметку ToothFairy3, а не в
  принципиальную невозможность — вопрос данных.

### Мораль: «невозможно» надо проверять по ПЕРВОИСТОЧНИКАМ

Два вывода этого раздела — MB2 и пазухи — были сформулированы как
«невозможно» и оба оказались неверны в этой формулировке. Врач принёс ссылки
и был прав.

Разбор, почему ошиблись, одинаков в обоих случаях: **измерили задачу СВОИМ
инструментом и перенесли вывод на задачу вообще.**

- По MB2 мерили нашей сегментацией — а работает классификация среза.
- По пазухам мерили нашей моделью — а виновата разметка датасета, и не
  проверили эталон, пока не заставили.

Оба раза правильная формулировка звучит «не берётся ТАК-ТО» с указанием, что
именно упирается. «Невозможно вообще» — утверждение о мире, и на него нужны
основания сильнее, чем один неудачный замер на своих данных. Это ровно та же
ошибка, что уже описана в разделе про циклическую проверку, только в другую
сторону: там проверка питалась источником ошибки, здесь вывод питался
ограничением собственного инструмента.

### ВНЧС: задача решаема, но СУСТАВА НЕТ В КАДРЕ наших снимков

Врач принёс работы по суставу, и они убедительны. Ключевая
(PMC12236576): 150 томов, **воксель 0.3 мм — ровно наш**, поле зрения
10x10 см; точность 92.4%, чувствительность 90.8%, специфичность 93.7%,
AUC 0.95, согласие с рентгенологом kappa 0.89. Находки: эрозия мыщелка,
сужение суставной щели, остеофиты, уплощение, склероз. Эталон — ручная
разметка двух челюстно-лицевых рентгенологов. Сегментация мыщелка отдельно
доходит до Dice 0.92-0.98 (3D U-Net, MVEL-Net).

То есть по разрешению и по объёму данных задача нам по силам. **Упирается
она в другое — в поле зрения.** Замер по нашим кейсам:

```
кейс      том                поле зрения      верх нижней челюсти
client5   335x516x516        104 x 161 x 161  z=334 при верхе тома 334
client4   577x516x516        180 x 161 x 161  z=576 при верхе тома 576
client2   335x516x516        104 x 161 x 161  z=334 при верхе тома 334
```

Нижняя челюсть у ВСЕХ кейсов доходит ровно до верхней границы кадра, и в
трёх верхних срезах лежит 4-5 тысяч вокселей плотной ткани — том обрезан.

**Проверка, что обрезана именно ветвь, а не мыщелок:** площадь сечения
нижней челюсти сверху вниз монотонно РАСТЁТ (client4: 64, 106, 110, 180,
373 мм² на 0..4.7 мм ниже верха). У мыщелка форма обратная — округлая
головка, сужающаяся к шейке, и только потом расширение в ветвь. Значит в
кадр попал срез ветви, а суставная головка осталась выше поля зрения.

**Вывод для клиники, а не для кода: сустав мы не видим не потому, что не
умеем, а потому что его не снимают.** Чтобы делать ВНЧС, нужен протокол с
полем зрения, включающим суставные головки. Пока таких снимков нет, любая
модель для сустава обучаться не на чем.

### Архитектура: конвейер против одной сети — где мы уже стоим

Врач спросил, не разъедутся ли отдельные модели в трактовке одного места
(«одна скажет корень, другая пазуха»). Опасение верное — это известная
проблема анатомической согласованности. Но по этой оси **мы уже стоим в
правильной точке, и половина совета выполнена**:

- **Шаг 1 конвейера у нас есть и он многоклассовый.** nnU-Net выдаёт одну
  маску, где softmax гарантирует ОДИН класс на воксель. Конфликт «две сети
  по-разному пометили один воксель» для анатомии физически невозможен.
- **Логический модуль поверх масок есть** — `cbct_findings` и соседи считают
  геометрию по готовой маске, а не отдельной сетью. Именно поэтому находки
  не могут противоречить анатомии: они из неё выведены.
- **Анатомические правила пост-обработки есть**, и каждое откалибровано:
  `_filter_pulp` (пульпа обязана лежать внутри своего зуба),
  `TOOTH_BONE_MAX_MM` (зуб и коронка сидят в кости), правило моста между
  челюстями, `orient_sides` (сторона по геометрии).

**Чего у нас нет и что стоит взять из совета — каскад ROI.** Для микро-задач
(MB2) нужна вторая сеть, которой на вход подаётся не сырой кроп, а
**кроп ПЛЮС маска первой сети**: тогда микро-сеть опирается на анатомию, а
не спорит с ней. Это же снимает опасение врача — вторая модель не выносит
самостоятельного суждения о том, где зуб.

**Multi-task с общим энкодером не брать.** Минус, названный в совете
(переучивание ради одной задачи роняет остальные), для нас особенно дорог:
обучение ResEncL на этой машине идёт сутками, а `batch_size = 1` уже стоит
на пределе видеопамяти. Конвейер позволяет трогать одну задачу, не ломая
проверенные.

### Двухэтапная схема на 2D: ПРИНЯТА, данные под неё уже есть

Врач принёс рекомендацию строить 2D не одной сетью на весь снимок, а
каскадом: YOLO находит и нумерует зубы -> кроп зуба уходит в классификатор
градаций. Рекомендация верная, и её стоит взять — на панораме зубы
накладываются, а корни фронта размыты, поэтому сеть, которой скормили весь
снимок, путается.

**Данные под этот каскад у нас уже лежат.** DENTEX
`quadrant-enumeration-disease`: 705 снимков, 3529 аннотаций, и в КАЖДОЙ есть
три метки сразу — `category_id_1` квадрант (1-4), `category_id_2` номер зуба
в квадранте (1-8), `category_id_3` патология. Плюс bbox и полигон. То есть
номер зуба FDI размечен, и мы его до сих пор ОТБРАСЫВАЛИ, беря только
патологию.

Чего не хватает: подвыборки `quadrant-enumeration`, где размечены ВСЕ зубы,
а не только больные — она есть в DENTEX, но не скачана (`download_dentex.py`).
Без неё этап 1 обучится только на больных зубах.

Классы второго этапа берём геометрические, а не диагнозные:
`здоровый / поверхностный / глубокий (перегородка до пульпы сохранена) /
с экспозицией пульпы`. Последний класс — измеримая величина (толщина
перегородки до камеры), а не диагноз.

### Пульпит: расхождения с материалом врача НЕТ, есть разница в слове

Материал, который принёс врач, говорит буквально то же, что записано у нас:
«сам пульпит на ОПТГ увидеть невозможно», и ИИ идёт по КОСВЕННЫМ признакам —
слияние кариозной тени с камерой (вероятность экспозиции пульпы) плюс
расширение периодонтальной щели у апекса. Мы называли это «вероятность
вскрытия пульпы», источник называет «пульпит». Величина одна и та же.

Практический вывод: класс в интерфейсе завести МОЖНО, но называть его надо
тем, что измеряется. «Кариес проецируется на камеру зуба 46, перегородка не
прослеживается» проверяемо; «пульпит» — нет, это диагноз по боли и тестам
чувствительности.

**Мультимодальность даёт скачок, и это ожидаемо:** снимок плюс жалобы
пациента поднимают точность до 96-98% против 82-86% по снимку. То есть
прирост приходит из симптомов, а не из картинки — что ровно подтверждает,
почему по одному снимку диагноз не ставится.

### Осторожно с высокими числами в этой области

PMC12663471 заявляет 97.7% на СЕМИ клинических классах эндодонтического
состояния (включая «витальный бессимптомный» и «гиперчувствительный дентин»)
по одному снимку. Смотреть надо на выборку: 425 исходных изображений, тест —
**43 изображения**, аугментация до 1700 из ОДНОГО источника. Если копии
одного снимка попали и в обучение, и в тест, метрика недействительна. Авторы
сами признают single-source и отсутствие проверки в работе.

Это тот же класс ошибки, что мы уже ловили у себя: оценка на данных, близких
к обучающим. Сопоставлять такие числа с нашими 0.665 mAP нельзя.

### Эндо и ре-эндо на ОПТГ: факт да, качество — с оговоркой

Классы, предложенные в материале (`канал пуст / запломбирован качественно /
запломбирован плохо / запломбирован, но есть очаг`), разумны, и первый с
третьим берутся уверенно: наличие пломбировочного материала детектируется с
точностью 92-98% — гуттаперча яркая, сеть её видит легко.

**Но класс «запломбирован плохо» на панораме не работает даже у лидера
рынка**: у Diagnocat на ОПТГ короткая пломбировка F1 **8.3%**, пустоты F1
**14.3%**, «адекватность обтурации» 55.8% — при том что на КЛКТ у той же
системы >94%. Это измерено на их же данных.

Материал называет и причину, и она физическая: у верхних моляров 3-4 канала
на плоской панораме накладываются друг на друга и сливаются в одну-две
полосы — сеть видит «один канал, залит хорошо», когда два других пустые.
Плюс поиск апекса: на нижней челюсти корни моляров накладываются на канал
нерва.

Поэтому: факт лечения отдаём, очаг у корня отдаём, «пломбировка
неадекватна» — не отдаём без прицельного снимка. Это ровно та позиция,
которая уже занята по `fill_gap_mm` на КЛКТ.

### Пародонтит на ОПТГ: две РАЗНЫЕ задачи, и цифры у них разные

Врач принёс материал, где сказано «точность выше 92-94%». Проверка по
первоисточникам показала, что это число относится к ДРУГОЙ задаче, чем
стадирование, и обе задачи стоит различать.

**Задача 1 — бинарная, и она решена лучше, чем я считал.**
HC-Net+ (PMC12627451): «есть ли пародонтит стадии II-IV» против
здоровья/гингивита/стадии I. **AUROC 94.2%** — вот откуда 92-94%.
Обучение: 10 881 ОПТГ (10 400 без разметки для предобучения). И главное —
**эталоном служило полное пародонтологическое обследование с зондированием**
у 382 пациентов внешней выборки. Авторы прямо называют это первой моделью на
ОПТГ, связанной с КЛИНИЧЕСКИМИ диагнозами, а не с рентгенологическими
измерениями.

Это отменяет мою запись «публичного набора с парной клинической разметкой не
существует, поэтому валидировать стадию не на чем». Существует — его собрали.
Ценой 10 тысяч снимков и полного обследования сотен пациентов.

**Задача 2 — четырёхклассовое стадирование, и тут 0.77, а не 0.94.**
PMC8973652, двухэтапная схема ровно как в материале (UNet сегментация зубов
+ YOLO-v4 на ШЕСТЬ ключевых точек: CEJ, гребень, апекс — мезиально и
дистально), 640 панорам. **Точность 0.77**, по позициям зуба 0.71-0.81.
Эталон — только рентгенологическое чтение трёх пародонтологов, без
зондирования и потери прикрепления.

**И авторы этой работы пишут ровно то, что записано у нас:** «модель может
помогать со стадированием только РЕНТГЕНОЛОГИЧЕСКОЙ убыли кости», а
клинический диагноз требует данных сверх снимка.

**Итог, честно по обе стороны.** Моя формулировка «полную стадию по 2018
нельзя» верна и подтверждается первоисточником материала. Но я недооценил
бинарную постановку: «пародонтит II+ или нет» на клиническом эталоне даёт
AUROC 0.94, и это полезнее, чем звучит, — именно она отвечает на вопрос
«отправлять ли к пародонтологу».

**Что берём.** Схема с шестью ключевыми точками — это ТОЧНО то, что уже
работает в `cbct_perio` на КЛКТ: CEJ, гребень, мезиально и дистально
раздельно, результат в долях длины корня. Перенос на 2D прямой, алгоритм
известен, менять надо только способ поиска точек (на КЛКТ — по плотности
вдоль оси зуба, на 2D — регрессия ключевых точек).

Отдавать по-прежнему будем перцентиль своей выборки и проценты убыли, а не
клиническую стадию — но теперь у этого решения есть и вторая опора: сами
авторы стадирующей работы ставят ту же оговорку.

### Корни на 2D: что из материала подтверждается

- **Периапикальные очаги** — да, уже делаем (DENTEX). Оговорка про клыки
  (чувствительность 0.27) остаётся.
- **Резорбция корня** — коды есть у Diagnocat, но во ВСЕХ редакциях его
  официального списка для 2D отсутствуют; отдельной валидации не нашлось.
- **Вертикальные трещины корня** — материал сам признаёт, что на 2D они
  теряются из-за наложения тканей; на прицельных снимках отдельная работа
  даёт accuracy 0.80 у моляров, то есть уровень подсказки.

### Правило про разметку, которое дороже любой модели

Единственная панорамная работа, где ground truth подтверждён БИТВИНГАМИ,
даёт recall 0.96 против типичных 0.70-0.85 у всех остальных. Пары
«ОПТГ + прицельный того же пациента» от клиники стоят больше, чем смена
архитектуры. То же для пародонта: пара «ОПТГ + пародонтальная карта» —
единственный способ когда-либо валидировать стадию, и публичного такого
набора не существует.

### Где мы строже эталона

Diagnocat меряет ЦЭГ→гребень в миллиметрах ровно как `cbct_perio`, но
называет степень КЛИНИЧЕСКИ (mild/moderate/severe) — то есть несёт ровно тот
риск, от которого мы отказались в пользу перцентиля выборки. Их качество
эндо на ОПТГ: короткая пломбировка F1 8.3%, пустоты F1 14.3% — при том что
находки показываются. Наше решение считать `fill_gap_mm`, но не превращать в
находку, методологически честнее. Регуляторно у них на 2D нет клиренса FDA
вообще, а в ЕС устройство идёт как класс I (самосертификация).

## Двухэтапная схема на 2D: этап 1 — детекция и нумерация зубов

Первый шаг каскада, описанного выше. Своя подвыборка DENTEX, свой конвертер
(`convert_dentex_teeth.py`), свой набор `research/datasets/dentex_teeth`.

**Данные лежали всё это время, и мы их выбрасывали.** В архиве DENTEX три
подвыборки, распакована была одна:

```
quadrant-enumeration-disease   705 снимков, 3529 меток (5.0 на снимок)
quadrant_enumeration           634 снимка, 18095 меток (28.5 на снимок)
```

Вторая размечает ВСЕ зубы, а не только больные. Номер собирается из двух
полей: `category_id_1` даёт квадрант (индекс 0-3), `category_id_2` — позицию
(индекс 0-7); FDI = квадрант*10 + позиция. `convert_dentex_yolo.py` брал из
первой подвыборки только `category_id_3` (патологию) и номер зуба
выбрасывал — для одноэтапной схемы он был не нужен.

**32 класса, а не «зуб» плюс регрессия номера.** Номер это метка, а не
величина: между 18 и 21 нет среднего. Плюс сеть, знающая номер, опирается на
форму — моляр не спутать с резцом.

**Разбиение по СНИМКАМ, а не по зубам.** Зубы одного пациента похожи, и
разнеси их по обе стороны — метрика завысится. Та же ошибка, что в
официальном разбиении Teeth3DS (382 пациента и в train, и в test).

### Гоча обучения: batch 8 на 960 px не влезает в видеопамять

## Класс кости D1-D4 БОЛЬШЕ НЕ ВЫДАЁТСЯ

## ИМЕНА ФАЙЛОВ В ПОДВЫБОРКАХ DENTEX НЕЗАВИСИМЫ

Ловушка, стоившая одного обучения классификатора и почти уведшая в неверный
вывод «двухэтапная схема не работает».

`train_283.png` в `quadrant_enumeration` и в `quadrant-enumeration-disease` —
это РАЗНЫЕ СНИМКИ. Из 60 проверенных пар не совпал ни один байт, а размеры
изображений расходятся у 622 файлов из 634 (2710x1316 против 2872x1504).
Подвыборки нумеруют файлы каждая по-своему.

Сопоставление по имени приписывает метки патологий чужим снимкам. Симптом
обманчив: обучение идёт, потеря падает, метрика просто «низкая» — F1 кариеса
0.27 и не растёт. Легко списать на сложность задачи.

**Проверяется одним замером — перекрытием рамок ОДНОГО И ТОГО ЖЕ зуба:**

```
сопоставление по имени файла      медиана IoU 0.12, IoU>0.7 у  2%
сопоставление по содержимому      медиана IoU 0.94, IoU>0.7 у 88%
```

После правки F1 кариеса вырос 0.27 -> 0.39, глубокого 0.09 -> 0.31 при том
же коде обучения.

Соответствие строится по MD5 файлов и лежит в
`research/datasets/DENTEX/enum_to_disease.json`: **одни и те же снимки есть в
обеих подвыборках под разными именами, но их только 260 из 634.** Только на
них метки достоверны, и только они идут в набор кропов.

**Правило:** прежде чем соединять две разметки, проверить, что они говорят об
одних и тех же данных. Совпадение имён — не доказательство; доказательство —
совпадение содержимого или геометрии объектов.

Это тот же класс ошибки, что уже описан в разделах про обратную нумерацию
DentVoxel и про зеркальные стороны ToothFairy: две разметки выглядят
совместимыми, пока их не сверить замером.

### Находки на зуб у врача (`teeth2d`)

`demo_server.teeth2d_for(sid)` кэширует результат `opg_teeth_findings` в
`derived/teeth2d.json`: новые снимки считаются при обработке, старые — при
первом открытии (`/api/studies/<sid>/teeth`, около 2 с). Сводка и план
пациента читают только кэш (`compute=False`) — открытие карточки не должно
запускать модели.

- В план идут только находки, где согласны обе схемы; «под вопросом» —
  повод открыть снимок, а не основание для лечения.
- **Очаг у верхушки — отдельно от кариеса**, тем же правилом двух схем

  очаг на пролеченном зубе терялся — ровно там, где он важнее всего.
- Карточка снимка адресуется `?numbers=1&tooth=<FDI>`. Пока номера
  включены, рамки ансамбля приглушены: иначе подписи «Кариес NN%» закрывают

## Разметка: 19 классов вместо 4

`annotate_server.py` — классы в ОДНОМ справочнике `CLASSES`, фронт берёт их
по `/api/classes` (раньше была вторая копия в `index.html`). Добавлены по
списку врача: пульпит (кариес до пульпы), эндо и его дефекты, ре-эндо как
оценка врача, фрагмент и резорбция корня, убыль кости по третям корня,
фуркация, имплант, коронка, пломба.

  четыре класса ансамбля (`ENSEMBLE_CLASSES`), как в остальных копиях `wbf`.
- `?ds=<набор>` открывает набор по ссылке — и врачу, и для проверки

- Машинная предразметка набора клиники до расширения сохранена в

## Запуск после перезагрузки: туннель проверялся ПО ИМЕНИ ПРОЦЕССА

После перезагрузки машины снаружи оба адреса отдавали 530 при том, что
локально все три сервиса отвечали 200. Причина не в перезагрузке:

На машине живёт ВТОРОЙ туннель — `gamerly.yml`, другой проект пользователя.
`start_stomadent.ps1` проверял туннель так: `Get-Process -Name cloudflared`.
Чужой процесс есть — значит «туннель уже запущен», и наш (`config.yml`,
домены aicenterkk) не стартовал вовсе. Сбой молчаливый: скрипт рапортует
успех, лог туннеля остаётся вчерашним, а диагноз виден только снаружи.

Это ТА ЖЕ ошибка, которая уже была исправлена строчкой выше для демо — там
стоит комментарий «проверяем ПОРТ, а не имя процесса: python.exe на машине
крутится и по другим поводам». Туннель остался на старой проверке.

Теперь проверяется НАШ туннель — по файлу конфигурации в командной строке
процесса; и прежде всего проверяется служба Windows, если она установлена.

### Службы: туннель и сервисы до входа в систему

**Состояние на 14.10:** обе половины на месте — служба туннеля
(`C:\PROGRA~2\cloudflared\cloudflared.exe --config <config.yml> tunnel run`,
запуск Auto) и задача планировщика `Stomadent` (старт при загрузке, от
SYSTEM, задержка 30 с, `install_boot_task.bat`).

**ПРОВЕРЕНО перезагрузкой 12.11: демо под SYSTEM поднимается, CUDA в нулевом
сеансе работает.** Опасение было ровно в этом — там грузятся веса nnU-Net на
видеокарту, а служба живёт в нулевом сеансе. Замер: загрузка системы 00:32:17,
старт сервисов 00:33:02 (ровно задержка 30 с из задачи), демо в списке
процессов с контекстом CUDA у `nvidia-smi`, `demo.err.log` пуст, снаружи 200.
Отработало пять суток без вмешательства.

Признак, по которому это видно из обычного шелла: у процессов SYSTEM владелец
и командная строка читаются пустыми — `Get-CimInstance Win32_Process` без прав
администратора их не отдаёт. Пустое поле здесь означает «не наш сеанс», а не
«сбой».

Если когда-нибудь снаружи окажется 502 — смотреть `data\logs\demo.err.log`:
тогда это будет про CUDA в сеансе службы, и задачу надо переводить с SYSTEM на
учётную запись врача с галочкой «выполнять вне зависимости от регистрации
пользователя».

**Три грабли, на которых это заняло час:**

1. **Служба без аргументов.** `cloudflared service install` зарегистрировал
   службу как просто `cloudflared.exe` — без `--config` и `tunnel run`. Она
   числится Running, туннель не поднимает, снаружи 1033/530, лог пуст.
   «Служба есть» — ещё не значит «служба работает»: сверять `sc qc`.
2. **`sc stop` висит на такой службе.** Она не отвечает на команду
   остановки, залипает в StopPending, и скрипт установки висит вместе с ней.
   Лечится только снятием процесса по PID (`sc queryex` -> `taskkill /F`) и
   пересозданием службы.
3. **Окно с правами администратора не видно инструментам.** Запущенный через
   UAC скрипт выводит всё в свою консоль, снаружи это выглядит как «ничего не
   происходит». Такие скрипты обязаны писать ход в файл
   (`data\logsix_tunnel_service.log`).

Вложенные кавычки в `binPath=` и `/TR` не нужны и опасны (cmd, sc и
PowerShell разбирают их по-разному): пути берутся без пробелов —
`C:\PROGRA~2\...` и `D:\code\dbc\stomadent\...`.

### Что делает установщик (`install_services.bat`)

Автозапуск из папки «Автозагрузка» работает только ПОСЛЕ входа в учётную
запись. Пока сервер стоит перезагруженный и никто не залогинился, клиника

* задача планировщика `Stomadent` при загрузке от имени SYSTEM, запускает

Чужой туннель (`gamerly.yml`) службой не делается и не трогается.

**Проверять это надо НЕ ВХОДЯ в систему** — перезагрузить и открыть

разбор падает на `TerminatorExpectedAtEndOfString` в произвольной строке

## Языковой слой: СВЯЗАТЬ, а не решить

Два модуля, и роль у модели в обоих узкая намеренно.

- **`plan_agent.py`** — изложить план лечения связным текстом, поймать
  противоречия между источниками, сказать, чего не хватает для решения. Что
  лечить, решают правила `cbct_plan`.
- **`case_chat.py`** — чат по открытому кейсу: `POST /api/cbct/chat/{case_id}`.

**Почему модель не решает.** Весь продукт держится на проверяемости: у каждой
находки есть основание — что измерено, каким методом, при каком пороге. Текст
модели звучит уверенно и не проверяем ничем. Поэтому защита механическая:

- в контекст уходят только находки, зубы и ручная проверка ЭТОГО кейса;
- ФИО, дата рождения, номер карты и снимки не уходят вовсе
  (`plan_agent.check_anonymous`); при утечке — отказ без обходного пути;
- ответ обязан назвать ключи находок (`cbct_backend.finding_key` — те же, что
  у отметок врача, поэтому ссылка кликается в строку ленты). Несуществующие
  отбрасываются, и если опоры не осталось, показывается отказ, а не текст;
- **числа с единицами сверяются с данными отдельно.** «1.6 мм» и «6.1 мм»
  одинаково убедительны, а решение по ним разное. Допуск 0.1 мм и 2% — чтобы
  законное округление не считалось выдумкой.

Эта защита не ловит ОДНОГО: число может быть взято из данных, но привязано к
чужой находке. Проверяется наличие числа, а не его принадлежность.

### Имена моделей: только псевдонимы с `-latest`

Приколоченные номера версий провайдер снимает без предупреждения. Замер
17.11 одним прогоном:

```
gemini-3.8-flash            503  высокая нагрузка — жива, но не всегда
gemini-3.5-flash            503  то же
gemini-flash-lite-latest    OK
gemini-2.5-flash-lite       OK
gemini-2.5-flash            404  «больше не доступна»
gemini-2.0-flash            404  «больше не доступна»
```

Поэтому в списке всегда должен быть хотя бы один `-latest`, и перебор идёт
сверху вниз.

**Гоча, стоившая неверного вывода:** сообщение провайдера извлекалось и
выбрасывалось, в логе оставалось «HTTP 404» без причины. По этому я заключил,
что `plan_agent` сломан, — а он исправно переходил на рабочую модель. Разные
коды лечатся по-разному: 404 требует правки списка, 503 — просто повтора.
Теперь сообщение показывается целиком.

## Кейс БЕЗ ТОМА: SimpleITK роняет процесс, а не запрос

Демо-кейс из `fixtures/` состоит из меша и посчитанных находок: том весит
сотни мегабайт и в репозиторий не кладётся. На таком кейсе `sitk.ReadImage`
пути, которого нет, даёт **access violation и убивает весь процесс** —
исключения не бросает, поэтому `try/except` вокруг него бесполезен, а в логе
не остаётся ничего.

Так пропадало демо: фронт на этом кейсе запускал сегментацию, рабочий поток
читал несуществующий том, и сервер исчезал — страница оставалась на «строим
3D…». Диагноз нашёлся только через `python -X faulthandler`, который печатает
стек при фатальном сигнале.

Правило: **перед передачей пути в SimpleITK проверять файл.** Проверки стоят
в трёх местах — `_arrays_for`, `_run_inference`, `_segment_worker`; кейс без
тома, у которого меш и находки уже посчитаны, считается готовым, а не ошибкой.

Эндпоинты, которым нужны воксели (срезы, панорама, карточка зуба, список
зубов), отвечают 409 через `_voxel_model`, а фронт узнаёт об этом заранее по
`has_voxels` в `/api/cbct/info` и не показывает эти вкладки: вкладка, которая
всегда отвечает ошибкой, читается как поломка.

**Гоча при этой же правке:** массовая замена проверки по шаблону задела и
эндпоинт НАХОДОК, которому воксели не нужны вовсе, — лента находок погасла
целиком, а причина выглядела как поломка чата. Менять такие места списком, а
не доверять счётчику совпадений.

## Состояние кейса пишется туда, откуда читали

`_save_meta` сохраняет `meta.json` через `case_dir(c)`, а не в `CASES_DIR`.
Иначе отметки врача на фикстуре уезжали в `web_cases/<id>/meta.json`, и этот
огрызок — без тома, без меша, но с тем же `case_id` — при следующем запуске
ЗАТЕНЯЛ фикстуру: `register_fixtures` видел занятый номер и молча её
пропускал, а список примеров оказывался пуст. Затенение теперь печатается в
лог, а не происходит молча.

Файл пишется с отступами: `meta.json` фикстуры лежит в гите, и после одного
клика в демо diff показывал «1722 строки удалено, 1 добавлена» вместо трёх
строк отметки.

## Уровень критичности и надёжность — ОДИН справочник

Три уровня (Критичная / Важная / Незначительная) переводятся из `severity`
один к одному, а слово, короткий бейдж, цвет и формулировка для пациента
живут в `clinic_routes.LEVELS` — там же, где роли. Своих копий заводить
нельзя: они уже расходились. В PDF `info` назывался «к сведению» и рисовался
СИНИМ, на экране — «Незначительная» и серым; врач читал бумагу иначе, чем
снимок.

Неизвестное значение `severity` НЕ подставляется нижним уровнем: критичная
находка молча прочиталась бы как норма. Для него отдельный уровень с честной
подписью, и он идёт первым в списке.

Надёжность находки (`confidence`) отдаётся СЛОВОМ — высокая / средняя /
низкая. Процента уверенности у находки нет и не будет: вероятности мы не
считаем, находки геометрические. Измеренный процент один и относится к
другому слою — точности распознавания зубов (96.9%, 95% ДИ 96.2-97.6, 100
пациентов DentVoxel); он печатается только для модели, на которой измерен, и
прямо так и назван.

## Чат: счёт сверяется с ТЕМ счётчиком, который назван

Сверять все целые числа ответа со всеми числами данных бесполезно: номера
зубов 11-48 покрывают почти любое малое число, и выдуманные «9 проблемных
зон» при семнадцати проходят насквозь (проверено). Поэтому `_unsupported_counts`
берёт число ВМЕСТЕ с тем, что оно считает («17 находок», «6 важных», «31
зуб», «4 этапа»), и сверяет с настоящим счётчиком. Количество визитов и сроки
лечения не считаются ничем — любое их число блокируется, а не сверяется.

Ответ БЕЗ ключей находок при этом принимается: на вопрос «сколько находок»
опоры в виде отдельной находки не существует, а прежнее правило «нет ключей —
нет ответа» резало верную сводку целиком.

Таймаут провайдера — повод перейти к следующей модели, а не уронить запрос:
раньше `TimeoutError` улетал наружу, и сводка отвечала пятисоткой после
минуты ожидания. Ожидание на модель 20 с (обычный ответ приходит за 1-6).

## Перспектива в 3D: «деформация» бывает объективом, а не данными

Жалоба с показа: кость на заставке спереди сходится в точку, а дальше
становится шире — геометрия выглядит сломанной. Первым делом проверяются
ДАННЫЕ, а не вёрстка.

Замер расстояния от зуба до челюстной кости по самому мешу (тот же, которым
ловили «зубы съехали с кости»):

```
зубов 31 · медиана 2.02 мм · 90-й перцентиль 2.84 · максимум 3.12
дальше 3 мм — 2 зуба, дальше 6 мм — ни одного
```

Данные верны. Виноват объектив: расстояние камеры считалось от ЗУБОВ, а
череп вдвое больше — камера стояла внутри его габарита.

```
угол 35°, расстояние 226 мм     ближний край крупнее дальнего в 1.81 раза
угол 18°, расстояние 451 мм     1.34
ортографическая камера          1.00
```

**Правило: прежде чем искать деформацию в меше, посчитать отношение
«дальний край / ближний край».** Для анатомических видов, где важны
пропорции, ортографическая проекция честнее перспективной — так рисуют
рентген и технические виды.

**И вторая половина правила, оплаченная повторной жалобой: один и тот же
баг живёт на КАЖДОМ экране, где рисуется та же модель.** Заставку
(`home.html`) починили, а разбор (`index.html`) — экран, на котором врач
и работает, — остался с перспективной камерой, причём с углом 45° вместо
35°: раздутие там было **2.38**. Починка одного экрана не закрывает
жалобу; проверять надо все экраны с 3D. Замер обоих — `window.__heroDbg`
и `window.__viewDbg`, оба отдают «раздутие» числом.

Во вьюере у перехода на параллельную проекцию есть следствие, которое
легко пропустить: **приближение перестаёт зависеть от расстояния**.
Пролёт камеры к зубу обязан тянуть `camera.zoom`, иначе он красиво
двигает камеру и ничего не приближает. Целевую крупность берём из того же
множителя расстояния, что был при перспективе (half = dist · tg(45°/2)) —
тогда кадр сохраняется без подбора новых чисел.

**Полупрозрачная кость рисуется ДАЛЬНЕЙ стенкой (`BackSide`) и во
вьюере тоже.** При `DoubleSide` десятки налегающих оболочек умножают
затемнение, и зубы тонут в молочной пелене; аддитивное смешивание съедает
тонкую альвеолярную кость вокруг корней. При 100% прозрачности сторона
возвращается в `FrontSide`, иначе непрозрачная кость выглядит вывернутой.

**Гоча ПРОВЕРКИ, а не кода:** headless-клиент создавал вкладку через
`/json/new?<url>`, и Chrome обрезал адрес по первому `&` — ссылка
`?tab=tooth&tooth=13` приходила в страницу без зуба, и десять минут
казалось, что сломана адресация вьюера. Вкладка открывается пустой, адрес
задаётся `Page.navigate`. Третий раз в проекте, когда врёт инструмент
проверки, а не проверяемое.

**Смещать модель вбок, чтобы освободить место под текст, НЕЛЬЗЯ.** Она
уходит с оптической оси, и у края кадра перспектива её растягивает;
при вращении искажение ползёт по модели. Сдвигать надо КАДР —
`camera.setViewOffset`, камера при этом продолжает смотреть по оси.

**У нашего GLB нет нормалей** — только позиции вершин (меш строят marching
cubes и упрощение). Любой освещённый материал без нормалей заливает модель
ровным цветом, и она читается силуэтом. Вьюер считает их сам
(`computeVertexNormals`), любой новый просмотрщик обязан делать то же.

**Полупрозрачная кость: `BackSide`, а не аддитивное смешивание.** Оболочка
челюсти — десятки налегающих поверхностей: обычная прозрачность умножает
затемнение и топит зубы в чёрное, аддитивная высвечивает толстые ветви и
полностью съедает тонкую альвеолярную кость вокруг корней (зубы выглядят
висящими в воздухе, хотя в данных сидят в кости). Дальняя стенка не
закрывает зубы вовсе и даёт силуэт.

## Соглашения

- Скрипты — самостоятельные CLI: докстринг с примером запуска, `argparse`,
  `main()`, пути через `Path(__file__).resolve().parents[N]`.
- Комментарии объясняют **почему** (особенно эмпирические пороги и обходные пути
  для Windows), а не что делает строка. Образец стиля — `cbct_backend.py`.
- API-ответы демо отдаются с `Cache-Control: no-store` (меши и срезы
  перестраиваются между версиями) — middleware в `demo_server.py`.
- **Имя человека не попадает ни в код, ни в комментарии, ни в этот файл —
  чьё бы оно ни было.** Перед первым push в GitHub нашлось три таких строки:
  фамилия стояла рядом с client2/client4 как имя кейса, на котором меряли
  порог (это был собственный снимок автора, не пациента, но правило одно и то же:
  строка связывает имя с медицинским замером и уходит в публичный репозиторий).
  Для ссылки на замер хватает идентификатора кейса; соответствие «кейс -> человек»
  живёт только в `research_3d/patient_map.json`, который в `.gitignore`.
- Пути к файлам, приходящие из HTTP, всегда валидируются регуляркой и проверкой
  родительского каталога (`_example_path`, `dataset_dir`, `get_case`).
