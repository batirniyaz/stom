## Показываем ТОЛЬКО КЛКТ

2D-панорамы и интраоральные сканы на показ не идут. Код не удаляем — он
работает и остаётся в проекте, — но в демонстрации их нет. Один трек,
сделанный до конца, сильнее трёх начатых. На КЛКТ находки от 2D не зависят,
поэтому ничего не ломается.

## Сценарий показа

```
главная  ->  список пациентов  ->  один пациент  ->  его КЛКТ  ->  останавливаемся здесь
```

На экране КЛКТ видно и работает:

1. **3D вращается сама**, медленно; руками вращается как раньше. ✅
2. **Какие находки** — по специальностям, не сплошной лентой. ✅
3. **Почему именно такие** — основание: что измерено, сколько, при каком
   пороге, при каком вокселе. ✅
4. **Насколько надёжно** — словом у находки, измеренным процентом у системы. ✅
5. **Насколько критично** — три уровня. ✅
6. **Зубы поштучно** — карточка зуба со срезами вдоль собственной оси. ✅
   (на демо-кейсе из `fixtures/` недоступна — нужен исходный том)
7. **Врач подтверждает или отклоняет** каждую находку, пишет комментарий,
   может поменять уровень и формулировку, затем подписывает набор. ✅
8. **PDF в конце, двух видов**: врачу с терминами, пациенту разжёванный. ✅

## Решения, принятые по дороге

### Шкала — ТРИ уровня (В2 спеки закрыт)

Критичная / Важная / Незначительная, бейджи Крит / Важн / Незнач, цвета
красный / жёлтый / серый, без оранжевого. Перевод из `severity` один к одному.

Слова, цвета и формулировки для пациента лежат в ОДНОМ месте —
`clinic_routes.LEVELS`. Копий больше нет: они уже успели разойтись — в PDF
`info` назывался «к сведению» и рисовался синим, на экране «Незначительная» и
серым.

### Уверенность — словом; процент только измеренный (В1 спеки)

На карточке находки стоит **надёжность измерения**: высокая / средняя /
низкая. Процента там нет и не будет — вероятности у находки не существует,
она посчитана геометрией по маске, и калибровать процент не на чем.

Измеренный процент в отчёте один и относится к другому слою:

```
Точность распознавания зубов 96.9% (95% ДИ 96.2–97.6%),
100 пациентов, 2923 зуба, внешняя выборка DentVoxel
```

Печатается только для модели `sp`, на которой это и мерили, и прямо назван
точностью РАСПОЗНАВАНИЯ ЗУБОВ, а не точностью находок: разметки рентгенолога
в проекте нет, поэтому «модель верно находит очаг в N%» сказать нечем.

### Комментарий врача — 10 символов плюс два настоящих фильтра

Длина из спеки почти ничего не отсекает: «подтверждаю» — 11 символов. Реально
фильтруют два правила: после удаления слов согласия должно остаться хоть одно
слово по существу, и текст не должен быть копией объяснения ИИ. Отказ
возвращается врачу дословно — он объясняет, чего не хватает.

## Перенос макета: этапы

Направление переноса: в прототипе (`site/`) — вид и сценарий, в рабочем демо —
настоящие 3D, находки, проверка и PDF. Переносим ВИД на демо, а не наоборот:
обратный перенос означает переписать весь движок.

| Этап | Что | Состояние |

| 0 | Палитра, знак Actina, полноэкранный экран разбора | ✅ |
| 0 | Главная с 3D, вход врача, шапка без вкладок модальностей | ✅ |
| 1 | Список пациентов строкой: жалоба, счёт уровней, прогресс разбора | ✅ |
| 2 | Карточка пациента: анкета, чипы аллергии и лекарств, заметка | ✅ |
| 3 | Пролёт камеры к зубу, показ одного зуба, карточка структуры, заключение на экране | ✅ |
| 4 | Профиль врача: имя один раз, подставляется в подпись и отчёт | ✅ |
| 5 | Новый пациент и новый снимок — боковыми панелями | ✅ |
| 6 | Сквозная проверка сценария | ✅ |

**Анкета пациента НЕ заведена в базе** — это решение. Вести медицинскую
анкету (согласия, доступ, хранение персональных данных) — отдельный
продукт, а девять колонок под показ дали бы девять пустых граф у настоящих
пациентов. Анкета лежит рядом с ростером (`patients.DEMO_PROFILES`) и
отдаётся ТОЛЬКО карточкам с пометкой «пример».

**Мастера нового пациента из макета нет по той же причине**: его второй шаг —
как раз эта анкета. Форма осталась прежней, но переехала в боковую панель.

### Что проверено сквозным прогоном

```
кейс client5: находок 6, в ручную проверку 3
PDF до разбора       HTTP 409   (закрыт, как и задумано)
отметки врача        9 из 9 приняты
после разбора        6 из 6, отчёт готов
PDF врачу            200, 364 КБ, это PDF
PDF пациенту         200,  56 КБ, это PDF
откат отметок        0 из 6 — показ начинается с чистого кейса
```

Вход: главная → панель входа → неверный код отклонён → список пациентов с
именем врача в шапке. Горизонтальной прокрутки нет ни на одном экране.

**Карточку пациента не заменяем, а дополняем.** В рабочем демо она богаче
макетной: вкладки «Обзор / Находки / План лечения / Фотопротокол /
Исследования», плитки со счётом, зубная карта по всем исследованиям и раздел
«что можно посчитать» с оговорками. В макете этого нет — там анкета человека.
Нужно и то и другое.

## Какой кейс показываем

На главной и по кнопке «Посмотреть демо-кейс» открывается снимок С АППАРАТА
КЛИНИКИ (`client5`), а не публичная фикстура. Причина видна глазом на
заставке во весь экран: на фикстуре модель путает зубы, а позади черепа у
неё вырастает лишний зуб. На снимке клиники тех же артефактов нет.

Выбор делает сервер (`SHOWCASE_CASES` в `demo_server.py`), а не фронт: какой
снимок лучше выглядит в 3D — вопрос данных. Фикстура остаётся запасным
вариантом: на машине, где снимков клиники нет, показывать больше нечего.

**Имена к кейсам не привязаны.** `research_3d/patient_map.json` пуст, то есть
соответствия «кейс → человек» в данных не существует вовсе, и на публичный
адрес уезжает только геометрия челюсти.

## Данные для разработки

`fixtures/cbct_pair001/` — готовый кейс КЛКТ: меш и посчитанные находки,
публичный набор CC BY 4.0. Исходного тома в нём нет и не будет (сотни
мегабайт), поэтому срезы, панорама и карточка зуба на нём не работают —
интерфейс эти вкладки просто не показывает (`has_voxels` в `/api/cbct/info`).

На пустой базе сервер заводит пациента-пример для этого кейса: иначе сценарий
показа начинается с пустого списка пациентов.

Подробности — `../SETUP.md`.

## Чат: что именно защищает ответ

Защита механическая, а не промптом (`case_chat.py`):

- в контекст уходят только находки, зубы, план и ручная проверка ЭТОГО кейса;
- ФИО, дата рождения и снимки не уходят вовсе (`plan_agent.check_anonymous`,
  при утечке — отказ без обходного пути);
- ответ обязан назвать ключи находок; несуществующие отбрасываются;
- **числа с единицами сверяются с данными** — «1.6 мм» и «6.1 мм» одинаково
  убедительны, а решение по ним разное. Допуск 0.1 мм и 2% на округление;
- **счёт сверяется с тем счётчиком, который назван** («17 находок», «6
  важных»); количество визитов и сроки не считаются ничем, поэтому любое их
  число блокируется.

Ключ: `ANTHROPIC_API_KEY` в `data/secrets.env`; пока его нет — работает через
`GEMINI_API_KEY`. Замер: ответ 4 с, сводка 4–6 с.

## Грабли, на которых уже потеряно время

**SimpleITK на несуществующем файле роняет ПРОЦЕСС, а не запрос.**
`ReadImage(None)` даёт access violation; `try/except` вокруг не спасает, в
логе пусто. На кейсе без тома это валило весь демо-сервер: страница
открывалась «строим 3D…», и демо исчезало. Проверять пути до вызова.

**Состояние кейса пишется туда, откуда читали.** Отметки врача на фикстуре
сохранялись в `web_cases`, и огрызок с тем же номером при следующем запуске
затенял саму фикстуру — список примеров оказывался пуст.

**Массовая замена по шаблону задевает лишнее.** Замена проверки «есть ли
воксели» прошлась и по эндпоинту находок, которому воксели не нужны, — лента
находок погасла целиком. Проверять каждое место списком, а не доверять
счётчику совпадений.
